A delegated coding session can pass that review cleanly while the\ndiff still carries hundreds or thousands of lines of non-functional bloat that\na human reviewer will immediately notice and be annoyed by. Run this as an\nexplicit pass before finalizing/merging a PR built by a coding agent — do not\nwait for the user to catch it manually.\n\nObserved case: a forward-scrub-control feature PR passed a high-confidence\n(88) `pr-review-toolkit` review with zero CRITICAL/HIGH findings, and passed a\ndedicated complexity/over-engineering review as \"right-sized\" — yet still\ncarried ~1,370 lines of pure reformatting churn and dozens of over-verbose\ncomments once audited, all introduced incidentally by the rename/refactor\nwork. The user caught it by eye (\"there is a big diff which is basically just\nexpanding imported functions... stop half doing shit and do it properly\").\n\n## The two bloat classes\n\n1. **Expansion/reflow churn.** A coding agent touches one line inside an\n   import/destructure/JSX call/argument list and, as a side effect, explodes\n   the whole single-line statement into multi-line, or reindents a block it\n   didn't need to touch. This is NOT limited to renames — any edit that adds\n   one identifier to an existing statement can trigger it.\n   - **`git diff -w` (whitespace-insensitive) under-counts this.** It only\n     collapses content-identical reflows (pure whitespace/comma changes). It\n     does NOT catch reshaping where lines are genuinely added/reordered as\n     part of the explosion (e.g. a single-line import with 6 names becomes 7\n     lines to add 1 name) — those still read as \"real\" changes to `-w`, so\n     line-count deltas from `-w` are not a reliable churn signal.\n   - **Audit by comparing shape, not just diff stats.** For each changed file,\n     check whether main's version of the touched statement was single-line\n     and would still be single-line/short enough to stay that way with just\n     the new content added. If yes, the multi-line explosion is pure churn —\n     collapse it back to base's shape and reapply only the genuinely new\n     token(s).\n   - **Respect prettier's actual constraints when collapsing.** If the real\n     new content pushes a line past the project's print width, multi-line\n     IS the correct prettier-canonical shape — don't fight the formatter.\n     The churn to avoid is defaulting to multi-line even when the edit\n     doesn't require it, not multi-line per se.\n   - **A \"collapse pure-churn hunks\" first pass under-fixes this.** Only\n     stripping hunks that are byte-identical (whitespace/comma-only) misses\n     real reshaping. To fully normalize, instruct the cleanup session to\n     collapse each file's *shape* to base's shape wherever the actual edit\n     doesn't require a different shape — not just to strip whitespace-only\n     hunks. Expect at least two passes: one broad collapse, then an audit\n     pass across the *whole* diff (not just the files flagged first) because\n     large files (providers, machines, big test files) hide the same pattern\n     inside otherwise-legitimate new logic.\n\n2. **Comment bloat.** Coding agents tend to over-comment renames and\n   refactors: restating what the code already shows, narrating a superseded\n   prior state (\"previously X did Y, now it does Z\" — irrelevant once merged),\n   or labeling something already self-evident from the code. Do an explicit\n   strip pass; this convention (terse, present-tense, necessary-only comments,\n   no narration of past/fixed behavior) applies to every repo, not just one —\n   don't rely on the review gate to catch violations.\n\n## Procedure\n\n1. Run this AFTER functional/spec review has passed, before finalizing/\n   merging the PR. Don't skip it just because review came back clean —\n   review approved means behavior was checked, not that the diff is lean.\n2. Get real numbers first: `git diff --stat base..HEAD` split by\n   test/non-test files, then eyeball a few of the largest non-test files'\n   diffs directly (not through `-w`) for the shape pattern above.\n3. Dispatch the collapse/strip as its own coding-agent session (same\n   delegation-boundary discipline as any other code change — don't hand-edit\n   dozens of files yourself). Give it BOTH instructions explicitly: normalize\n   diff *shape* to base wherever the real edit doesn't require a different\n   shape, AND strip comment bloat per the terse-comment convention. A session\n   given only \"remove churn\" will often do the narrow content-identical\n   version and miss reshaping.\n4. **Verify the working tree yourself — never trust the session's self-report\n   of \"diff is now minimal.\"** Two independent failure modes observed:\n   - The session reports a shrunk diff/green tests, but the *actual* working\n     tree or committed HEAD doesn't match the report (e.g. it reverted its own\n     collapse locally while the earlier commit still has the churn, or vice\n     versa). Always `git diff --stat` / inspect the real HEAD yourself.\n   - The session's collapse leaves files in a formatter-dirty state (real\n     edits present, but not in the project's canonical prettier/lint shape)\n     even though the *diff* looks minimal — check `pnpm run format`/linter\n     on the touched files, not just line counts.\n5. Re-run the full test suite + lint + typecheck yourself after the audit\n   pass, same as after any other code change — a diff-shape cleanup can still\n   introduce a real regression (wrong identifier collapsed, wrong brace\n   dropped).\n6. Repeat audit + collapse across the WHOLE diff, not just the first files\n   flagged — a single pass tends to catch the obvious small files and miss\n   the same pattern buried inside large files with legitimate new logic\n   (providers, state machines, big test files).\n\n## Self-imposed formatter gates cause exactly this churn — verify the gate is real first\n\nBefore requiring `ruff format --check` / `black --check` / `prettier --check`\nto pass as part of your own brief to a coding session, confirm the project's\nCI actually enforces it (and at what pinned version). Observed case: a T2\nbrief told the implementer \"run ruff format --check\" as a self-imposed\nquality bar; the tool version in the venv (ruff 0.16.4) formatted\ndifferently from whatever produced the base branch, so satisfying the check\nmeant reformatting 10 files (310+/194− of pure reflow) for a one-line\nfunctional fix. Investigation showed the repo's CI has **no ruff step at\nall** and no pre-commit pin — the gate was invented, not real, and the\n\"fix\" it demanded was the bloat this skill exists to strip.\n\n- Check `.github/workflows/*.yml` and any pre-commit config for the actual\n  enforced formatter + pinned version BEFORE writing \"must pass X --check\"\n  into a coding-session brief. If nothing pins it, don't invent the gate —\n  ruff/black's own default style can and does drift between versions, and a\n  local venv's installed version reformatting to ITS OWN idea of canonical\n  style is not evidence the base branch is non-compliant with anything real.\n- If a self-imposed gate already caused a reformat commit, it's fully\n  reversible: diff that commit against the true functional need (the actual\n  regex/logic fix) and revert everything else file-by-file back to the base\n  branch's formatting — same procedure as the rest of this skill, just with\n  a clearer root cause (the gate itself, not the coding agent's judgment).\n- A useful confirming test when in doubt: run the checker against the BASE\n  branch (before any of your session's commits) with the same locally\n  installed version. If the base branch itself fails `--check`, the gate is\n  not actually enforced anywhere upstream and your session's compliance\n  attempt is pure self-inflicted churn, not a real fix.\n\n## Related, smaller orchestration nuance (kanban claim vs status)\n\nWhile driving a manually-claimed kanban task end-to-end (not through the\ndispatcher), `hermes kanban claim <task_id>` does NOT transition the task's\nstatus to `running`. `heartbeat` and status-transition helpers expect\n`running`, so a claimed-but-still-`ready` task can reject those calls with no\nobvious dispatcher-free \"mark running\" verb (the dispatcher path spawns a\nworker you don't want when you're driving manually yourself). Don't burn\ncycles hunting for the right CLI incantation — the claim itself is still the\nreal duplicate-work guard, independent of status text. Track progress via\n`hermes kanban comment` instead, and use the review-transition helper script\nfor the review-state move (it tolerates the ready/running mismatch).\n\n## Related orchestration nuance (server lifecycle across manual QA)\n\nA dev/demo server started for a human's manual QA pass, if launched from\ninside a coding agent session's own foreground shell/tmux pane, dies the\nmoment that session exits (its foreground processes die with it). Once coding\nwork finishes and a human is about to run a multi-turn manual test checklist\nagainst that server, restart it as an independently tracked\n`terminal(background=true)` process so it survives across the coding\nsession's lifecycle and doesn't die mid-checklist.\n
