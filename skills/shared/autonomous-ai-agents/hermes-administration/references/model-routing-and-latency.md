# Model Routing Changes and Latency Checks

## Switching models
1. Echo back the exact model id before writing config (for example `openai-group/gpt-6-sol`, not a same-family neighbor such as `gpt-5.6-sol`). Near-miss version numbers are an easy mistake; the user notices when the runtime banner shows the wrong model.
2. Change every requested role explicitly: `model.default`, `model.provider`, `delegation.model` and `delegation.provider`. Leave auxiliary/review models alone unless named.
3. Apply the same change to every machine the user named (local and remote host), then read the values back on each.
4. Stay within the user's allowed model group. Stop and ask if the model exists only in another billing group.
5. OpenAI reasoning models that reject function tools with `reasoning_effort` on chat completions need a provider entry using the Responses transport (`transport: codex_responses`). Use a separate provider entry for those models so other models on the same gateway keep chat completions.
6. Set context length per model under the provider's model entry when the gateway's model list lacks metadata; verify the resolved context in a fresh session.
7. Existing sessions and running gateways keep their loaded model/config. Start a fresh session or restart the gateway after the change.

## Adding a model alias (opt-in, no default change)
1. Probe the exact id first: `hermes chat --model <group/id> --provider <provider> -q 'Reply exactly PONG. Do not use tools.' -Q`. Gateway ids use hyphens for versions (`claude-group/claude-sonnet-5-5`), so confirm the route answers before writing config.
2. Pin context per model: `hermes config set 'providers.<provider>.models.<group/id>.context_length' <n>`, copying the value from the same family's existing entry.
3. Add the alias with the short form: `hermes config set model.aliases.<name> '<provider>/<group/id>'`. Follow the naming style of the existing aliases (`hermes config get model.aliases`). `model.aliases` accepts only these `provider/model` strings; an alias that needs its own `base_url`/`api_key` is a dict under top-level `model_aliases:` (`model`, `provider`, `base_url`, `api_key` or `key_env`). Dict entries placed under `model.aliases` are silently ignored and the run falls through to the default model.
4. Repeat on every host the user uses (local Mac and the remote host via its full venv `hermes` path), then read back the alias, the context length, `model.default` and `model.provider` to show the default is unchanged.
5. A PONG reply proves nothing alone: if the primary call fails, `fallback_providers` answers instead. First grep `~/.hermes/logs/agent.log` for the session id: the `conversation turn: ... model=... provider=...` line shows whether the alias resolved, and any `Fallback activated` line means the reply came from the fallback. Then verify with a fresh alias run (`hermes chat --model <name> -q ... -Q`) that includes a unique marker, and check `~/.hermes/state.db` read-only: in `session_model_usage`, look only at the row with an empty `task` (the main model). Rows with `task=title_generation` or other auxiliary tasks show the auxiliary model and are expected. `billing_provider` shows `custom` for named custom providers, so check the `billing_base_url` hostname instead of the provider name.
6. Do not change launchers, `model.default` or delegation settings when the user asked only for an alias. Tell them how to use it for a new session (`hermes -m <name>`), and mention the billing group if it differs from the default.

## Adding a new authenticated gateway provider (extra headers, requested slugs)
1. Get auth working before anything else: list `/v1/models` with every header the gateway needs. Gateways that layer a membership token on top of a caller key (for example caller key in `x-tfy-api-key` or `Authorization: Bearer`, plus a membership token in `x-maat-token`) return 401/403 "missing caller key" / "not a member" when a header is missing or swapped. Read the error text and fix the header combination before calling the key bad.
2. Check every requested slug against that list, then send a tiny `chat/completions` probe (`Reply exactly PONG`) to each. A 403 "not authorized to access model" means the account lacks that model group. Probe the bare id and sibling groups (`gpt-6-sol`, `codex-group/...`) so you can say what works now.
3. Configure as a named provider: `providers.<name>` with `api`, `api_key`, `extra_headers` for the membership token, and `models.<slug>.context_length` per model. Apply the same entry on every host, then read back the `api` value, the model list and whether headers are present (no secret values).
4. Report plainly which requested slugs are unauthorized or missing, which ids answered live, and who has to grant access (the gateway's error usually names the stack owner). Never present unverified slugs as working, even if they are registered in config ahead of an access grant.
5. Edit remote YAML by piping a script over stdin: `ssh <host> 'python3 -' <<'PY' ... PY`. Nested quoted heredocs inside `ssh '...'` break the terminator and can run half the script locally.

## Rotating a gateway key across hosts
Replace the key in every place it lives on each host: `~/.hermes/.env`, inline `api_key` values in `config.yaml` (providers and MCP servers), shell rc exports and shell history. Then grep for the old key prefix to confirm no copies remain, re-read the new value's fingerprint and run a live probe with the new key. Local scrubbing does not revoke anything. Tell the user that real revocation happens on the gateway's side.

- Grep by token-type prefix (for example `tfy_pat_`, `tfy_va_`), not by the old value alone. Keys also hide inside composite variables such as a headers blob (`seatbelt_headers=$'x-tfy-api-key: ...\nx-maat-token: ...'`), and a host can carry a third, older token nobody mentioned. List every hit with its last-8 fingerprint and confirm each matches the new key.
- Parse `$'...'` rc values by decoding the escape (`\n` is a literal backslash-n in the file, not two lines) before comparing.
- Running shells, tmux panes and the agent's own process keep the old env. A 401 "Invalid token" right after rotation usually means a stale in-process value or a missed composite variable, not a bad new key. Test in a fresh shell (`zsh -ic` / `bash -ic`) and tell the user to `source` their rc.
- Do the local host first, verify, then the remote host. Do not start on the remote host when the user is testing locally.

## Giving the user a probe to run
When a live check is faster for the user to run than for you to automate (interactive CLIs, their own shell env), hand them the one-shot commands (`type <alias>`, `<alias> -p "Reply with exactly: OK"`). Do not wrap one-shot `-p` probes in tmux; tmux is only for sessions that must persist.

## Answering "is model X better/cheaper than model Y?"
1. Compare at the effort level the user named (e.g. high vs high). Vendor launch tables often report max or xhigh for their own model; label every figure with its effort level and harness, and say plainly when no matched-effort number exists.
2. Pull prices from the vendor's API pricing page (short-context and long-context rates differ; some vendors charge long-context premiums, others do not), not from aggregator summaries.
3. Check whether the candidate model is actually available on the configured gateway (list its models) before recommending a switch; a model missing from the gateway cannot be trialled in our workflow yet.
4. Anchor the comparison to the model currently configured as default (read config), not a model named earlier in the conversation; a price/quality edge over an old model may vanish against the current one.
5. Change no config while answering a comparison question. Recommend a same-task trial (same T2 coding tasks, same effort) before any switch.
6. Cite sources inline with numbered references.
7. For "which model for tier X", rank by that tier's actual workload (T1: orchestration + docs + ideation, so hallucination rate, instruction-following and long-context recall; T2: terminal/CLI supervision, so Terminal-Bench-style scores), present a compact table, and respect the user's price ceiling (exclude top-tier models they ruled out). Check post-promo pricing dates, not just today's rate. When the user says cost is not a factor, re-rank from scratch: an earlier pick made under a price constraint (e.g. Sonnet over Opus) no longer holds, so say so plainly instead of defending it.
8. Before answering "so we're on X for tier N, right?", grep the tier skill launch lines and every `auxiliary.*` slot on both hosts; list what actually runs where (primary vs fallback-only vs aux) rather than confirming from memory of what was discussed.

## Switching a tier (T1/T2/T3) model
The tier skill holds separate model slots: the T2 supervisor launch line (`hermes chat -s <skill> -m <alias> --tui`) and each T3 `claude_orchestrate` step (design author, design review, implementation, code review: `model_provider=...`, plus `model=...`). "Switch T2 to X" means the supervisor line only; "T3" means the claude_orchestrate steps. Change exactly the slots the user named. Moving the review routes along with the supervisor is over-scoping and gets reverted. Before changing a slot, tell the user what it ran on before.
1. Confirm the alias and the review route answer live first (PONG through `hermes chat -m <alias>` and one real `claude_orchestrate` session), per "Claiming a route works".
2. Edit the tracked copy in the setup repo (`~/hermes-setup/skills/<skill>/SKILL.md`). Grep for every old-model token in the slots being changed (model name, alias, provider name) and update that step's launch params, the header summary, the route-summary line and any rationale text that names the old route. A missed reference makes a future run launch the old route.
3. Troubleshooting notes about a route no longer used stay, labelled legacy; they are still true for that route.
4. Routing rationale follows the user's routing. When the user puts author and reviewer on the same engine (e.g. all seatbelt: Opus for design author and review, Sonnet for implementation and code review), rewrite the cross-engine invariant: reviewer independence then comes from a fresh session with no shared context. Keep the "no silent engine fallback, STOP for approval" rule either way. Mention the cost tradeoff once (reviews on per-token seat pricing vs a cheap reviewer model).
5. Verify with a string-check script over the edited file (each slot's new params present, no stale old-route token outside legacy notes, untouched slots unchanged) before committing.
6. Commit to the setup repo's main, pull on the remote host, then copy the file over every live copy on both hosts. Find live copies with `find ~/.hermes/skills -maxdepth 2 -iname '*<skill>*'`; a host can hold the skill under both a category dir and the top level.
7. Running tier sessions keep the old skill text; only new spawns pick up the change.

## Auxiliary models (vision, title generation, compression)
Auxiliary tasks have their own `auxiliary.<task>.provider/model` slots. `provider: auto` lets Hermes pick a model on whatever gateway is configured, which can silently route a task to a model family the user wants kept off that gateway (e.g. Claude via a metered gateway). When auditing "what runs model family X through gateway Y", list every `auxiliary.*` slot, not just `model.default`, delegation and fallbacks.
1. Pin the slot explicitly: `hermes config set auxiliary.vision.provider <provider>` and `auxiliary.vision.model <group/id>`; when the main default model is multimodal, reusing it for vision is the natural pick (vision traffic is low, so a stronger model costs little).
2. If the model needs a non-default wire on that provider, set it per model (`providers.<p>.models.<id>.api_mode`), never globally.
3. Verify with a real image turn: `hermes chat -q '<question>' --image <file>` (`-q` takes the query string; put `--image` after it), then read that session's `session_model_usage` rows. The aux row (alongside the main and title-generation rows) must show the new model and gateway hostname, and the answer must be correct.
4. During a leak audit, report each finding and let the user mark which ones are intentional before removing anything; an "intentional" route stays as is.

## Attributing gateway spend to a slug
A gateway bill line such as `<group>/<model>` names the server-side route the request resolved to. Group-prefixed ids sent by our configs bill under that group; a bare model id (no prefix) can resolve to the gateway's primary/direct route. To find the source: grep every config, skill, plugin and launcher script on both hosts for the slug and for bare ids of that family (`ANTHROPIC_MODEL=`, `--model`), list `session_model_usage` models per host, and check `~/.hermes/tasks/*/meta.json` `model` values. Use the bill's shape (cached share vs fresh input vs output) to describe the workload, not to name a culprit. If no local source is found, say so plainly and ask the user to check the gateway console's per-slug usage over time (was it active after the last routing change?). A server-side slug cannot be disabled from our side; the controllable fix is making every launcher send prefixed ids, optionally enforced by a hook that rejects bare ids.

## Answering "is this bill expensive vs model Y?"
Decompose the shown cost into cached input, fresh input and output at the gateway's per-token rates until it sums to the bill, then price the same token counts on the comparison model (including its cache rate). Report the ratio for that exact call and name the driver (usually cache reads on long agent sessions). A list-price ratio alone misleads when cache share is high.

## Answering "why did run/commit X use model Y?"
Find out whether Y was **explicitly requested** or **fell in as a default**. Do not guess from the commit label.

1. Launcher default: read the coding-agent launcher (for example `~/.hermes/plugins/claude-orchestrate/__init__.py`) and note whether it pins `--model` or passes it only when the caller sets one. The claude-orchestrate tool's `model_provider` defaults to `seatbelt` when omitted (`truefoundry` is refused for executor=claude); the tier flow gets its author/implementer/reviewer routes because the tier2 skill passes `model_provider` (and `model`) explicitly on every launch, so read the skill's current values rather than assuming a reviewer model. Distinguish "tool default" from "flow default" when asked what a launch uses.
2. CLI default: read `~/.claude/settings.json` `model` (an alias such as `opus` resolves through the CLI's model catalog, not a fixed version). The cached catalog at `~/.claude/cache/model-catalog/published-*.json` maps aliases to ids per provider under `document.surfaces.cc.model_selector_config[0].provider_alias_targets`; a model's presence in the `models` list only means it is selectable.
3. Per-run record: check `~/.hermes/tasks/<task>/meta.json` `model`. A value there means the orchestrator passed it explicitly, so the cause is the dispatching prompt/skill, not a default.
4. Keep Hermes's own `fallback_providers` separate: a model in that list affects Hermes turns, not coding-agent launches.
5. Report the distinction: explicit argument vs default, with `path:line` evidence for each layer checked.

## Answering "why does my session keep switching to model Y mid-prompt?"
A model change that appears mid-turn in the status bar, with no `/model` from the user, is Hermes's `fallback_providers` chain firing after the primary call errored (rate limit, overload, provider error). The bar shows the fallback's model for that turn.
1. Read the chain: `hermes config get fallback_providers` on the host running that session.
2. Confirm from the agent log: grep for `Fallback activated: <from> → <to>` with the session id, and read the error logged just before it. That error, not the fallback, is the real problem.
3. Report which primary call failed and why, and the chain order. Changing or removing a fallback entry is a model-group decision; ask before touching it.

## Using Claude models through the seatbelt gateway as Hermes's own model
"Use Claude via seatbelt in Hermes" means Hermes stays the agent and seatbelt becomes a model provider. It does not mean delegating turns to the Claude Code CLI; offering the CLI route as the answer misreads the ask.
- Seatbelt rejects requests that do not look like Claude Code (429 even with free seats), so an OpenAI-style `/v1/chat/completions` probe failing says nothing about seat availability.
- Hermes's Anthropic adapter (`agent/anthropic_adapter.py`) already produces the Claude Code shape in its `oauth` auth style: the `claude-code-20250219` and `oauth-2025-04-20` betas, a `claude-code/<version>` user-agent, `x-app: cli`, and the Claude Code system prefix block. Use a provider entry with `api_mode: anthropic_messages`; put the gateway credentials and any extra betas in that entry's `extra_headers` (applied last, so they win).
- The `oauth` style is chosen by token shape (`sk-ant-` non-api, `eyJ`, `cc-` prefixes in `agent/anthropic_credentials.py`) and, for the Claude Code identity on the key_cmd path, only for the native host or the `anthropic` provider. Check how the route classifies before assuming the identity is sent; a third-party base URL can fall into plain `api_key` style.
- Register each model with its `claude-teams-group/` prefixed id and a per-model `context_length`, then PONG-probe each through `hermes chat --model ... -q ... -Q` before calling the route working. Confirm from the agent log that the reply came from seatbelt and not from a fallback.
- Find what the gateway requires with a raw Messages-API matrix (vary one element at a time: system block, betas, user-agent, auth header) before changing Hermes config. The Claude Code system prefix block decides it: with it the call answers, without it seatbelt returns `429 anthropic error: Error` whatever the auth header. Headers and betas alone are not enough.
- A seatbelt base URL registered as a custom route or a `model_aliases` entry runs as provider `custom`. `anthropic_route_is_oauth` then classifies it as third-party and leaves out the Claude Code system block. An `llm_request` middleware plugin can prepend that block (it gets the wire kwargs plus `base_url`/`api_mode` as context kwargs; match on both so it never touches other routes).
- **Historical patch diagnostics, not a setup recipe:** an earlier install needed changes to `anthropic_route_is_oauth()`, `_is_third_party_anthropic_endpoint()` and `_maybe_wrap_anthropic()` for the Seatbelt route. Check current upstream source and active provider config first; do not patch installed Hermes just because this note describes an older workaround. If a real regression remains, get approval, test and track the patch.
- Current Seatbelt identifiers use plain `claude-teams-group/<model>` with NO `[1m]` suffix. Resolve the exact allowed ID, provider headers and context limit from current config/gateway rather than copying an example. Keep secrets as `${VAR}` references; verify a fresh `hermes chat` PONG and a tool call both land on the intended Seatbelt route without fallback. Apply only the roles/hosts the user requested.
- Write config programmatically only with a targeted text edit of the block being changed, keeping secrets as `${VAR}` refs. `hermes_cli.config.read_user_config_raw` can return secrets already masked (`***` / `''`) on some installs, and writing that dict back with `atomic_config_write(path, cfg)` saves the mask over the real key; if you do use them, grep the written file for masked values on `api_key`/`x-*` lines before restarting anything. `atomic_config_write` refuses a write that drops existing keys; deliberate removal needs `atomic_config_replace(path, cfg)`.
- Verify "not using raw TrueFoundry": grep `agent.log` for the session's `API call #N: model=claude-teams-group/... provider=seatbelt` lines, confirm `ANTHROPIC_API_KEY` is absent from the TUI process env, and list every `auxiliary.*` slot. A side task (e.g. `background_review` pinned to `truefoundry/claude-group/...`) can keep billing per-token Claude while the main chat is on the seat.

## Switching a live chat from a Gemini/TrueFoundry model to Claude
TrueFoundry appends a `__thought__<base64>` signature to Gemini tool-call ids (175+ chars). Anthropic/Bedrock reject `toolUseId` over 64 chars, so `/model opus` mid-chat fails with `400 ... toolUseId failed to satisfy constraint` (surfaced as "rejected this request as malformed"). Fix in `_sanitize_tool_id()` (`agent/anthropic_message_convert.py`): strip from `__thought__` onward and hash-truncate anything still over 64. Also strip the suffix from existing `messages.tool_call_id`/`tool_calls` rows in `state.db` on each host. A long-running TUI process keeps its in-memory history: `/resume <session>` or restart it before switching again.

## Verifying the main fallback chain (`fallback_providers`)
The chain is a top-level ordered list of `{provider, model}`; the user's standing order is seatbelt Opus (primary `model.*`) -> TrueFoundry Argon -> Fireworks Kimi K3.1 Pro. Drop entries the account cannot reach (a 403 "not authorized to access model" entry just burns a hop before a per-token fallback answers). Prove each tier on the local Mac only:
1. Copy `config.yaml` + `.env` into a `mktemp -d` dir under the scratch dir, `chmod 600`, `trap 'rm -rf "$T"' EXIT`, `mkdir "$T/logs"`.
2. Break tiers by URL in the copy: tier 2 = replace every `https://<model-gateway>` with `https://seatbelt-broken.invalid`; tier 3 = also replace `https://<llm-gateway>.truefoundry.cloud`. Set the memory provider to `''` in the copy (an external provider not installed under the copy's home slows startup).
3. Run `HERMES_HOME="$T" perl -e 'alarm shift; exec @ARGV' 240 hermes chat -q 'Reply with exactly TIERn_OK' </dev/null >"$T/out.txt" 2>&1`. macOS has no `timeout` binary (a `timeout` prefix fails instantly and the run never happens); use the perl alarm. `</dev/null` stops the CLI waiting on stdin.
4. Run it with `terminal(background=true, notify=true)` and the two tiers chained in one command: foreground runs past the tool timeout get interrupted and leave the scratch copy (with keys) behind.
5. Read `$T/logs/agent.log` for `API call failed ... base_url=...broken.invalid`, `Fallback activated: <from> -> <to>` and `API call #1: model=<expected> provider=<expected>`. Two failed attempts per tier, then the hop, is normal.
6. After the run, `ls -d <scratch>/fbprobe.*` and delete any leftover dir, and remove the probe script.

## Frozen session policy (remote-host gateway sessions)
On the canonical gateway, every session stores a policy receipt at start (`state_meta` key `gateway.local_policy.v1:<session_id>`): a full copy of the config (including `fallback_providers`) plus `config_secret_ref`, a `profile-config-v1:` JSON with fingerprints of each route secret. Consequences:
- A config change (new fallback chain, provider, aux slot) never reaches already-open sessions; they keep the chain from their start. Say which open sessions keep the old chain rather than claiming the change is live everywhere.
- If a route secret changes after the session started (including restoring a key that a bad write had masked), the next turn fails with `launch_credentials_unavailable (providers.<p>.<field>: changed in config.yaml since this session started)`. Normal fix: `/new`.
- When the user needs that exact chat back: back up the receipt row first, recompute the fingerprint with `agent.credential_persistence.fingerprint_secret_value` over the current value (`json.dumps(value, sort_keys=True)` for dict values, `${VAR}` expanded from `.env`), write only the matching `entries` item, optionally replace `fallback_providers` inside the receipt's `config_json`, validate with `gateway.session_policy.restore_policy(receipt['policy'])`, then restart the gateway. The restart is required: the gateway caches the old policy in memory and the next turn otherwise fails `storage_unavailable` (in-memory policy != disk). Before restarting, confirm no running kanban tasks, tmux tier sessions, `hermes`/`claude` workers or in-flight turns.

## Auxiliary fallback per task
`auxiliary.<task>.fallback_chain` is a list of `{provider, model}` tried when the pinned provider fails. It fires on capacity errors (402/quota, 429 after retries, connection failure, timeout), and on auth errors only when a chain is set; a malformed-request 400 never falls over. Example: `background_review: {provider: seatbelt, model: claude-teams-group/claude-opus-5-5, fallback_chain: [{provider: truefoundry, model: gemini-group/gemini-4-argon}]}`. Verify with a direct `agent.auxiliary_client.call_llm(task="background_review", ...)` call using the Hermes venv interpreter that has the deps (on the remote host, the gateway process's interpreter + its install-env site-packages); otherwise confirm from the next real `bg-review` log line.
- When the user OKs a revertible experiment, list every config key the trial wrote and either revert them at the end or report them as residual. Leaving none behind is required.
- The GPT side (`codex-seat-traffic/*` slugs on the gateway's `/v1/chat/completions`, registered as a `seatbelt-codex` provider) is not a confirmed Hermes route either: a full Hermes run got 401 "Could not parse your authentication token" and fell back, and raw probes got a 403 HTML edge page for every header/UA shape. If asked "can Hermes run through seatbelt at all", re-probe live with attribution before answering; never claim it works from an earlier raw probe.

## Claiming a route works
Never tell the user a provider/route "already works" from memory of an earlier session's probe. Gateways change access and raw-HTTP success does not prove Hermes's own client gets through. Run a fresh `hermes chat --provider <p> --model <m> -q 'Reply exactly PONG' -Q`, then grep `~/.hermes/logs/agent.log` for that session id: a 401/403, `marking <provider> exhausted` or `Fallback activated` means the PONG came from the fallback chain. The `sessions` row in `state.db` also records the fallback's model/provider when that happens.

## Debugging which wire/provider a custom route really uses
- `HERMES_DUMP_REQUESTS=1 hermes chat ... -q ... -Q` writes one `~/.hermes/sessions/request_dump_<session>_*.json` per HTTP call. Read every dump for the session: the first is the primary, later ones may be fallbacks. The `url` (`/messages` vs `/chat/completions`) settles the wire question faster than reading resolver code.
- `model_aliases` dict entries resolve through the direct-alias path, which carries no `api_mode`/`transport`; the host-mandated mode wins and an OpenAI-compatible gateway lands on `/chat/completions`. To force a wire, use a named `providers.<name>` entry with `api_mode` and select it by name.
- A provider entry named after a built-in (`anthropic`, `openai`, `nous`) is shadowed by the built-in when selected by its raw name. Select it as `--provider custom:<name>` to hit the saved entry.
- Check resolution offline before a live run: `~/.hermes/hermes-agent/venv/bin/python -c` with `from hermes_cli.runtime_provider import resolve_runtime_provider; resolve_runtime_provider(requested='custom:<name>', target_model='<id>')` prints provider, `api_mode`, `base_url` and headers (redact secrets before printing).

## Where to run checks
Run API, config and gateway probes on the local Mac first. Use the remote host only when the question is about that host's config, network path or run records. Defaulting to the remote host for everything wastes time and draws a correction.

## Answering "is model X slower on our connection?"
Separate transport latency from model latency; do not answer from benchmarks alone.

1. From the host that actually runs Hermes, time an unauthenticated endpoint request with `curl -w` (`dns`, `connect`, `tls`, `first_byte`, `total`). A 401 is fine; it measures the network path.
2. Run the same tiny streaming prompt on both routes in parallel with the configured transport (`/responses` or `/chat/completions`), reading keys from `~/.hermes/.env` without printing them. Record HTTP status, first-byte time, total time and whether the parsed stream contains the expected text.
3. Use published provider benchmarks only for model behavior at scale: time to first token, output tokens per second, total tokens per task and effort setting. Compare matching effort levels.
4. Explain the tradeoff plainly: a model can have slow first output and still finish faster when it generates faster or uses fewer tokens.
5. Do not attribute a multi-minute stall to the network when small probes are fast. Inspect that turn's request timing and gateway errors before changing models or timeouts.
