# Infrastructure and process-lifecycle staged rollout

Use when a change moves a production workload to a new host/region/runtime, changes process ownership or deployment topology, or replaces a core dependency. If the user says to keep the old system live until the replacement is proved, a green PR and code review are **not** cutover authorization. Keep the old path operational; stage from the branch; deliver a documented go/no-go with residual risks; obtain separate approval for merge/cutover and old-system retirement.

## Stage and prove the actual path

1. Verify the target region/account/AMI, IAM resource names, DNS zone and permissions with current APIs before provisioning or claiming a blocker. Move credentials only through approved least-privilege secret-manager paths; no plaintext `.env`/service-account copy into a shared temp directory, command argument, log or chat. Compare target-specific configuration without exposing values.
2. Make the migration additive when the agreed plan requires parallel operation: preserve the old deploy job/default and production behavior, put the new target behind an explicit opt-in selector/flag, and compare the flag-off behavior to base. Scope removal/retirement separately, ideally in a clearly marked draft cutover PR. A long-lived PR must periodically incorporate base changes and recheck additivity; for merge conflicts retain both new base logic and the migration guard, then test. Never assume a sibling's conflict resolution remains correct after newer base changes.
3. Deploy the actual target host/service and endpoint from the branch. Run on-host tests, a real workflow with representative inputs, public-path smoke, storage write→readback and latency/outcome capture for the risk being addressed. A healthz response is only process health. Mine durable usage records as well as recent process logs for old-versus-new parity; compare route/contract sets structurally rather than relying on a count or a recollection.
4. If the public endpoint is auth-fronted, backend-only tests are insufficient. Verify an unauthenticated redirect and cookie/CSRF properties, TLS termination, public hostname, redirect URI and cookie domain; then test an authorized end-to-end login through the real domain. A 401/403 alone does **not** prove the login works. Do not weaken secure cookies or bypass the identity provider silently. A deliberately invalid OAuth code can help test CSRF state handling but cannot prove the real identity exchange succeeds.
5. For process-lifecycle changes, run actual owner/coordinator/worker processes. Restart the coordinator mid-work, assert the same worker survives and completes, verify reattachment without duplicate/gap events, and check live-lock protection and dead-lock recovery. Test auto/scheduled trigger paths separately when they use different spawn/environment wiring. When exhaustive testing is explicitly requested, add concurrent workers, repeated restarts, hard-kill, reconnect, long runs, failure injection, real external dependency, and soak/leak checks. Reuse one harness, report which scenarios ran and which remain faked.
6. Audit deploy **ordering**: do not remove the working service before the replacement is healthy. Guard secondary startup/publish failures so they cannot take down the primary service; run a safe dry run and observe a permitted real deployment through *every* post-swap stage to a final exit. A successful health gate is not proof of the final publish or permission step. Have a fresh reviewer independently inspect the exact diff, real e2e assertions, lock/reconnect/error paths and residual risk; do not rely solely on the implementation owner's summary.

## Platform checks on the new host

- For Windows scripts, validate encoding for the installed PowerShell version (Windows PowerShell 5.1 differs from PowerShell 7; non-ASCII need not be banned), parse the `.ps1`, and transmit multi-layer SSM content as a file or safely encoded payload rather than hand-interpolating `\`, `$`, quotes and backticks through JSON/shell/PowerShell. Verify the file actually written and service end state. Check AWS CLI and SSM Agent separately; their installations are unrelated.
- For an unreachable Windows service or HTTP-01 TLS challenge, inspect both cloud security-group rules **and** the OS firewall/host listener; do not declare the OS firewall guilty without testing. Check target host's service-account permissions, installed CLI visibility in the *service* PATH, and actual TLS termination. On long SSM polls, verify the poller's credential validity before treating empty output as a build failure.
- On a newly deployed host, ambient env/mount state can expose tests that leaked variables or assumed a developer shell. Reproduce on host, isolate test environment, and verify the actual service-launched path. A synced/copied file's preserved mtime may not mark when local sync completed; use a sync watermark or explicit local timestamp if staleness semantics require it. Do not infer authoring/ownership from a path or process name alone.

## Decisions and verification

Resolve a user's flag instruction to the *literal current code semantics* (`on = ...`, `off = ...`) before asking another worker to flip it. If a `clarify` call fails to deliver, retry once, record a durable question and hold only the decision-dependent work. Let the owning worker investigate and fix within its worktree, but independently read back the final target state and challenge self-reported success. Verify actual branch-to-worktree mapping (`git worktree list`) and diff before believing a surprising 'zero changes' plugin gate; do not override a failed gate without recording why its path was wrong. After explicit approval, verify merge, running revision, public flow, and old-system state before declaring cutover done.
