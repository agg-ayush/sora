# Evaluate agent tools against the actual workflow

Test a tool on an isolated **representative workflow**, not merely its README or `--help`. Verify import/export, worker ownership, state/claim compatibility, recovery semantics, UI visibility and exit behavior. An alternate dashboard that only displays workers it spawned cannot be assumed to observe externally spawned tmux sessions; using two independent lifecycle managers risks conflicting writes and cleanup. Treat older beads/amux verdicts as historical decisions under their then-current versions and architecture, not current product facts: retrieve live docs and exercise the current releases before recommending adoption or rejection.

Separate **task-tracking completeness** from **judgment quality**. A graph row per check proves that a check was recorded, not that the LLM reasoned about it independently. For multi-check judge prompts, validate returned check keys against the expected set; use targeted retries for missing/ambiguous judgments, structured per-check evidence within a call, and a stable `(check_id, item_id, evidence_hash)` fingerprint to measure score flips. Consider selective repeated judgment for unstable checks when rate limits permit. Do not cite existing repo code as a proven precedent merely because it exists; inspect its behavior with a fixture first.

Record evaluated tool/version, commands, observed artifacts, known gaps and a reversible rollout decision. When a native feature seems to duplicate an external tool, prove its behavior on a scratch board/worktree rather than inferring equivalence from names. Never install a watchdog, publish an integration or change an existing dispatcher merely to explore a tool without scope and authorization.
