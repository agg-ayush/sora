# Adobe Acrobat Sign REST v6 integration

For feasibility research, PoCs and builds that create agreements, attach per-signer context, track signing and pull signed artifacts back.

## Procedure

1. **Ground in the live spec, not SDK samples.** Fetch `https://secure.na1.adobesign.com/restapijson/v6/restapi.json` and read the schemas you touch (`AgreementCreationInfo`, participant sets, `MergefieldInfo`). Adobe's guides disagree with each other on OAuth paths (`/oauth/v2/token` vs `/oauth/token`), first retry delay and `CANCELLED` vs `ABORTED`; the live spec and a live tenant settle these, never a guess.
2. **Check the gates first, they kill the product before any code does:**
   - API access needs an **Enterprise or Developer-tier** account. Ask the tenant owner early.
   - Private messages must be enabled by the admin (`PRIVATE_MESSAGES_NOT_ENABLED` 403 otherwise).
   - Sender identity: legal-admin `:self` OAuth grant is the simplest; account-admin consent plus `x-api-user: email:<user>` acts as another user. Test what recipients and the audit log actually show.
   - Do not base an unattended service on the JWT technical-account recipe; JWT service credentials are end-of-life. Confirm the current S2S path with Adobe.
3. **PoC on the free Acrobat Sign Developer Edition** (test-labeled agreements) while entitlement is being confirmed. It validates the flow, not the tenant gates. Account sign-up is a human browser step; ask the user for it, give exact numbered browser steps, and expect the provisioning email to take ~30 minutes (check spam).
   - A missing provisioning email does not mean no account: have the user log into Acrobat Sign directly before re-submitting the form.
   - **Credentials come from inside Acrobat Sign, not the Adobe Developer Console.** Direct the user to the Acrobat Sign web app: Account (admin-only menu) -> Acrobat Sign API -> API Applications for an OAuth client ID/secret, or Personal Preferences -> Access Tokens for an integration key. The Developer Console lists an "Acrobat Sign API" but enabling it there fails with "License required" unless the console org itself holds an enterprise Sign license, so don't send the user there.
   - If the Account menu is absent, the user is not an account admin on that Sign account; ask exactly what their profile menu shows before guessing at paths.
   - Give the user one short next step at a time during account setup, not every possible menu path at once.
3a. **Prep while the account provisions, so the first credentialed session runs end to end:**
   - **Webhook listener first**, because registration does a live HTTPS GET handshake before any event arrives. A single stdlib Python file is enough: answer 2xx on GET and POST, echo `X-ADOBESIGN-CLIENTID` in the response header (and a `{"xAdobeSignClientId": ...}` body), write the 2xx before any parsing or disk I/O, append each POST to a JSONL log with `received_at`, dedupe on `webhookNotificationId` rebuilding seen-ids from the log at startup, and expose `GET /status` (counts, last event time). Verify locally with curl: handshake echo, one POST logs one line, a repeat POST is marked duplicate, restart keeps dedupe.
   - **Public HTTPS without exposing the box:** run `cloudflared tunnel --url http://localhost:<port>` in the background tee'd to a log, grep the `https://*.trycloudflare.com` URL from it, and curl the handshake through the tunnel before calling it ready. Quick-tunnel URLs change on restart: re-register the webhook with the current URL whenever the tunnel is relaunched, and tell the user.
   - **Test contract with real named AcroForm fields** (counterparty/customer name, date, signature text), generated with reportlab in a throwaway `uv venv`, so field detection and `mergeFieldInfo` prefill hit real field names. Confirm the field names by reading the PDF back (pypdf `get_fields()`).
   - If Python packages fail to import despite pip reporting them installed, check for a stray `PYTHONPATH` pointing into another venv and run with `env -u PYTHONPATH`.
3b. **Contract before code.** Before writing any API-call code, define the exact contract the product will use (endpoints, request/response shapes, auth flow, webhook payloads, error cases) from the live spec plus public repos for usage the docs omit, as a versioned file in the product repo on a branch. When down-converting Adobe's live OpenAPI 3.1 to 3.0, normalize its nonstandard schema `type` values (`date`, `double`, `long`, `int`, `file`) to standard type/format pairs, and validate every `$ref`. Build against mocked calls that honor the contract while credentials are pending, and UI refinement can run in parallel. When coding starts, install a code-graph tool in that repo so each contract element traces to the functions that implement it and contract changes show their blast radius. Ask the user where the contract lives and the research scope before dispatching.
4. **Minimal PoC flow:** CUSTOMER API Application (admin creates, redirect URI, scopes `agreement_write`, `agreement_send`, `agreement_read`, `webhook_write`, optionally `webhook_read`) -> auth-code grant, store refresh token (access ~1h, refresh dies after 60 days idle) and the returned `api_access_point` -> `POST /transientDocuments` (one file per multipart call, ID valid 7 days) -> `POST /agreements` in `AUTHORING` with per-set `privateMessage` and `mergeFieldInfo` -> inspect fields -> `PUT /agreements/{id}/state` `IN_PROCESS` -> resource-level webhook -> on completion confirm `status == SIGNED`, then download `combinedDocument` and `auditTrail`. **Scope discrepancy:** live v6 operation security requires `agreement_write` for creation and state/merge PUT, while the OAuth quickstart also teaches `agreement_send`; request both in a PoC and verify tenant permissions. The webhook create operation declares HTTP 200 in live v6 even though a guide says 201; accept successful 2xx and capture its returned ID.

5. **First live run: stop before dispatch.** Run the live flow with the send/dispatch step behind a kill-switch env flag (off) so the first contact exercises auth, upload, create, privateMessage and prefill without emailing anyone. When a step fails, probe the same agreement directly with the raw endpoint (GET formFields vs GET mergeInfo, agreement status) to separate a tenant/doc divergence from a code bug; leave the unsent agreement in place for the fixer to probe. A doc-vs-tenant divergence is a source fix: file it as a task with the evidence, don't patch the flow inline.
5a. **Waiting on the signer:** run the live flow as a background process with completion notification and end the turn; never sit in foreground sleep loops polling the event log. Tell the user what (if anything) they should see on their side, since the visible outputs land on the box, not in their inbox.
6. **Credential packets:** unpack into a dedicated 0600 dir under `~/.hermes/secrets/<project>/`, source the env file with `set -a; . file; set +a` per command, never print values, never copy into the repo. Before a live run, curl the listener's `/status` through the current tunnel URL and rewrite the webhook URL env line if the tunnel restarted.

## Auth and scopes for a short-lived prototype on someone else's account

- **Client ID + secret identify the app; they do not authorize it.** A token tied to an account user is still needed, via OAuth consent (long-running service, refresh token) or a token generated in the Sign UI (Personal Preferences -> Access Tokens). Explain this distinction before asking anyone for anything.
- **For a temporary prototype on a borrowed account, ask only for a scoped access token.** Never ask for the account login; the owner knows how to generate the token, so name the token and the scopes and nothing else. OAuth is for the permanent service-user setup.
- **Scope set for the full PoC loop:** `agreement_read`, `agreement_write`, `agreement_send` (the live spec and quickstart disagree on whether write covers sending, so request both), `webhook_read`, `webhook_write`. Verify scope claims against the contract notes before stating a set as complete.
- **Private messages need no extra scope** and can go to recipients outside the account; the only gate is the account-level toggle, which the first live send answers.
- **Read scope already reaches the account's other agreements** (the token acts as that user and can list them), so a webhook adds no capability, only push vs pull. Don't argue webhooks are a confidentiality risk on that basis. Use a RESOURCE-scope webhook on your own test agreement and delete it when the run ends.
- **Test with the user's own email as the signer**, and tell the account owner one line up front that a test agreement will appear in their sent list.
- **Messages to the account owner/admin stay short:** the yes plus the one concrete ask (token + scope list). No ground-rules paragraph (professionalism is assumed), no echoing back what they just sent, no meeting references in group threads with people who weren't there. Ask the question to the person who can answer it (the account admin), not the intermediary.

## Service user identity (permanent setup on the org's account)

- The account admin creates the service user and needs an email for it. It must **receive mail** (Adobe sends an activation email someone has to click). A Google Cloud/GCP "service account" address cannot receive mail, so it dead-ends the setup; don't pick it from an IT catalog.
- Use a **Google Group** (e.g. `<product>@<org>.com`) with external senders allowed, since a group locked to internal posting silently drops adobesign.com mail. Owners: the builder plus the long-term owner from day one, so no handoff step is needed later. Members: whoever should get Adobe's notifications (add operators at go-live). A plus-alias on the builder's mailbox is the zero-provisioning fallback.
- Set the account's display name deliberately; it is the sender name counterparties see in signing emails.
- **The message handing the email to the admin carries only the address and display name.** Never explain that it is a Google group, that external delivery is on or where mail lands; the admin acts the same either way. Confirm group delivery yourself before sending.
- **Scope level (`:self` vs `:account`) follows from who sends.** If every agreement originates from the service user, `:self` already reads, tracks and downloads all of them; `:account` only matters while people still send by hand from their own Adobe logins. Ask the user whether the dashboard must show every agreement in the account; if yes, `:account` is a requirement and needs an admin consent on the app. Either way, build and test on `:self` meanwhile rather than blocking.
- When the user asks why OAuth is needed if they already have a client ID and secret, give the one-line answer (the pair identifies the app; consent ties it to a user and yields a self-renewing refresh token) and move on.

## Rules that bite

- `participantSetsInfo` (not `recipientSetsInfo`). Different `order` values route sequentially, the same order runs in parallel.
- `privateMessage` lives on the **participant set**; every member of a set gets the same text. Use singleton sets for per-signer messages. The agreement-level `message` is not private. No published max length: test it.
- Two `fileInfos` are merged into one signing packet, not delivered as a separate attachment. `urlFileInfo` needs a publicly reachable URL, so use transient uploads for confidential contracts. 10 MB per file; 500-page Enterprise packet cap.
- **Upload limits: Adobe accepts 10 MB per file, but a serverless upload route caps far lower** (Vercel function bodies ~4.5 MB). Never let the hosting cap become the product limit: upload browser files straight to storage with a signed upload URL, then pass them to `transientDocuments`, and name Adobe's 10 MB limit in the over-size message. Before choosing or defending a limit, query the real file-size distribution in the source system (median, p99, count over each threshold) and show it.
- **Agreement notes exist: `PUT /agreements/{id}/me/note` with body `{"note": "..."}`, read back with `GET .../me/note`.** A body keyed `value` returns 204 and silently saves nothing, so always read the note back after writing. The note belongs to the acting Adobe user (`x-api-user`/token owner), is visible to whoever logs in as that user, and is never emailed to signers.
- **Nothing on a sent agreement's content or form values can be changed.** Set message, files and prefill at creation or in `AUTHORING`. A product that augments sends made by hand in the Adobe UI cannot add a private message or prefill afterward; sends must originate through the API.
- Webhooks: registration is an HTTPS GET; every GET and POST must answer 2xx and echo `X-ADOBESIGN-CLIENTID`. No HMAC body signature in the standard guide. 15 retries over 72h, then the webhook is disabled and later events are lost; duplicates occur. Dedupe on `webhookNotificationId`, prefer RESOURCE-scope webhooks and back them with low-frequency status polling.
- `combinedDocument` succeeds before signing, so gate artifact download on `SIGNED`. The audit endpoint is `/auditTrail`, not `/auditReport`. Attaching the audit report to a digitally signed doc can yield a PDF Portfolio.
- **Binary endpoints (`combinedDocument`, `auditTrail`) return a bare 406 with an HTML body when the request sends `Accept: application/json`.** Send `Accept: application/pdf` (or no Accept) on those calls; a shared JSON transport that sets Accept globally breaks only the final download step, after the signer already signed.
- **A webhook listener that echoes `X-ADOBESIGN-CLIENTID` only on the GET handshake looks healthy but is not.** Adobe treats a POST response without the echo as unacknowledged and redelivers the same `webhookNotificationId` at 1m/2m/4m/8m backoff, so later events (WORKFLOW_COMPLETED) queue behind the retry storm. Symptom: the same notification ID repeating at doubling intervals. Verify the POST response header through the tunnel with curl, not just the GET.
- **Self-scoped tokens cannot `DELETE /webhooks/{id}` (403 PERMISSION_DENIED); `PUT /webhooks/{id}/state {"state":"INACTIVE"}` works.** Clean up leftover test drafts with `PUT /agreements/{id}/state` `CANCELLED` plus `agreementStateInfo`. Do both at the end of every live run on a borrowed account.
- **Self-scoped tokens cannot remove agreements either:** `DELETE /agreements/{id}` returns 404 NOT_FOUND while `GET` on the same ID still returns 200, so the 404 means "not permitted", not "gone". Removing signed/cancelled test agreements needs an account admin. Always probe a cleanup call yourself (refresh the ~1h access token first; a 401 INVALID_ACCESS_TOKEN is expiry, not scope) before asking the owner to clean up, and only ask for what you verified you can't do.
- **Definition of a proven loop:** a clean scripted re-run on current main (pull, reinstall, re-verify listener and tunnel first) that exits 0 with every step DONE, both completion events received once each, status `SIGNED`, and both artifacts saved with byte counts and sha256. Report exactly those facts. Then offer the borrowed account's owner a one-line heads-up on the test agreements left behind and the webhook state, which is also the moment to ask for the promised token rotation.
- **When the scripted run fails after the real-world event already happened (signer signed), probe the failing endpoint by hand, recover the artifacts manually, then file the code fix as a task.** Don't call the milestone done on the manual recovery; a clean scripted re-run is the proof.
- **Consent page error "client configuration is invalid: invalid_request" (before login) is the auth server rejecting the client's saved config.** Diagnose against the app's actual config, not by regenerating link variants: first get the exact redirect URI the admin saved (scheme included) and match it character for character. An `http://` vs `https://` mismatch alone produces this error, and Configure OAuth forces `https://`, so an admin-configured app almost certainly saved `https://localhost:...`. Only after the redirect matches, check the remaining causes in `references/oauth-setup-pitfalls.md`. Say which `client_id` each link uses when you hand it over.
- **Consent error "client configuration is invalid: unauthorized_client" on a freshly created API app usually means the app was never activated/configured for OAuth** (Configure OAuth for Application not saved, or app inactive). Ask the creator to activate it and save the OAuth config, then mint a fresh link; don't change scopes or redirect first.
- **Keep every `state` you mint until its code is exchanged.** Users often paste the callback from an earlier link than the latest; accept the code if its `state` matches any unused state you minted for that app, and say which link it came from.
- **`error=access_denied` "Only account admins can approve account scopes" on the callback means the app is valid and registered** and the flow reached the scope check. Retry the same app with `:self`; `:account` needs an account admin to run the consent once (or the service user made admin). If the error persists after the admin says they "changed the user's scope/permissions", the service user still lacks the account-admin role: ask for exactly that role, not a vague permission change. Offer the admin both options in one message: (1) grant the service user the role and we consent ourselves, or (2) the admin runs the consent once. For (2), an admin-consented account token plus the `x-api-user: email:<service user>` header makes calls act as the service user, keeping actions off the admin's name; verify what the audit trail shows on the first live call before relying on it. Without that header, every automated action lands under the admin's name.
- **Shape of the message to the admin (user's preferred style):** open with the exact error string as fact ("OAuth consent still fails with the error "...""), no warm-up line; then "These are the possible options:" as a flat numbered list with "Recommended" marked inline on the pick; name the real requirement plainly (if the minimum is admin, say admin, don't soften it to "minimum rights"). Phrase benefits from the recipient's side ("any calls will be recorded under the service user only"), not as the builder's worry. Omit history the recipient lived through (the earlier `:self` step, what they already changed) and internal lingo; a header name like `x-api-user` is fine when the option depends on it.
- **Before minting or forwarding any consent link, check whether that consent already happened.** Look in the secrets dir for the saved `state` and token files and which env uses them; if the deployed token came from an earlier admin run, say so and stop. Re-asking an admin for a consent they already gave is a correction the user makes immediately.
- **Admin-run consent handover:** an `:account` link only works for an account admin, so unless the user is confirmed admin, hand them a ready-to-forward message for the admin (what it is, same permissions as last time, click Allow, send back the full localhost URL, the link) instead of asking them to click it first. Mint the `:account` link (fresh `state` saved to the secrets dir) for the admin's app, verify client_id, redirect (scheme included), scope set and shard before handing it over, and tell the admin to log in as themselves, click Allow, and send back the full address-bar URL from the dead localhost page. Check `state` matches before exchanging the code.
- **Prove account scope with an account-gated endpoint, not a list call.** On a fresh account `GET /agreements` returns 0 for both `:self` and `:account`, so it proves nothing. `GET /webhooks` returns 200 only for an account-scoped token (self tokens get PERMISSION_DENIED). Pair it with `x-api-user: email:<service user>` returning 200 and an invalid email returning 401 INVALID_USER, which shows the header is enforced rather than ignored. All three are read-only.
- **The app's configured scope level is a ceiling, not a token property.** A `:self` consent on an app configured for `:account` yields a self token and leaves the app's account capability intact; a later admin consent on the same app yields the account token. No code change, just swap the stored token.
- **When two credential paths both exist, keep one verified working at all times.** Exchange the code, store the tokens 0600, make one live `GET /agreements` call with them, and only then delete the other app. Prefer the admin-created app as the long-term one: it is admin-owned and upgradeable to account scope.
- **Verify account-model claims (who sees which apps, what a user vs admin can configure) against Adobe docs before asserting them** in an explanation or a message to the admin; a confident wrong model sends the admin a wrong ask.
- **Once the user dismisses a theory or names the screen they are on, drop the theory.** Answer whether that screen is the right one directly; re-raising a ruled-out path (e.g. the Developer Console after the user said to forget it) costs a correction round every time.
- **Agreement name is immutable once the agreement exists** (`PUT /agreements/{id}` rejects a name change in both `AUTHORING` and `OUT_FOR_SIGNATURE`). Any rename UI must act before creation and show the control disabled afterwards, explaining that Adobe Sign (not the product) blocks it; use `aria-disabled` so the explanation stays reachable on hover, focus and tap.
- **An `AUTHORING` draft opens for editing only for the Adobe user who created it (`senderEmail`).** `autoLoginUser: true` on the authoring URL removes that gate, but lets any dashboard user enter Adobe Sign as the service account. Recommend individual Adobe accounts in the same tenant instead, and confirm which tenant/account the operators actually use before proposing a sharing model.
- **Same-tenant accounts are reachable with the existing account-scoped token** via `x-api-user: email:<that user>`; test it live before asking for a new grant, which also answers whether their existing agreements can be linked.
- **For account-wide agreement forensics, do not stop at one sender's fully paginated `GET /agreements`.** `POST /search` with scope `AGREEMENT_ASSETS`, `agreementAssetsCriteria.visibility: SHOW_ALL`, and `x-ownership-scope: SHARED_AND_OWNED` can expose agreements shared with the token user that neither the sender's default owned search nor their list shows. A search hit's `userId` is the acting identity for that result; prefer a row with role `SENDER`, then retry a 404 agreement GET using `x-api-user: userid:<userId>`, read `senderEmail`, and fully paginate that sender's own agreements. A CC hit may report the CC user's id instead, so verify detail ownership rather than assuming every returned `userId` is the sender. If `GET /users` is 403 without `user_read`, negatives remain limited to discovered/accessible users, never the whole account.
- **Link to the exact agreement, never the generic Sign home.** `POST /agreements/{id}/views` with `{"name":"ALL"}` returns per-agreement `MANAGE` (`.../account/agreements?aid=...`), `DOCUMENT`, `MODIFY` and `POST_CREATE` URLs. Mint the MANAGE URL server-side on click (a redirect route) rather than storing it or hand-building `public/agreements/view/{id}`; fall back to the generic Manage page with a short note when the agreement is not visible.
- **Matching agreements to tickets by `#<id>` in the name must survive real data:** the number appears at the start, the end or after a prefix (`URGENT ...: #1383 - ...`), as the short intake id (`#1481`) OR the full ticket number (`#111481`), and often glued to the next word with no space (`#111481GFI USA...`), so match both forms and don't require a word boundary before a following letter. One ticket often has several agreements including CANCELLED duplicates. Cancelled agreements may link for history but must never drive status, attention or "waiting on" while a non-cancelled one exists. Scan the real account read-only to collect these patterns as test cases before trusting the matcher.
- **Scans and auto-match must page to the end.** Follow `page.nextCursor` until it is absent (or run incremental by modified-since plus a periodic full pass); a hard cap (e.g. stopping at a few thousand of tens of thousands) silently misses matches and makes "not found" claims false. Report the total scanned with any negative result.
- **Only ticket-number matches may auto-link.** Matches by counterparty or document name alone are strong guesses, not facts: surface them as ranked suggestions for an admin to confirm, never insert them as links (also in manual backfills).
- **The token sees only what its acting identity (`x-api-user`) can see.** Agreements sent from personal accounts in the tenant are invisible to the service sender's token even with account scope on the app; find them via `POST /search` per discovered sender, and make the product render a linked-but-unreadable agreement as "not visible to <product>'s Adobe account", not an error. Getting them tracked means the sender shares them with the service account, an ask for the business owner.
- **Status precedence on multi-agreement tickets: rank by Adobe `lastEventDate`, not `createdDate`.** An abandoned `AUTHORING` draft created after a since-signed agreement wins a newest-by-created rule and shows a signed ticket as "Draft". A draft with no activity since creation never outranks a later-active SIGNED or OUT_FOR_SIGNATURE agreement.
- **Manually backfilling ticket-agreement links on prod (only after the user OKs it):** first confirm the prod code path only reads with links (no writes to Adobe or the ticket system, so no emails or notes fire); build candidates from the read-only scan, keep only ticket-number matches, drop CANCELLED and AUTHORING, dedupe on agreement id; GET each agreement with the prod token and abort on any non-200; insert with a distinct `source` (e.g. `import`) and `on conflict do nothing` so the batch is identifiable and reversible; force a board refresh and read the snapshot back (fetched/failed counts and each linked ticket's status). For any ticket whose shown status disagrees with its agreements, inspect `createdDate`/`lastEventDate`/status per agreement, unlink the abandoned one, and card the precedence fix. Tell the user which tickets newly surface in Needs Attention, since correct-but-new flags look like regressions to operators.
- **"Can prod see X" has two answers: API access and what the UI shows.** A dashboard typically shows only agreements linked to a ticket, so access without links displays nothing; answer both and say what creates the links.
- Identical GET polling is capped around three calls per minute; honor `429` `Retry-After`.
- Treat every claim from docs alone as unverified until a live send confirms it (sender display, message rendering, field conversion, webhook delivery, seal/certification).

## Swapping or retiring credentials on a deployed service

- **A dropped credential is dropped everywhere, verified.** When the user retires a token, replace it in every store (local `tokens.json`-style files, deployment env vars for every target) and confirm the RUNNING deployment uses the new one (redeploy, then a live call such as the board refresh). Keeping it as a fallback anywhere is disobeying the instruction.
- **Check an env var's targets before changing it.** On Vercel one entry often covers production, preview and development together, so a "staging" PATCH silently rewrites prod. Read `target` first; split into per-target entries (PATCH the shared one to the non-prod targets, POST a production-only entry) when environments need different identities. Changing anything prod-scoped needs explicit approval.
- **Redeploy without new code via the API** when the CLI rejects the token: `POST /v13/deployments?forceNew=1&teamId=<team>` with `{"name": <project>, "deploymentId": <current prod uid>, "target": "production"}`, poll `GET /v13/deployments/{id}` until `READY`, then confirm `GET /v9/projects/{prj}` `targets.production.id` equals the new id.
- **A credential set is app + token + acting identity, and retiring one means all three.** A refresh token is bound to the OAuth app (client id/secret) it was minted under, so swapping only the token while the old client id/secret stay in env still runs on the old app. For every environment, state which app, which token and which `x-api-user` identity it uses before claiming a switch is done; a token on a borrowed/prototype app breaks when that app's secret rotates.
- **Prove a retirement with an exhaustive needle audit, run by a background subagent.** Write the old and new identifiers (client id, secret, app name, old account email fragment) to 0600 needle files under `~/.hermes/secrets/<project>/` and have the subagent match with `grep -rIl -F -f <file>` (paths only, never values) across: all files under home incl. worktrees, scratch and `vercel pull` artifacts; git history (count only); cached access-token files; `ps eww` process envs; every project in the Vercel team with decrypted env values (`GET /v1/projects/{id}/env/{envId}`); deployment `createdAt` after the switch (env is baked at deploy time); GitHub Actions secret names and workflow refs; text/jsonb DB columns. It fixes local leftovers itself and only reports remote ones. Delete the needle files once the audit returns, since they hold the old secret.
- **A literal audit cannot prove which app minted a refresh token** (they are opaque). A token that was minted before the switch can keep refreshing for now and still be tied to the old app. Re-consent through the new app for every environment (prod by the account admin, staging by whoever owns the staging sender login), swap the token in and run a live call. Only then deactivate the old app.
- **Isolate staging by Adobe identity, and verify the refusal.** Staging uses a separate sender account that sees only its own (loudly labelled test) agreements; confirm with a live call that the staging token is refused on the production account's `x-api-user` before asserting isolation. The clean end-state is a separate API app created inside the staging sender's own account (CUSTOMER domain, `:self` scopes), so staging has its own client id/secret and cannot be granted account reach on prod's tenant. Have the user save the id/secret to a 0600 env file under the secrets dir, then send a `:self` consent link for the staging sender login.
- **Cutover order when moving an environment to a new app (keeps one path working throughout):** (1) exchange the code with the NEW app's id/secret and save tokens 0600; (2) live-verify with the new token: its own agreements list, a refresh-token grant returns 200, and the other environment's `x-api-user` is refused (403); (3) split/repoint the deployment env vars for that target only and read back decrypted values per target, labelling each as which app/token; (4) redeploy (rerun the deploy workflow) and confirm the deployment `createdAt` is after the env change; (5) run the live refresh endpoint and read the snapshot back (mode, fetched, failed); (6) only then revoke the old token with `POST /oauth/v2/revoke` (`token=<refresh token>`), confirm a refresh with it now returns 401, re-run the live refresh, and update/delete the local token files so no stale copy remains.
- **Scopes for any new or re-consented app: least privilege derived from the code, never "everything except X".** Grep the API client for the endpoints it actually calls (`git grep` on `/agreements`, `/transientDocuments`, `/webhooks`, `/users`, `/libraryDocuments`, sub-paths like `/views`, `/events`, `/reminders`, `/state`), map each to its scope, and match the set the admin already approved for prod (typically `agreement_read`, `agreement_write`, `agreement_send`, `webhook_read`, `webhook_write`). Present it as a short table (scope, why) and list anything kept only for parity. Asking for broader scopes than the admin approved erodes trust and is a correction the user makes immediately.

## Product passes on a signing dashboard (user's standing preferences)

- **Features first, redesign after features lock.** Split a pass that mixes new features with a layout redesign into feature passes and a later redesign pass gated on them; features land functionally in the current layout.
- **No automatic writes into the counterpart system (e.g. ticket notes) until the business owner confirms.** Build a suggested note the admin can copy/edit, and add the confirmation question to the project's action tracker.
- **Every test agreement announces itself:** `[TEST - DO NOT SIGN]` in the title AND the signer message, `@example.com` (fictional) signers only. Put this rule in every build card.
- **Cards require strict TDD** (failing test first) and live verification of any Adobe behaviour relied on.
- **Label every note/message field by where it goes and who sees it** ("Legal Intake ticket note" vs "Adobe Sign agreement note" vs "Private message to this signer"). Never give a field the vendor's name when it is stored only in the product; back it with the real vendor object or relabel it. Check that the send flow offers each destination exactly once.
- **UI copy uses Adobe Sign's own terms** (Recipients, CC, Complete in order / in any order, Agreement name, Message, Private message, Reminders, Preview & add fields, Send). Professional and unambiguous beats over-simplified: a toggle says exactly what happens and when ("When the draft is created in Adobe Sign, also: ..."), never a vague "also run these updates".
- **Report product-facing changes, not mechanics.** Status updates to the user describe what admins see and can do; endpoints, payloads and API contracts only when the user asks to discuss them.
