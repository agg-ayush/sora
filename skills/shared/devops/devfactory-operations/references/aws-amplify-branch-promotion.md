# Amplify: staging -> prod promotion setup on an existing app

Use when standing up a staging environment on an Amplify app that already serves prod, renaming the prod branch, or enforcing "nothing enters prod except via staging".

## Procedure

1. **Read the app first.** `aws amplify get-app` (repository, platform, app-level env vars, build spec) and `list-branches` (which git branch each Amplify branch tracks, auto-build on/off). An app wired to the repo's default branch with auto-build ON means any merge to that branch ships to prod.
2. **Create the `staging` git branch from prod's head, never from a feature branch.** Branching staging off the feature branch makes the feature PR's diff against staging collapse to the last commit, and the PR no longer shows what is being promoted. If GitHub keeps serving a stale diff after you reset staging, push a no-op to the PR branch or re-target the base to force a recompute.
3. **Connect the staging branch in Amplify** (`create-branch --stage DEVELOPMENT --enable-auto-build`), then set its env vars at the BRANCH level from the secret store without printing values (build a JSON file, `update-branch --environment-variables file://...`, delete the file). `update-branch --environment-variables` REPLACES the whole map: read the current map, modify, write back.
   - **Match each value to the app's env schema before setting it.** Read the config parser (e.g. a zod schema in `src/lib/**/config.ts` via `git show origin/<branch>:<path>`): a flag parsed as `enum(["0","1"])` rejects `true`, and the failure only surfaces at request time as a generic error page.
4. **Forward server-side env vars into the SSR runtime via the build spec.** Amplify env vars exist only in the BUILD container; a Next.js SSR server (route handlers, server components) does not see them at runtime unless `amplify.yml` writes them into `.env`/`.env.production` before `npm run build` (`- echo "NAME=${NAME}" >> .env`, one line per var). An existing app usually already does this for its old vars; every NEW server-side var the feature adds must be appended to that list or it reads `undefined` in prod while the branch env shows the right value. Verify the yaml parses and every new var appears (python `yaml.safe_load`, check the build commands) before pushing.
5. **Override every app-level URL-ish env var per branch.** App-level env vars are inherited by every branch. A shared `NEXT_PUBLIC_BASE_URL` (or site URL, auth callback URL) pointing at the prod domain makes the staging site link and redirect to prod. `NEXT_PUBLIC_*` values are inlined at build time, so after setting the branch override start a new `RELEASE` job; changing the var alone does nothing. Verify by grepping the served HTML for the domain (`curl -s <staging>/login | grep -oE 'https://[^"]*<domain>'`).
6. **Custom subdomain:** add `staging` to the existing domain association's subDomainSettings mapped to the staging branch. When the Route53 zone is in the same account, Amplify writes the DNS records and the cert re-validates itself. Wait for `domainStatus=AVAILABLE`.
7. **Renaming the prod branch (e.g. main -> prod):** GitHub's rename carries PRs and settings; the Amplify branch mapping does NOT follow. Order matters: connect the new branch in Amplify, start a RELEASE job on it, wait for SUCCEED, repoint the domain mapping to it, and only then delete the old branch mapping. Deleting the old mapping first deletes its deployment and the prod domain serves Amplify's "Welcome / first deployment" placeholder until a build lands.
8. **Protect prod:** branch protection requiring PRs plus a required check that fails unless the PR's head branch is `staging` (read the head ref from the event payload via an env var, never inline-expanded into the shell).
9. **Supabase auth allow-list per environment** (when the app uses Supabase auth): add `https://staging.<domain>/**` (and the amplifyapp default domains if anyone signs in through them) to the project's Redirect URLs; replace stale entries for renamed branches (`main.<id>.amplifyapp.com` -> `prod.<id>...`). Read and write it via the management API: `GET/PATCH https://api.supabase.com/v1/projects/<ref>/config/auth` (`uri_allow_list` comma-separated, `site_url`), then read it back to confirm the write landed. PATCH needs Owner/Admin on that project; a read-only member gets "account does not have the necessary privileges" and the console fields are greyed out.
10. **Verify each environment by content, not status code.** A 200 can be the Amplify placeholder. Check the HTML is the real app (framework markers, no "Welcome") and that auth-gated routes redirect to login with the `next` path preserved.

## Pitfalls

- Run builds/watchers as a background loop on `list-jobs --max-results 1` status with completion notify, and make the same loop sweep the SSR logs after SUCCEED (`aws logs filter-log-events --log-group-name /aws/amplify/<app-id> --filter-pattern '<ErrorClass>' --start-time <now-90s>`), then hit the route once and sweep again. A green build says nothing about runtime config; env fixes surface schema errors one variable at a time, so each deploy can expose the next bad value.
- **Bound log sweeps to after the deploy finished.** A 10-minute window still contains the pre-deploy errors and reads as "still broken"; use a window that starts after the job's end time, or compare timestamps against it.
- **Amplify only builds and serves; it never applies the app's DB migrations.** A feature that ships `supabase/migrations/*.sql` (new tables, grant tables) deploys green but fails at runtime until someone applies the migration to the Supabase project. Check this before blaming auth.
- **Read the WHOLE migration file before applying it** (`git show origin/<branch>:supabase/migrations/<file>.sql`, all lines), then apply it verbatim and verify the resulting schema lists every table/index the file declares. Applying a partial reconstruction leaves missing tables that fail later in a different place.
- **Login on staging bounces somewhere wrong: diagnose in this order, each step a direct probe, not a guess.**
  1. Served HTML references the right domain (base-URL override, step 5).
  2. The `next`/return path survives the round trip: read the route guard, login page, sign-in action and `/auth/callback` on the deployed branch (`git show origin/<branch>:<path>`).
  3. The Supabase allow-list actually contains the staging callback (step 9, read via management API). Do NOT trust a probe of `/auth/v1/authorize?redirect_to=<staging>`: it 302s to the IdP carrying the staging `redirect_to` even when staging is NOT allowed, and Supabase only falls back to `site_url` (prod) after the IdP returns. Sign-in landing on prod = staging missing from the allow-list.
  4. The target route's own access gate: a layout that checks a grant table (`notFound()`/redirect on no row) bounces a logged-in user exactly like an auth failure. Probe the table with the app's service-role key from the Amplify env (write it to a 0600 file, never print): `curl "$SUPABASE_URL/rest/v1/<table>?select=*&limit=1" -H "apikey: $KEY" -H "Authorization: Bearer $KEY"`. HTTP 404 means the table does not exist, i.e. the migration was never applied; 200 with `[]` means the user lacks a grant row.
- **Past auth but the page shows a generic "could not be shown / Reference <id>" error:** the server threw at request time; the reference is a correlation id in the SSR logs. First suspects, in order: a server-side env var not forwarded into the runtime (step 4), a value rejected by the env schema (step 3), then the upstream API itself.
- Applying migrations, seeding grants or editing auth config on the app's Supabase project needs project access. If no tooling can reach the project, tell the user the exact project-level role needed (Owner/Admin on that project, not org membership) and the exact file/row/setting; once they have it, do the edit yourself rather than walking them through the console.
- When the old app's Supabase project is identified this way (`NEXT_PUBLIC_SUPABASE_URL` in the Amplify env), record it as part of the old-deployment inventory for teardown.
- **Audit an inherited deployment before promoting new code onto it.** Reusing an existing Amplify app and Supabase project because they were already there does not make them production-grade. Before the first staging->prod promotion, measure cold and warm latency on staging, check the hosting's SSR scaling posture against the alternatives available in the account, audit the kept code paths (auth, DB clients, middleware) and the DB project's plan, RLS and backups. Return a keep/fix/replace verdict per area. Promotion stays blocked until that verdict exists.
- **Retiring legacy data from the inherited Supabase project:** (1) export every legacy table to JSON and walk every storage bucket recursively (list with `prefix`, entries without `id` are folders), downloading idempotently (skip files already on disk) as a background job, since a large bucket outlasts a foreground timeout; (2) verify the archive: row counts match, object count matches the bucket, spot-check file magic bytes (`%PDF-`); (3) list dependents before dropping: FKs into the legacy tables, views (`information_schema.views`), and storage RLS policies on `storage.objects` that reference the tables. Drop policies, then views, then tables in ONE named migration, never `CASCADE` blind; keep tables the new code FKs into (e.g. `users`); (4) delete all bucket objects (`DELETE /storage/v1/object/<bucket>` with `{"prefixes": [...]}`), then the bucket; (5) read back `information_schema.tables` to confirm only the intended tables remain; (6) ask where the archive should live durably (Drive or S3) since a box-local copy is not a backup.
- When handing the user a staging link, give the full route of the feature (`https://staging.<domain>/<route>`), not only the domain root; a feature added as a side route is invisible from the landing page.
