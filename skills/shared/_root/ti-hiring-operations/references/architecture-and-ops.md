# TI-Hiring — Architecture & Operations Reference

Map of the whole pipeline: what's deployed where, how data flows, where creds live, and the operational gotchas. Read this before any TI-hiring infra/ops task so nothing gets missed.

## Components

| Component | What it is | Where it runs | Deploy trigger |
|---|---|---|---|
| **Orchestrator** | Session lifecycle: create/join/provision/teardown/upload. Admin API. | ECS service `ti-orchestrator`, ap-south-1, acct <aws-account> | `deploy-orchestrator.yml` on push to main |
| **Wrapper** | Candidate-facing SPA at `<internal-host>` (terminals, briefing, review pane) | ECS service behind same ALB, host-header routing | `deploy-wrapper.yml` on push to main |
| **Sandbox** | Per-candidate ephemeral env running Claude Code in tmux | **Vercel Sandbox** (`VercelSandboxProvider` in `orchestrator/src/providers/sandbox.ts`) | provisioned on demand per session |
| **Recall** | Meet bot that joins the video call and records | Recall.ai API, dispatched by orchestrator at session create | per-session |
| **Drive upload** | Recording + transcript land in a startgreat Drive folder | **orchestrator-side only** (see "Drive & Google creds") | teardown pipeline |
| **VVA / Deep Dive** | The 20-min AI interview (separate system) | `<internal-host>` | not this repo |
| **Evaluator** | Grades a candidate's captured transcript against a rubric | `transcript-eval/` (GCP Cloud Build + GCS + Vertex), in the ti-hiring repo | manual/on-demand, not part of the candidate-facing deploy |

## Data flows (where things come from)

- **Transcripts / workspace files**: orchestrator runs `tar czf /tmp/capture.tar.gz` INSIDE the sandbox via the sandbox provider's agent (`SandboxHandle.runCommand`), then pulls the bytes back with `SandboxHandle.readFile` → `readFileToBuffer`. No SSH, no creds in the sandbox — the provider's control channel is the transport.
- **Recording video**: comes from **Recall's API** (the Meet bot), NOT the sandbox. Orchestrator downloads it post-session.
- **Drive upload**: 100% orchestrator-side (`orchestrator/src/lifecycle/teardown.ts` `drive.uploadFile`). Pipeline: `capture → spool → upload → await_confirm`. Spool is local dir or S3 (`S3SpoolStore`). Sandbox never sees a Google credential.
- **Meet link**: created by orchestrator at session-create using startgreat's Google identity. Per-session, dies when the session is destroyed.
- **The captured `transcript.jsonl` is the sole evaluation signal for a candidate's session.** `prompts.txt` is a derived, filtered, human-readable view generated FROM the transcript (`renderPromptsDigest` in `orchestrator/src/lifecycle/teardown.ts`) for the candidate/reviewer pane — it carries nothing the transcript doesn't and is not a separate input. There is also no `DECISIONS.md` or other workspace file to read — candidates are not asked to produce one, and no such signal exists in the capture. When scoping any ingest/grading task against session data, don't assume an auxiliary derived file or workspace artifact is a needed input — verify against the actual capture pipeline (teardown.ts) what gets produced, and default to "transcript.jsonl only" unless a new artifact is confirmed to exist.

## Evaluator (transcript-eval)

- **`evaluator-v1/` is deprecated — the live evaluator is `transcript-eval/`.** Don't touch or extend evaluator-v1 for new work; its README points at transcript-eval as current.
- **Assignments live in a separate repo, `<org>/ti-hiring-assignments` — and its branches hold DIFFERENT assignment sets, which matters for anything that syncs rubric knowledge.** `seed/initial-16` = the 16 new `the-*`-named assignments (seeded this batch cycle; `INTERNAL/<X>.md` hoisted to the repo's TOP level, one per top-level folder = `ASSIGNMENT_ID`). `seed/full-20` and `main` = the original/full assignment set (20 folders, includes the older non-`the-*` ids like `say-it-in-json`, `promise-them-nothing-twice`, `the-spec-nobody-implemented`, `the-audit-log-that-could-lie` that real candidate batches have actually run on) — on THIS branch the INTERNAL.md hoist has NOT been applied, so the rubric/answer-key still lives inside each candidate folder (`<assignment>/INTERNAL.md`), not at top-level `INTERNAL/`. Before wiring or debugging any rubric-sync step, check which branch actually contains the assignment id you need and read INTERNAL.md from the right path for that branch — don't assume the initial-16 layout (top-level `INTERNAL/`, hoisted) applies repo-wide, and don't assume a missing rubric means content was deleted or never written; it usually means the sync pulled from the wrong branch.
- **The evaluator's ingest was originally built for a different flow (GitHub-submission clone: `acquire-submission` → clone a candidate repo → expects `sessions/` + `solution/` + `DECISIONS.md`, with machinery catering to multiple AI-tool submission formats) and has since been rewired to take our captured-session `transcript.jsonl` directly** (a dedicated `acquire-capture` step, sha256-verified, rendered into the dialogue-markdown format the judge/`slim-transcripts` step consumes). `DECISIONS.md`/`solution/` are not read anywhere post-rewire — the transcript is the only evaluation signal (consistent with the "Data flows" section above). Grading is per-assignment: `loadRubric(assignmentId)` overlays `src/knowledge/assignments/<assignmentId>.md` (synced from ti-hiring-assignments' `INTERNAL/`) onto the shared rubric; unknown ids fail loudly.
- **When wiring the evaluator's ingest to a new input source, verify against the ACTUAL storage location the artifact lives in, don't trust the existing scaffold's assumed backend.** The captured-session rewire initially read via `CAPTURE_OBJECT`/`CAPTURE_DIGEST` through a `GcsObjectStore` (GCS) — but real candidate transcripts land in the candidate's per-session **Google Drive** folder (per the "Drive upload" data flow above), not GCS. A pipeline component that already exists for one purpose (grading) can be built against the wrong backend for a NEW purpose (real captures) even when it looks complete and passes its own unit tests — cross-check the actual artifact's real location before considering an ingest step wired, not just that it downloads-and-verifies successfully against whatever test fixture it was built with.
- **Validate a rewired evaluation/ingest pipeline against real diverse captured sessions, not a single synthetic happy-path e2e.** At minimum: one or more "proper" sessions where the candidate did real work (confirms grading produces a sensible per-assignment score), AND one or more empty-transcript sessions (confirms the pipeline handles no-content honestly — flagged as ungraded/no-signal, not scored as if work existed, and does not crash). A worker's "e2e tested" claim on a single fabricated or synthetic transcript is not sufficient evidence the pipeline works on the actual population it will grade.
- **Before grading a full batch, always run a small representative subset first as an explicit gate** — pick sessions spanning every distinct `ASSIGNMENT_ID` the batch actually used (not just one), plus at least one thin/low-content session, and require each to produce a real per-assignment-rubric verdict with citations before green-lighting the full run. A batch commonly spans assignment ids from more than one source branch/seed set (see the branch-topology note above) — running only on ids from the set you happened to build against will silently mis-grade or hard-fail on the rest once the full run starts. Treat "ready for the full batch" as unproven until the subset covers every assignment id actually present in that batch.
- **When a rubric/config lookup is missing or a discrepancy shows up in a system with multiple contributors (e.g. "why does the evaluator know about the new assignments but not the ones a specific person actually ran candidates on"), verify the real cause with `git log --author`/`git ls-tree` across every relevant branch and repo before attributing it to a person's mistake or oversight.** The likely answer is a wrong default (a sync script pointed at the wrong branch, a config that only covers the newest data) introduced by a DIFFERENT recent change, not the original author having done something wrong — check who wrote which piece and which branch each artifact actually lives on before narrating fault.

## Credentials & where they live

- **startgreat Google OAuth** (calendar, drive, meet, gmail.send): SSM params `/ti/orchestrator/GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `GOOGLE_OAUTH_REFRESH_TOKEN` (ap-south-1). The refresh token has `gmail.send` scope (added Sep 18). To READ startgreat's Gmail: pull the three SSM params, exchange the refresh token at `oauth2.googleapis.com/token`, hit `gmail.googleapis.com` directly. Do NOT rely on the ops-box gog keyring.
- **Orchestrator reads Google creds at task boot only** — after rotating the SSM token, force a new ECS deployment or the running service keeps the old one.
- **Admin API token**: `/home/ubuntu/.ti-hiring-admin-token` on the ops EC2 box.
- **LLM gateway**: sandbox Claude Code points DIRECT at Fireworks (`ANTHROPIC_BASE_URL=https://api.fireworks.ai/inference`, `ANTHROPIC_MODEL=accounts/fireworks/models/glm-5p3-flash`), both read from SSM `/ti/orchestrator/ANTHROPIC_*` — there is NOT a TrueFoundry hop in the candidate-facing path. TrueFoundry is only in play for this team's OWN tooling (Codex CLI, model fallbacks), a separate concern from what candidate sandboxes call. Always re-read the actual SSM values (`aws ssm get-parameter --name /ti/orchestrator/ANTHROPIC_BASE_URL ...`) before reasoning about which provider's rate limits apply — don't assume a gateway hop exists just because one exists elsewhere in the org's infra.

## Session lifecycle mechanics

- **No reschedule API.** To move a candidate: destroy the session, create a new one at the new `scheduled_start_at` (same assignment), resend the email with the NEW Meet link. `/override` only has extend/freeze/force_destroy/retry_upload.
- **Join window**: `JOIN_WINDOW_MINUTES` default 10 (`orchestrator/src/config.ts`). A verified join past `scheduled_start + joinWindow` → `forfeit` (terminated, end_reason=forfeited). `join.ts`.
- **scheduledStartAt** is camelCase on detail/list; `scheduled_start_at` on the list endpoint returns empty — use the detail endpoint for the real time.
- **Session times are stored UTC.** IST = UTC + 5:30. (e.g. 12:30 UTC = 6:00pm IST, 14:00 UTC = 7:30pm IST.)
- **Auto-mode classifier pin (#256)**: pinned into sandbox `settings.json` `env` block at provision. Gotcha: the pins are conditional on `model` being non-empty (`...(model ? {...} : {})`), and reattach paths (provision.ts resume, reconcile sweepVanished, join ready-expiry) do NOT re-run provision.sh — so a pre-fix sandbox keeps stale pin-less settings.json. Fix: convergeAuthSettings on reattach.

## Sandbox permission mode (candidate-facing, must be silent)

- **Requirement: candidates must see zero permission prompts AND zero permission warnings.** Working fix: launch with **`--permission-mode bypassPermissions --permission-prompts none`** on the `claude` CLI invocation (`sandbox/entry.sh`) — empirically confirmed against the actual binary to produce no warning and no prompt (unlike the two failed attempts below). Two earlier attempts were insufficient:
  - `defaultMode: "bypassPermissions"` in sandbox `settings.json` (provision.sh) alone — did NOT actually suppress edit prompts for a live candidate despite being deployed; settings.json default mode is not equivalent to passing the CLI flag.
  - `--dangerously-skip-permissions` CLI flag — bypasses runtime checks but shows a startup "are you sure" warning/confirmation, which candidates must not see. Also broke the sandbox harness (see below). Reverted.
  - When a CI harness fails only because its literal-string/stub assertions don't recognize a legitimately-verified new flag (confirmed manually against the real pinned binary, or a live candidate session), it is reasonable to admin-merge past that failure under time pressure — but file/keep open a same-branch or follow-up fix for the harness stub itself so the test stays meaningful for the next change.
- **Always test permission-flag behavior against the actual pinned Claude Code version, not whatever is locally installed.** The ops box had 2.1.276 while the sandbox pins 2.1.268 — flag help text and gating behavior can differ across versions; `claude --help` locally is a hint, not proof, for the pinned version.
- **The sandbox harness (`sandbox/harness/verify.sh`) stubs a fake `claude` binary that only implements `--version`** (`printf '%s (Claude Code)\n' "$CLAUDE_CODE_VERSION"`). Any change to the real launch line (`sandbox/entry.sh`) that adds a flag the stub doesn't expect makes the harness fail with "entry did not reach Claude Code" — this is a test-harness gap, not proof the real flag is broken. When changing the claude launch invocation, update the stub (or the harness's expectations) in the same PR.
- **`verify.sh` hard-asserts exact tmux config strings** (`grep -Fq 'set -g set-clipboard off'` must match, `set-clipboard on` must NOT appear; same pattern likely applies to `mouse`). Before changing any `provision.sh` tmux/security directive, grep `verify.sh` for the exact string first — the harness enforces specific literal lines, not just behavior.

## Session admission / stale-cookie 404

- **`boundSessionRecord(id)` 404s ("Page not found") if the signed-in cookie's session id doesn't match the CURRENT session `lookupByEmail(email)` resolves for that candidate.** This bites you whenever a candidate (or a tester) has more than one session for the same email — e.g. after a reschedule, or repeated manual test sessions. Symptom: candidate signs in fine, but the session page 404s even though the session record itself is healthy (`scheduled`/`ready`).
- **Fix for testing**: destroy all but the one session you want to test for that email, or clear the site's session cookie (incognito window, or clear cookies for `<internal-host>`) and sign in again — this re-resolves the lookup to the current session.
- **"We couldn't start your environment. Please contact support" can be a transient false failure**, not an actual provisioning failure — it can render while provisioning is still mid-flight (join → sandbox_created → meet_created → recall_dispatched → ready takes tens of seconds). Reload the session page before treating it as a real outage; check the session's actual status/events first.

## Scaling / known ceilings

- **RDS db.t4g.micro ~85 conns; PG_POOL_MAX=20/task ⇒ RDS-safe MaxTaskCount=4.** The autoscaler (#259) is held unmerged pending a gate.
- **Vercel Sandbox concurrency ceiling is ~10k on the Pro plan** — not the bottleneck for a 600-candidate wave. Sandbox provisioning is join-triggered (fires in `join.ts` only; there is no schedule-ahead sandbox warm-up, only the Meet window is pre-created at schedule time), so a batch's real concurrent-provision spike happens at the scheduled start time as candidates join within the join window, not spread out. **There is no client-side concurrency throttle/queue in the orchestrator's provision path** — the real risk at scale is the orchestrator's own DB pool (see RDS ceiling above) and downstream API rate limits (Recall, Google Meet), not Vercel capacity. This has not been load-tested at 600-concurrent-join; treat post-batch verification (claims == recordings, 0 failures) as the actual signal, not an assumption that it's fine.
- **`deploy.sh` preserves live DesiredCount/Min/MaxTaskCount across deploys** — a template default change does NOT affect an already-deployed stack; only the read-back path or an explicit override does.
- **Deploy runs only on push to main** (image + CFN together) — no partial image-vs-stack state.

## Candidate terminal connectivity

- **"Connection lost, reconnecting…" that never recovers is usually the wrapper's terminal reconnect loop giving up too early, not the sandbox dying.** `wrapper/src/components/terminal-client.tsx`'s TerminalPane retried the dropped WS with a short fixed backoff and a small attempt cap, then permanently declared the session lost — any transient outage longer than that cap (WiFi blip, laptop sleep, NAT rebind, brief edge hiccup) locked the candidate out even though the sandbox was alive and the orchestrator still showed the session `live`. Fix pattern: retry indefinitely with capped exponential backoff + jitter, never show a terminal "lost" state while the orchestrator session is live, only a non-blocking "reconnecting". tmux persists scrollback/shell state across a reconnect, so recovery is seamless once the socket reconnects.
- **Retry-forever fixes the LOCKOUT (candidate recovers instead of getting stuck), it does NOT fix why the socket drops in the first place.** Don't present "we now retry forever" as root-caused if a meaningful fraction of sessions are still dropping (check ws-bridge logs for reconnect-storm frequency across the fleet, e.g. ~46% of sessions in a batch is a systemic rate, not scattered bad WiFi). `ws-bridge` already pings both client and upstream every `PING_INTERVAL_MS` (default 30s) specifically to stay under the ALB's 60s idle timeout (`ws-bridge/src/config.ts`, `server.ts`) — so an ALB idle-kill is already defended against. If drops still correlate with ping cadence at scale, suspect the ws-bridge→sandbox-ttyd hop itself (ttyd's own keepalive stalling under concurrent load, or a Vercel sandbox network/egress limit under concurrency) rather than re-explaining it as "the ALB" or "WiFi." Root-causing the sever (not just the recovery) needs a separate investigation reproduced under realistic concurrency, not a single manual test session.
- **Before assuming a platform timer (Vercel sandbox WS lifetime) is killing the connection, hold a direct WS connection to a FRESH sandbox's ttyd for several minutes.** If it holds with no drop, the platform is not the cause — look at the wrapper's own reconnect/give-up logic first, and at ws-bridge logs for reconnect-storm frequency across the fleet (a high fraction of sessions storming means a systemic client bug, not isolated bad networks).
- **A `410 Gone` on the sandbox URL during a live-seeming session is not itself the bug — check WHY the sandbox is gone before treating it as a spontaneous death.** It is commonly downstream of an intentional teardown (tab-strike freeze, admin freeze/force_destroy) that already happened for an unrelated reason; the 410 is a symptom of that teardown, not evidence the connection-drop and the teardown share a root cause.
- **Candidate reports of "arrow keys don't work" most often turn out to be the Claude Code Bypass Permissions disclaimer parking focus on a dead-key modal** ("No, exit" / "Yes, I accept" — focus starts on "No, exit", and plain arrows/Tab don't move it; only Esc or Enter-on-"No, exit" respond), not a cursor-key/terminal-mode bug. Fix: pre-accept the disclaimer at provision time so fresh sandboxes boot straight past it.
- **The real fix for "can't scroll back through the transcript" is disabling tmux's alternate-screen mode (`set -g alternate-screen off` in the sandbox's tmux config, `write_tmux_config` in `sandbox/provision.sh`), not accepting wheel-sends-arrow-keys as expected behavior.** With alternate-screen on, tmux discards scrolled-off lines the instant Claude Code redraws its fullscreen TUI — there is nothing to scroll back TO no matter what key/wheel event is sent. With it off, tmux renders inline and keeps the whole transcript in the pane, so PgUp/PgDn become real scrollback and the wheel can be routed there too. **Never repurpose up/down for this** — they are Claude Code's own prompt-history recall by design and must stay exactly as-is; wire the new scroll path (wheel, PgUp/PgDn) to move the pane's scroll position without emitting arrow sequences, so scrolling and prompt-recall stay fully independent and never clobber the input line.
- **Before closing an arrow-key/scroll report as "root-caused, no code change needed," get a live repro against the exact build the reporting candidate hit.** A single fresh manual/Chromium test session by the investigating worker on a fresh sandbox is not equivalent to a real candidate's session state, timing, or browser — if the user reports the symptom persisting on candidates AFTER the claimed fix (e.g. the disclaimer pre-accept) is deployed, treat the incident as still open and re-repro rather than relaying the prior investigation's conclusion as settled.
- **tmux prefix-matches session/window names unless you force exact with a leading `=`.** On tmux 3.4 `has-session -t candidate` exits 0 when only `candidate-1` exists, and `list-windows`/`select-window`/`display-message -t candidate` resolve to the wrong session. In `sandbox/provision.sh` every target naming the candidate session or a `candidate-N` group MUST use the `=`-exact form (`=candidate`, `=candidate-N`, `=candidate-N:N`); the one deliberate exception is `stop_tmux_sessions`, which intentionally prefix-matches so a surviving `candidate-N` still triggers cleanup. A non-exact target reads as "session exists" whenever a `candidate-*` group is alive, silently skipping reconvergence of the real `candidate`.
- **A candidate pane with no Claude is a bare shell, and the reliable signal is `pane_start_command`, NOT `pane_current_command`.** entry.sh relaunches claude in a `while true` loop instead of exec'ing it, so `pane_current_command` stays `bash` whether Claude is healthy or not. `pane_start_command` is `$TI_HOME/bin/entry` for a good pane and EMPTY for a bare default shell — that empty value is the dead-pane signal. `check_terminal` and the orchestrator pane-health probe both key off it.
- **A window-N ttyd reconnect that races a tmux-server death lands the candidate on a bare shell unless the attach converges the pane first.** `tmux new-session -A -t candidate -s candidate-N` on a dead server creates a FRESH ungrouped session literally named `candidate-N` running a default shell (no entry), and the `';' select-window` fails silently. The fix is `sandbox/bin/attach-window.sh`: it runs `ensure_panes` (the same convergence start_terminal uses) before attaching, so a reconnect can only land on a window already running entry. Vercel sandboxes do NOT preserve processes across suspend/resume — only the filesystem is snapshotted — so any resume is a tmux-server death and hits this path.

## LLM gateway load / rate limiting

- **Candidate-facing 429s during a batch are very likely the model provider load-shedding under concurrent batch load, not our own API.** Check orchestrator/ECS logs for literal rate-limit log lines first (a raw grep for "429" can false-positive on timestamps like `12:54:28.429Z` — filter for an actual HTTP-status or rate-limit log field, not the substring). If nothing in our logs, the 429 is almost certainly from the LLM provider (Fireworks) itself under Standard-tier load.
- **A bare substring search for "429" false-positives everywhere, not just log timestamps: session/thread ids (`...4295-...`), ISO timestamps (`14:00:13.429Z`), and base64-encoded mail bodies routinely contain the digits "429" with no relation to an HTTP status.** This bit the same way twice (orchestrator log grep, then Gmail body search). Always require a structured field (`apiErrorStatus`, an HTTP-status log key, a `X-Ratelimit-*` header) or decode the actual content and read it in context — never trust a raw substring hit as evidence of a rate-limit event.
- **VVA / Project Deep Dive candidates cannot hit Fireworks/Claude-Code rate limits — it's a separate proctored AI voice-interview system that never drives a Claude Code agent or calls the LLM gateway.** Only the ADD/technical assessment (Claude Code in the sandbox) touches Fireworks. If a candidate reports "rate limit"/"429"/"API error" on VVA specifically, that report is describing something else (video/audio/proctoring), not our token ceiling — don't cross-attribute.
- **Fireworks rate limits are token-based (TPM: Total Prompt, Uncached Prompt, Generated — three separate ceilings per model-size tier), not request-based (RPS).** A load test with a small fixed-size dummy prompt cannot reveal which TPM bucket actually binds for real traffic, because real Claude Code turns re-send the full growing conversation (system prompt + whole transcript + tool results) as input each turn — Prompt TPM dominates in ways a flat payload never exercises. To find the real binding constraint: drive the load test with multi-turn conversations whose input grows turn over turn like a real coding session, ramp concurrency past the known peak, and capture the `X-Ratelimit-Limit-Tokens-Prompt` / `-Cache-Adjusted-Prompt` / `-Generated` response headers on every call so you know which bucket is at its ceiling when 429s start — not just that 429s happened. Also run a cache-on (sticky prefix/session-affinity) vs cache-off arm, since prompt caching can raise the effective ceiling for the Prompt TPM bucket specifically.
- **Fireworks' Priority serving tier reduces 503/429 load-shedding under peak concurrent load but is strictly opt-in per request via `service_tier: "priority"` in the request body — there is no account-level default, and it costs ~1.5x Standard.** It's supported on both the OpenAI-compatible and Anthropic-compatible `messages` APIs.
- **Claude Code DOES support injecting arbitrary fields (including `service_tier`) into its own request body natively — via the `CLAUDE_CODE_EXTRA_BODY` env var (or the `env` block in `settings.json`), a JSON object spread verbatim into the outgoing `/v1/messages` body.** Verified empirically against the real pinned binary (`@anthropic-ai/claude-code-linux-x64@2.1.268`): source inspection shows the body-builder spreads `CLAUDE_CODE_EXTRA_BODY`'s parsed keys directly into the request literal untouched, and a live capture-server test confirms `service_tier: "priority"` lands in the outgoing body when the env var is set. This makes a network-hop relay unnecessary for injecting a body field Claude Code doesn't have a dedicated flag for — **before building a proxy/relay to add a request field, check the CLI's own env-var/settings passthroughs (grep the bundled source, don't trust a quick SDK type-def read or docs skim) — a one-line env var can replace a whole new service.** Caveat: `CLAUDE_CODE_EXTRA_BODY` is gated by the org's "experimental betas" managed policy — if that policy disables experimental betas, the env var is silently ignored (no error, just absent from the body). Confirm the target deployment has no such policy before relying on this path in place of a relay. Note `ANTHROPIC_CUSTOM_HEADERS` is a DIFFERENT mechanism (sets HTTP headers only, cannot carry a body field like `service_tier`) — don't conflate the two when checking passthrough options.
- **To attribute a 429/rate-limit incident to a SPECIFIC candidate rather than the fleet in general, check that candidate's own transcript JSONL (downloaded from their Drive folder) for literal `429`/`rate limit`/`overloaded`/`temporarily unavailable` strings.** This is direct per-candidate evidence the provider load-shed their session specifically, and is stronger than an orchestrator-log grep (which only tells you the fleet-wide rate, not who was hit) or an unverified assumption from a vague candidate complaint.
- **When sizing a TPM-limit-raise ask for N concurrent candidates, don't multiply a synthetic load-test's per-agent rate by N — derive the per-agent token rate from REAL completed candidates' transcript JSONL `usage` fields (`input_tokens`, `output_tokens`, `cache_read_input_tokens` on each `type:"assistant"` row) instead.** A synthetic stress test's concurrency-ceiling framing ("X agents was the breaking point, peak needs Y was that") and a real-usage-derived TPM figure (median per-agent tokens/min × N, against each Fireworks bucket ceiling) are different methodologies and give different multiples — the real-usage one is the defensible number to send the provider, because it's what actual candidates actually did, not a synthetic driver's assumptions about turn cadence/growth. Compute median `(fresh_input + cache_read)/duration_minutes` per bucket across a sample of >=5-turn completed sessions, then multiply by the target concurrency to get real demand per bucket (total-prompt, uncached-prompt, generated) vs the measured ceiling. Also remember N concurrent candidates are NOT N simultaneous requests — each candidate's real request rate is already captured in their per-minute average, so this median-rate method naturally accounts for non-simultaneity without needing a separate concurrency-vs-rate correction.
- **To test whether routing through TrueFoundry (e.g. model slug `fireworks-group/glm-5p3`) gives different rate-limit capacity than calling Fireworks direct, hit `https://<llm-gateway>/v1/chat/completions` (Bearer token from `$TFY_API_KEY` or `$TRUEFOUNDRY_API_KEY`, whichever is set in env) with the model slug and read the response's `x-ratelimit-limit-tokens-*` headers — same header names Fireworks returns direct, so the two are directly comparable.** `curl -s -D - -o /tmp/resp.json -X POST <url> -H "Authorization: Bearer $TFY_API_KEY" -d '{"model":"fireworks-group/glm-5p3",...}' | grep -iE ratelimit`. This org has multiple TrueFoundry-branded hosts that look plausible but are wrong for the candidate/hiring-side gateway: `gateway.truefoundry.ai` (generic SaaS entry, 403 here), `<llm-gateway>.truefoundry.cloud/api/llm/...` (this Hermes agent's own model-fallback config, a different workspace — returns 401 "Invalid token" here even with a valid-looking key). Only `<llm-gateway>/v1` is the right one for this team's models. A 401/403 from a TrueFoundry-looking host is much more likely the WRONG host/workspace than a bad key — confirm the host (ask the user for a known-good curl example) before concluding a credential is invalid.
- **Fireworks published TPM ceilings are per model-size tier (by TOTAL params, not active/expert params) and are separate from the account's live adaptive limit.** Tiers: Small <400B (64.8M total / 16.2M uncached / 648K generated), Medium 400B-1.6T (43.2M/10.8M/432K), Large >=1.6T (21.6M/5.4M/216K). Production uses **glm-5p3-flash = 320B total params = Small tier** — don't confuse it with the base `glm-5p3`/GLM-5.3 (744B, Medium tier); verify the exact deployed model string (`ANTHROPIC_MODEL` from SSM) and look up ITS param count, not a similarly-named sibling model, before picking a tier. The account's actual live ceiling floats below the tier max and grows/shrinks with sustained usage ("adaptive limit") — read it fresh from response headers (`x-ratelimit-limit-tokens-prompt` / `-uncached-prompt` / `-generated` on any real call), never assume it equals the doc tier ceiling. A 429 during a sudden batch wave means concurrent demand outran the current adaptive floor even though the account is still under the documented tier max — the fix/ask is to raise the account's adaptive floor (or request a custom raise if the need exceeds even the tier max, as with Generated TPM for a 500-candidate wave), not to argue tier headroom exists.
- **To check whether real candidate sessions approach the 200k context window or rely on auto-compaction, pull each session's transcript JSONL and for every `type:"assistant"` row sum `usage.input_tokens + usage.cache_read_input_tokens + usage.cache_creation_input_tokens` as that turn's effective context size, tracking the max per session; scan all rows for a `compact`-type system event to flag whether compaction fired.** In the 30-min-timeboxed assessment format, sessions have not been observed to approach 200k — the timebox itself caps growth (observed max ~145k), and Claude Code's own auto-compaction already fires well below that ceiling (observed starting in the 130-150k range) as a second-layer safeguard. Don't re-derive this from first principles each time; the transcript JSONL is the ground truth for actual context size, not an assumption about turn count or model context window.

## Proctoring accuracy (strikes vs recording)

- **The recorded `strike_count`/`tab_hidden` events can under-report real violations visible on the session recording.** Confirmed case: a candidate's recording clearly shows two focus/tab violations, but the orchestrator session had `strike_count=0` and zero `tab_hidden` events, so an automated clean/violation filter (based on strikes+events) wrongly counted the session as clean. The detector only fires on `document.hidden` (visibilitychange) — a focus change that doesn't trigger that event (PiP window, OS-level switch, clicking into a floating window without hiding the doc) can violate without ever counting as a strike.
- **When a human reviewer says the recording shows something the session record doesn't (a violation, a different outcome), treat the recording as ground truth and verify the record's mechanism, not the other way around.** Don't defend an automated filter's output against a live video review.
- **Before answering "is X the right recording/file for this candidate," verify independently**: pull the candidate's session id via `lookupByEmail`, confirm it matches both the Drive folder id (`drive_folder_id`) and the filename prefix inside that folder (files are named `ses_<id>-<type>`). Don't just assert it matches from the folder link alone.
- Also: a session's own `review_comment` field (candidate's self-reported note) can reveal a disruption (e.g. "my assessment automatically ended mid-session") that a strikes/events-only filter misses entirely — check it before mechanically bucketing sessions as clean.
- **Before hardening a soft proctoring signal (e.g. Recall webhook events for camera/screenshare/recording) into a hard gate on Continue, measure its reliability under realistic conditions first**: run many repeated real joins and check event arrival rate, delivery latency (p50/p95/p99), and failure modes (dropped/duplicate/out-of-order, degradation under a multi-bot burst) — as a separate investigation-only spike, not bundled into the gate's build PR. A hard gate on an unreliable signal risks locking out an entire batch on a webhook hiccup; only promote from a warning banner to a hard gate once the reliability numbers support it, and keep a fail-open timeout even then.

## Batch operations

- 600-candidate waves: sessions created in bulk at a fixed UTC time per city batch. Verify post-batch: claims == unique recordings, 0 doubles, 0 failures.
- Roster/schedule source: the candidate list is an application-form Sheet (no session times in it); session times live only in the session records, keyed by candidate email.
- **A named batch (e.g. "the IIT Patna batch") has no queryable identifier anywhere in the data — not in the session record, not in the Drive folder structure.** Drive's per-session folders (`ti-session-ses_<uuid>`) are sorted by upload date only, with no college/city/cohort field; picking folders by eyeballing a date range guesses at the batch boundary and will pull in unrelated smoke-test or other-batch sessions. Before running any per-batch count/analysis, get either the exact scheduled UTC time window for that batch or the candidate roster (email list) from the user — don't infer the batch from folder dates.
- **The orchestrator's RDS instance is VPC-internal and does not answer psql from the ops EC2 box** (`Connection timed out` dialing the RDS hostname on 5432, even though `psql` is installed and `DATABASE_URL` is in `.env.deploy`) — the security group only admits the ECS task network, not the ops box. Ad-hoc SQL analytics (e.g. "which sessions belong to batch X") isn't reachable this way; use the admin HTTP API (`/v1/sessions` list + `/detail`, see "Batch outcome reporting" above) or Drive, scoped by a known time window or roster, instead of trying a direct DB connection from this host.

## Batch incident triage at scale (flood of candidate error emails)

When a batch produces a flood of candidate error reports (dozens+) and the ask is "which of these are our fault" — this doesn't fit in one pass; fan it out:

1. Pull distinct issue-reporter emails from Gmail for the batch window (`newer_than:Nh -from:startgreat -from:mailer-daemon`, skip calendar accept/decline/maybe auto-replies), dedupe by sender.
2. Slice the sender list into N even chunks (one per parallel subagent — 4 subagents × ~20 candidates each is a workable size) and write each chunk to a JSON file the subagents read.
3. Fan out one subagent per slice via `delegate_task`, each doing, per candidate: (a) `lookup?email=` → `/detail` for join/enter/end_reason/strikes/scheduled time; (b) download and grep the candidate's own transcript JSONL from Drive for 429/rate-limit/overloaded strings and for emptiness; (c) note recording/Drive-folder presence. Each subagent classifies every candidate into a small fixed set of mutually-exclusive buckets (e.g. our-fault-system, our-fault-429, connection-lost-ambiguous, candidate-fault, no-issue-found) and writes one JSON verdict file per slice.
4. Aggregate the verdict files afterward into one report. This turns "read 80 emails and vibe-check each" into a structured, evidenced classification that scales, and keeps each subagent's cross-reference work (which needs several tool round-trips per candidate) off the main thread.
- Give every subagent the SAME bucket definitions and the SAME ambiguity rules (e.g. connection-lost defaults to ambiguous, not our-fault, per the regional-connectivity caveat above) — if each subagent free-forms its own classification criteria, the aggregated report won't be comparable across slices.
