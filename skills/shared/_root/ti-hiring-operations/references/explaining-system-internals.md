# Explaining ti-hiring internals (data flows, schemas, integrations)

Use when Ayush asks how a part of the system works (orchestrator loop, wrapper-to-orchestrator calls, media gate, Recall, Postgres columns).

## Procedure
1. Pin the DEPLOYED commit, not local HEAD: `aws --profile trilogy ecs describe-services --region ap-south-1 --cluster ti-orchestrator --services ti-orchestrator --query 'services[0].taskDefinition'`, then describe that task definition; the image tag is the commit sha. On `ExpiredTokenException` run the aws-creds-refresh script and retry.
2. Read code at that sha with `git -C /home/ubuntu/ti-hiring show <sha>:<path>` / `git grep <pattern> <sha> -- <paths>`, so the answer describes what is running, not an unmerged branch.
3. Check live config for every config-gated feature: task-definition `environment` + `secrets` (names only, never print secret values) and `aws cloudformation describe-stacks --stack-name ti-orchestrator` parameters. Many features register only when ALL their config is present (e.g. the Recall participant webhook route and `realtime_endpoints` need `RECALL_WEBHOOK_PUBLIC_URL` plus `RECALL_WEBHOOK_SECRET` or `RECALL_WEBHOOK_TOKEN`); a public URL alone, or an SSM parameter that exists but is not referenced by the task definition, leaves the feature OFF.
4. For lists (columns, events, env vars) verify completeness programmatically against the source (parse the interface, compare sets) before presenting a grouped table.
5. Distinguish push vs pull explicitly: who calls whom, webhook (vendor server POSTs to us) vs API call (we call vendor), and whether the browser polls its own route or a backend.
6. When listing a table's columns, also name the sibling tables keyed to it (e.g. media-gate signals live in their own table, not on `sessions`); omitting them makes a feature look unmerged.
7. For provider resource specs (sandbox CPU/RAM/region/disk), separate what our code sets explicitly from what falls to the provider default, then confirm against real instances: `mcp__vercel__list_named_sandboxes` on the ti-hiring project/team, reading the `ti-ses-*` entries (tag `ti-session`) for vcpus/memory/region/timeout/networkPolicy. Ignore untagged sandboxes (ad-hoc tests). Do not report the orchestrator's Fargate task cpu/memory as sandbox size.
8. For "link me the tests for X", classify each candidate: real-browser smoke against prod (`smoke/tests/`), orchestrator e2e over real HTTP + test DB but fake providers (`orchestrator/tests/e2e/`), unit, or docker harness (`sandbox/harness/`). Open stub files before citing them (e.g. `orchestrator/tools/smoke-real.ts` is an unimplemented stub). State which layer each link actually exercises; never call a fakes-based test end to end.

## "Did this candidate hit an old/stale deployment?"
Test the routing chain before accepting or rejecting a stale-deployment hypothesis:
1. Edge: `aws --profile trilogy cloudfront list-distributions` filtered on alias `<internal-host>`, then `get-distribution --id <id>` for origin + `LastModifiedTime`. The wrapper is CloudFront -> origin `ti-hiring.vercel.app` (no Vercel custom domain, so `list_aliases(domain=add.hiring...)` is empty by design; DNS has no CNAME).
2. Vercel: for each suspect deployment, `mcp__vercel__get_deployment` + `list_deployment_aliases` on team `team_OciwdTBwczi5C3DxiiwfnpT1`. A deployment with `target: null` and no aliases (CLI previews) is reachable only by its own hashed URL, so it cannot intercept the bare candidate link.
3. Re-verify "we already deleted those" claims: check `state`/`readyState` live; prior cleanup may not have landed.
4. Scope the conclusion: ruling out unaliased previews on the normal link does not rule out an old production wrapper build or an old orchestrator image at the candidate's session time; next check the candidate's actual URL (invite/transcript) and the ECS task-definition image sha + Vercel production deployment active at that timestamp.
5. Workspace-derived artifacts (`prompts.txt`, captured files) are generated from the candidate's workspace/conversation, so their content is a clue, not proof of which code version ran.
6. Vercel MCP pauses after 3 rejected calls; don't guess team/project ids (404s count), use the known team id above.

## Candidate-reported session problems (triage)
1. Locate artifacts fast: grep `/home/ubuntu/eval-cache-strong/<email>/` and `/home/ubuntu/eval-cache-all/<email>/` (`report.json`, `ledger.json`, `triage.json`) for the complaint text and session id; find the Drive folder with `gog --account ayushaggarwal018@gmail.com --readonly drive search 'ti-session-<session_id>'` (searching by email only hits sheets).
2. "Sessions" plural means check every session tied to the email before attributing a symptom to the one cached report.
3. Agent-side statements in the eval report (e.g. "workspace is empty") are paraphrase; confirm against the transcript, captured workspace tarball and provisioning logs before calling it a provisioning failure vs a normal assignment layout.
4. When the user reports a finding from their own review (recording checked, cause spotted), stop the overlapping subagent immediately and adopt their observation as the working hypothesis; don't keep re-verifying what they already looked at.
5. "Why was this session not captured / no Drive folder?": pull the full record in one call, `GET https://<internal-host>/v1/sessions/<id>/detail` with `Authorization: Bearer $(aws --profile trilogy ssm get-parameter --region ap-south-1 --name /ti/orchestrator/ADMIN_TOKEN --with-decryption --query Parameter.Value --output text)` (the `/v1/admin/sessions/<id>` path 404s). It returns the row plus `session_events`. `joined_at`/`sandbox_id` null + `end_reason=forfeited` means no web join reached the orchestrator before the start+10min cutoff, so nothing existed to capture. Then corroborate: `mcp__recall__get_bot` on `recall_bot_id` (`meeting_participants: []` = nobody joined the Meet either); startgreat Gmail search for the candidate's email (confirm the last invite's time/link and whether they replied); CloudWatch `/ecs/ti-orchestrator` filtered on the session id around the slot. State the boundary honestly: the record cannot distinguish "never tried" from "got stuck at sign-in before the join call"; ask for attempt time/screenshot rather than asserting a no-show.
6. Known interaction conflicts to check: Claude Code's own UI prompts "Esc to close" while the browser uses Esc to exit fullscreen (a counted proctoring violation, warned in `wrapper/src/components/terminal-client.tsx`); touchpad scroll can reach the terminal as arrow keys instead of scrollback. Separate the documented design conflict from proof the candidate actually triggered it.

## Architecture / module-boundary questions (e.g. stakeholder pushback on a diagram)
1. Read the current call chain at the deployed sha before proposing any restructure: who makes the single state transition (`handleJoin()` does `scheduled -> provisioning`), who coordinates vendors (`provision()` runs the sandbox create plus a Recall fallback dispatch; `prepareProctoring()` normally dispatches Recall at schedule time), where webhooks land (`routes-recall-webhook.ts` in the orchestrator). Proposing a "new top-level coordinator" that already exists wastes a round and erodes trust.
2. Separate two questions: (a) does one coordinator own the start attempt and its outcome (usually yes, and already true), (b) is the thing presented as an independent module actually independent (check its deps interface: `ProvisionDeps` carries store, Recall and sandbox, so `provision()` is the coordinator, not an isolated infra module). Pushback usually targets (b), the labels, not the flow.
3. Answer with the current-state fact first ("yes, it already works that way"), then the precise gap. Don't flip positions across turns; if an earlier answer overstated a needed change, say so in one line.
4. Name the lifecycle phase every proposal touches before arguing cost or scale: (a) advance booking at schedule time (session row, Meet, scheduled Recall bot via `prepareProctoring()`), (b) join-time provisioning (`handleJoin()` moves `scheduled -> provisioning`, then `provision()` creates the sandbox), (c) post-start work claimed by the lifecycle scheduler. A for/against list that doesn't say which phase changes reads as if sessions or sandboxes are created on the spot, and the user will correct it.
5. For "use the existing lifecycle scheduler for X?" weigh its real mechanics from `orchestrator/src/lifecycle/scheduler.ts` and `SessionStore.claimDue()`: Postgres-derived due set, `FOR UPDATE SKIP LOCKED` split across tasks, per-(session, action) claim stamps, failure backoff and restart self-healing, versus the `SWEEPER_INTERVAL_MS` cycle (default 15s) plus backlog/outage latency. Adding a new `DueAction` means a new UNION branch in `claimDue()` and a handler in `server.ts`.
6. For any per-session vendor call at a shared moment (cohort start), pull the live vendor quota before arguing peak load (`mcp__recall__list_rate_limits` with the exact path/method), then say plainly that the limit applies whichever trigger fires the calls; a different timer does not remove a vendor quota.

## Assignment data model (where an assignment "lives")
Three separate things, don't conflate them:
1. `sessions.assignment`: the selected slug for a booking.
2. `assignment_statements(slug, title, statement_md, updated_by)`: the candidate-facing `assignment.md` text shown in the app. This is what "we save the assignment in the DB" means.
3. Starter repository files: NOT in the DB. They live in pre-baked sandbox snapshots listed in `contracts/snapshots.json`, selected at join time by the tuple `(repoUrl, path, ref?)`. For `<org>/ti-hiring-assignments`, every snapshot shares one repoUrl, `path` equals the slug and `ref` is null. The infra service already validates the tuple against its snapshot map; candidate-start persists the tuple on the session row after the first attempt so retries replay it.

When the user asks "why does it look up X, isn't it in the DB?", first state which of the three the lookup is for. Then check whether a worker's new loader, catalog file or env var is actually needed: if DB slug + one known repo URL + path=slug is enough and infra already validates the snapshot, send the worker toward that minimal route instead of approving extra config or file paths.

## Answer shape
- Separate observed failures (test or live trace), deterministic code behavior and possible interleavings. Never present a reviewer's hypothetical concurrency race as a reproduced incident without a failing test or event trace; if evidence is absent, say so and stop treating it as an established blocker.
- When describing provider signals, state what the vendor actually reports and what our authenticated mapping persists. Do not invent a physical-device attestation requirement from a platform label unless the accepted product contract calls for it.
- Distinguish a code-chosen retry cutoff from a user-approved SLA and a provider's documented lead-time limit. Name which operation is retried and which ambiguous outcome must remain unresolved rather than saying only "retry/deadline."
- First line: the direct answer to the question asked (e.g. "It's an API call, not a DB change").
- Plain-language numbered flow, then a short table only if grouping helps.
- Surface any live-config finding that contradicts the intended design (feature not actually on in prod) prominently; it matters more than the design.
- Links as bare direct URLs pinned to the sha with line ranges, never embedded markdown links.
- One concrete next step at the end.
- When asked for arguments for and against, give the recommendation first, then a short For and Against paragraph each, grounded in the code and live limits pulled this turn.
- Scope blockers by owner: a gap in another engineer's component (e.g. how their editor URL is protected) is their concern, not a blocker on our work; record it on their side and unblock our card instead of listing it as ours.
- Answer the exact question; when the user asks only "how do we do X" (method), list the method and which existing credential/path it uses, do not propose building new infra.
