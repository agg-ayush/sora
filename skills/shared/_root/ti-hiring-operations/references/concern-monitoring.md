# Candidate concern monitoring

## Where concerns live
- Every concern lands in the DB as a session event and in the orchestrator's CloudWatch log group `/ecs/ti-orchestrator` as a `"endpoint":"concern"` line.
- `kind` values: `work_trouble` is the candidate-typed "I'm having trouble" form. `submission_concern` is either a real finish-page note or the wrapper's templated "Session ... hit an error: finalize failed" auto-report. Read the note before calling it a candidate concern.

## Enumerate across sessions (CloudWatch)
```
aws --profile trilogy --region ap-south-1 logs filter-log-events \
  --log-group-name /ecs/ti-orchestrator --start-time <epoch-ms> \
  --filter-pattern '{ $.endpoint = "concern" }'
```
Lines carry `sessionId`, `kind`, `length`, not the note text. In the console's "Search log group" box use the same `{ $.endpoint = "concern" }` form; a raw substring containing a quote is an invalid filter pattern.

## Get the note text (admin API)
- `GET /v1/sessions/:id/detail`: the concern event's top-level `kind` is null; kind and note are inside `detail_json`. Every POST appends a `concern_submitted` event, so the `events` array is the complete, append-only record.
- The row's `concern_kind` / `concern_note` are latest-value UI mirrors only. A later finalize-failed auto-report overwrites them and hides the candidate's earlier typed note. Always enumerate concerns from the `concern_submitted` events (one row per event), never from the mirror columns. Check the events before ever telling the user a note was lost or overwritten.
- `GET /v1/sessions/:id` shows `concernKind` / `concernNote` as null even when a concern exists. Never conclude "no concern" from the plain session GET.
- Setup-page "I'm having trouble" notes (including submit-and-exit from the media gate) land in the detail row's `setup_trouble_note`, not in `concern_note` or a concern event. Check `setup_trouble_note` before telling the user a candidate's note never reached the DB.
- Forfeited sessions (`joinedAt: null`) have no concern by construction.
- Trouble-exit (candidate submits the trouble form and leaves) shows up as a `trouble_exit` event (`detail_json` has `note` and `from`, e.g. `ready`), with `end_reason` `candidate_trouble` and the same text in `setup_trouble_note`.

## Triage a reply to a watcher ping
When the user replies to a TI concern / trouble-exit ping (asks for the Meet link, says what happened, etc.):
1. Resolve the full id first. Pings carry a truncated session id (first ~20 chars); `GET /v1/sessions/<truncated>/detail` returns 404. Pull `/v1/sessions?limit=500` via `/home/ubuntu/.local/bin/ti-hiring-admin.sh GET ...`, strip the trailing `[http NNN]` line before `json.loads`, and prefix-match on `id`.
2. The list row answers the common asks directly: `meetUrl`, `candidateName`, `candidateEmail`, `status`, `endReason`, `infraCapture`, `infraVideo.url`.
3. For "what happened", read the detail `events` timeline (joined, `candidate_joined_meet` with `platform`, mic/webcam/screenshare on, `media_gate_fail_open` with `missing`, `trouble_exit`, `sandbox_destroyed`) and state facts from it rather than restating the ping.
4. Always report the session's CURRENT status alongside the answer: the ping's status is a snapshot, and sessions often finish (`ended` / `candidate_done`, capture landed) by the time the user replies. Say whether work was captured, since that decides whether it is evaluable or a no-submission.
5. Offer the next action (reschedule vs leave as forfeit) only when nothing was captured; do not reschedule without the user saying so.

### "Wrong workspace" / "files don't match the instructions" concerns
Verify all four layers agree before answering, then say which layer (if any) diverges: (a) DB row `assignment`, (b) sandbox `state.env` `WORKSPACE_PATH` + `WORKSPACE_COMMIT`, (c) actual `/workspace` files, (d) the statement the wrapper served (`GET /v1/sessions/<id>/assignment`), checking every file the statement names exists. Recipe in `references/session-forensics.md` (Inspecting a live candidate sandbox). When all four agree, it is candidate confusion, usually because the assignments ship memos + spec + sample data with no starter code, which reads as "wrong/empty workspace" to someone expecting a code repo. Classify it as a candidate-confusion concern (alongside "how do I open claude" agent-discoverability questions), not infra, and offer a suggested reply rather than a fix.

### "Is this true?" checks (editor not opening, Claude slow/blank/not working)
Verify against evidence in this order, then give a verdict class: disproven, candidate-side, genuine (our side), mixed (state both halves), or unverifiable.
1. Detail events: entered time, gate fail-open `missing` list, rejoin churn.
2. Orchestrator CloudWatch `%<short-id>%`: join-endpoint retry storms and pane health probe failures point at the candidate link; a clean serving side plus retries means candidate network.
3. Claude transcript in the capture: prompt and response timestamps. Compare time-to-first-token with the cohort baseline before calling "slow" real.
   - Capture lives at `s3://ti-hiring-captures-<aws-account>/captures/ti-ses-<uuid>/ses_<uuid>.tar.gz`; the transcript is `.claude/projects/-workspace/<id>.jsonl` inside it. Read it with `tarfile` straight from scratch, no extraction needed.
   - Parsing: text lives at `record["message"]["content"]`, not top-level `content` (top-level is always None, so a naive parser finds zero turns). A real prompt is a `type:user` record whose content has no `tool_result` part and no `<system-reminder>`/`<local-command` text; `[Request interrupted by user]` marks a candidate abort. Assistant records carry no `promptId`, so segment turns by file order (every assistant record until the next real prompt).
   - A capture can hold several `.jsonl` files (one per Claude conversation, including near-empty 5-record stubs from an opened-but-unused panel). Merge all of them and sort by `timestamp` before segmenting. A low real-prompt count is not low engagement: IDE prompts start with `<ide_selection>` and one prompt can drive a long autonomous run, and messages typed while the agent is busy land as `queue-operation` records, so judge activity by the assistant-record span and count, not prompts alone.
   - Measure three things per turn: TTFT (prompt -> first assistant record), turn wall time, and tool_use -> tool_result gaps (tool name + command). Long tool gaps (Bash timeouts at 120s, multi-minute test runs) look like a frozen panel to the candidate even though Claude is fine.
   - Line the `concern_submitted` timestamp up against these gaps: a concern filed seconds after a multi-minute TTFT or test run pins what the candidate reacted to. Also note prompt sizes; large pasted prompts (several thousand chars) drive minute-plus TTFT.
   - Verdict shape when the agent kept producing work but with minute-scale TTFT or long tool runs: "genuine symptom, not an infra failure" (prompt-shape and test-runtime driven). Back it with counts (assistant records, files written, last activity time) so it is not just disproven or blamed on our side.
4. Panel watchdog diagnostics, stored at teardown to `s3://ti-hiring-captures-<aws-account>/diagnostics/ti-ses-<uuid>/ses_<uuid>/claude-panel-events.log`, with `editor-logs.txt` (code-server.log dump) alongside (live sessions: read it inside the sandbox). Both path segments keep their prefixes; a bare `<uuid>` second segment 404s, so list the `diagnostics/ti-ses-<uuid>/` prefix when unsure. A `reload notice dismissed` line means the candidate closed the reload-editor notice and the ladder restarted; the ladder repeats for as long as the candidate keeps dismissing, so many dismiss cycles on one host are a churn loop, not a window that gave up. Expected lines: `editor window started`, `panel not loaded after 90s, reloading the panel`, `panel loaded after the reload, Ns`, or the ~230s notice plus editor reload. No prefix plus orchestrator log `no claude panel events` means the log was empty and the watchdog never armed: it arms on panel-session start, not editor open, so a candidate whose panel never loaded (or was never opened) and who fell back to terminal Claude gets neither the 90s reload nor the notice. Report that as a watchdog coverage gap.
   - Live session still stalled: re-read the live `events.log` about 60s later (and again after the ~90s/210s marks) instead of reporting a snapshot. The candidate often recovers via the watchdog ladder while you check; report the full timeline (window started, reload, notice, editor reload clicked, `panel loaded after Ns`) plus current Claude state (`ps aux | grep -c '[c]laude'`, session `.jsonl` under `/home/vercel-sandbox/.claude/projects/-workspace/`).
   - Connection stability: count `reconnected|disconnected` lines in `/opt/ti-hiring/log/code-server.log`. Zero to two cycles with healthz OK means a stable candidate link, so a slow first load is the load itself, not their network; repeated cycles point candidate-side.
   - Time-to-first-editor: compare the detail `entered` timestamp with the first `ExtensionHostConnection ... New connection established` line in `code-server.log`. This gap (often 3-9 min on the slow tail) is a separate leg from the panel load in the watchdog log; report both. Concerns filed shortly before that first connection are "genuine in the moment" even when the sandbox was ready in seconds.
   - If the watchdog shows `editor window started` with no load line yet, wait ~60-75s inside the same check and re-read before answering, so the reply carries the outcome rather than a snapshot.
   - Watchdog lines are tagged `host=<pid>`, one per editor window, and windows interleave. Group lines by host and judge recovery by the newest host: an old window still escalating (90s reload, 210s notice) while a newer host shows `panel loaded after Ns` plus a Claude session `.jsonl` means the candidate is working. Print the full log tail per session, never a fixed-width truncation; a cut line hides whether the last host loaded, and a recovery claim must rest on a visible `panel loaded` line or a session `.jsonl`, not a bare process count.
   - Zero watchdog lines and zero `New connection` lines in `code-server.log` 10+ minutes in means the browser has not reached the editor yet, not a confirmed loss. Do not call it a casualty or a structural gap while the session still has time: report it as "not connected yet", re-check every couple of minutes, and only classify as a hard failure if the session ends with no editor connection (the never-loads class). On the slow tail, first connection can land 13-16 min after entry and still recover in under a minute.
   - "How many still stuck vs solved?" follow-ups: re-run the same per-session loop over every complainer and answer as a split (solved with evidence per name, still stuck with what is missing), with the check time in UTC.
- Verdict class for this shape: "genuine but transient, recovered" (slow first load, then panel loaded and Claude running). State current Claude state as proof of recovery, and keep it distinct from "disproven" and from hard failures where the editor never loaded.
- Running tallies across replies: recount the named cases each time before quoting "N for N"; a mismatched count next to a list of names undermines the whole verdict.
5. Proctor recording frames only after `recording_ready`: download to scratch, extract frames for the disputed UTC window, and have a delegate_task subagent read them. Never assert panel state from frames where it is obscured; confirm with step 4.
- An `s3 cp` failing with empty stderr can be an expired SAML token; list the prefix to see the `ExpiredToken`, run the aws-creds-refresh script and retry.

### "Did it work for everyone else?" batch sweep
When the user forwards one ping and says "these issues" (plural), first scan every live session's detail for `concern_submitted` events in the last few minutes and check all fresh complainers in one pass, rather than only the forwarded id.
When several candidates in one batch complain, sweep EVERY live session in that batch, not just the complainers, so the verdict is a split (e.g. 11 fast / 3 stalled) rather than an anecdote. One read-only loop per session: watchdog `events.log` (panel load seconds, any reload/notice lines), Claude process count plus session `.jsonl` presence, reconnect-cycle count. Report load-time distribution and how many needed the watchdog; a bimodal split (seconds vs minutes) is the useful signal for bootstrap/asset work.
- ID pitfall: session ids are `ses_<uuid>`, sandbox names are `ti-ses-<uuid>`. Prefix-match each against its own kind; matching a `ti-ses-` prefix against the live session list returns nothing and looks like "everyone already ended". Before reporting sessions ended, re-check `/v1/sessions?status=live` and compare against their `endsAt`.
- Ended sessions: their watchdog log is in the S3 diagnostics path above, keyed by the full sandbox id and session id from `/v1/sessions/<id>/detail`.

### Day-wide "what happened with the Claude complaints?" sweep (ended sessions)
When the user asks about Claude complaints generally (plural, after the batch), answer for the whole day, not just the forwarded ping:
1. Enumerate concern sessions via the CloudWatch filter above from 00:00 UTC, pull `/detail` per session id, read every `concern_submitted` note from `detail_json`, and filter with a word-bounded regex (`\bclaude\b|\bagent\b|\bAI\b`). Read each hit: guidance questions and praise also match and must be listed separately as not-complaints.
2. Per complainer, run the transcript check (step 3) and the watchdog log (step 4). Sort into classes: panel reload churn with prompts answered in seconds (genuine UI symptom, backend fine, work not lost); panel never loaded on the main window plus zero transcripts (genuine hard failure, ours); slow TTFT from prompt shape or long tool runs.
3. Silent-cohort check: list rows carry `infraCapture.transcriptFiles` and `infraCapture.bytes` on some API versions; when the list row has no `infraCapture` key, the same facts are on `/detail` as `infra_capture_transcript_files` and `infra_capture_bytes` (plus `transcript_stats` JSON with per-file minutes and messageCount). Among joined sessions (`joinedAt` set, smoke and `@<org-domain>` excluded) ending `candidate_done`/`timer`, `transcriptFiles == 0` with a starter-only capture (under ~15 KB) is the "Claude never ran" shape, whether or not the candidate complained. Report the count against total joined.
4. Cross-tab that cohort by `assignment`: an even spread rules out one broken snapshot; a cluster on one assignment points at that snapshot. Present the cohort as a lead needing a sampled frame/watchdog check, not a confirmed defect, until spot-checked.

### Multi-day "which complaints are on our end?" triage
When asked to go through all concerns over a window (e.g. last 48h) and separate technical/our-side from candidate-side:
1. Enumerate from the admin alert stream (`GET /v1/admin/concerns?limit=100&after=<cursor>`, paged) when the CloudWatch `concern` filter comes back empty for a window that is known to contain concerns; the stream carries the session id and note text, so it removes a per-session detail fetch just to read notes.
2. First-pass classify every note by reading it (keyword buckets only shortlist): candidate-side (network, screen-share/media confusion, wanting more time, privacy questions, workspace confusion, praise, notes about their own approach) vs suspect (editor/Claude refreshing or not loading, broken env such as missing pip/ports/repo late, agent slow). Report both counts against total joined sessions in the window so the scale is clear.
3. Pull `/detail` once per suspect and pickle it to scratch so later passes do not refetch. Detail `events` records are `{ts, event, detail_json}`: the event name is in `event` (not `kind`), and `detail_json` is a JSON string to parse with `strict=False`.
4. Cheap signals from detail before any S3 download:
   - `infra_capture_bytes` under ~12 KB with `infra_capture_transcript_files == 0` is the hard-failure shape (Claude never ran).
   - `editor_timing` events fire on every editor page load (`reason` `ready` / `pagehide` / `timeout`); many in one session (5-12+) corroborates "refreshed again and again", a `timeout` reason marks a load that never became ready, and runs of `pagehide` mean the page kept being torn down.
   - Line up `concern_submitted` timestamps against `entered` and the `editor_timing` burst.
5. Fan the deep check (watchdog log, editor-logs, transcript TTFT per steps 3-4 above) out to parallel `delegate_task` subagents, ~5-6 sessions each, each given a per-batch profile JSON in scratch and told to write `verify_batch<N>.md` and return a per-session verdict from the fixed class list. Re-verify any striking claim before relaying it.
6. Final report: our-side confirmed / our-side recovered / candidate-side / mixed / unverifiable, one line of evidence per candidate, plus the candidate-side bucket summarized by type.

### Root-causing "Claude keeps refreshing / my prompt got deleted"
This symptom is the panel watchdog ladder itself firing, not the browser: the 90s panel reload recreates the webview and wipes any typed-but-unsent prompt. Root-cause it in this order:
1. Read the shipped mechanism from source, not memory: clone `<org>/ti-hiring` to scratch and read the watchdog extension plus `bin/claude-panel` in `sandbox/provision.sh` (the panel counts as loaded only when `claude-panel` touches `started/<extension-host-pid>`). Confirm the source matches what ran by comparing the provision sha against the baked snapshots' `provisionSha256` before explaining behavior from it.
2. Quantify per session from `claude-panel-events.log`: windows (`editor window started`), panel reloads (`reloading the panel`), notices (`asking to reload the editor`), dismissals (`reload notice dismissed`), editor reloads clicked, and `panel loaded` per `host=`. Many reloads plus dismissals on a host that never loads is the churn loop; a sibling host loading in seconds rules out a broken sandbox.
3. Separate the causes of the never-loaded panel using `editor_timing` beacons:
   - `net` (`type`, `rtt`, `downlink`) is the candidate's own link. A 3g / sub-1 Mbps / several-hundred-ms RTT link cannot fetch the ~6 MB panel script inside the 90s budget, and each reload restarts the download, so the watchdog turns slow into impossible (mixed verdict: candidate link, our ladder).
   - Count beacons vs windows: a window with no `ready` beacon never reached `code/didHandleExtensionPoints`. A large `nav.ttfb` on one beacon marks a slow page request for that load.
   - Fast workbench marks (ready in ~1-3s, low ttfb) plus a good link and still zero `panel loaded` across every window is a panel-side failure the stored diagnostics cannot explain, because `editor-logs.txt` excludes extension logs. Report it as unexplained with that diagnostics gap named; do not guess a cause.
   - `ptyHost terminated unexpectedly` in `editor-logs.txt` is a separate code-server crash class that also reads as "the editor reloaded".
4. Check whether a recent change amplified it: `git log -- sandbox/provision.sh` around the snapshot bake date, then bucket refresh/reload-type concern notes by day across the full concern history. Call out confounds (tiny cohorts on some days) instead of claiming a rate change from raw counts.
5. Report the confirmed mechanism, the per-cause split with per-candidate counts, what is unverifiable, and the fix directions (cap the ladder, link-aware budget, capture extension logs) as options, not as decided work.

### "Keep tracking all the live ones"
When the user asks for ongoing tracking during a batch, run a bounded tracker instead of answering ping by ping:
1. Each poll (every ~2-3 min) re-scan EVERY live session of the day for `concern_submitted` events and add new complainers to the tracked set. Never hardcode the session ids known at launch: a fixed list silently misses the next complaint, and claiming "it catches new concerns" when the script cannot is a false coverage claim.
2. Per tracked session log: candidate name, `ENDED` when it leaves the live list, the newest-host watchdog lines (full, untruncated) and Claude process count plus session `.jsonl` presence.
3. Stop a few minutes after the latest `endsAt` in the cohort. Launch via the terminal tool with `background=true, notify=true` so its exit triggers the final tally; a silent background run means the promised end-of-cohort report never happens.
4. Final report: per candidate, solved (with evidence and recovery time) / still stuck / never connected, plus any concerns that arrived during tracking, with the check time in UTC.

### Escalating repeat concerns
When one candidate files several escalating concerns within minutes ("not opening" -> "12 minutes gone" -> "please help"), report the infra verdict and separately flag that nobody visibly answered the concern channel during that window. That is a staffing/process gap for whoever monitors concerns, distinct from the infra cause, and it belongs in the reply rather than buried.

## Exporting a concern/trouble-note table (e.g. to a gdoc)
- No single endpoint has every column. The session list endpoint lacks `setup_trouble_note` and concern text; `/v1/sessions/:id/detail` has the note and `recall_bot_id` but not `candidateEmail` / `meetUrl` reliably. Pull detail per session id for note + recall id, then join email and Meet link from the list response by session id. Check the first rendered row for `?`/empty email before writing the doc.
- "All concerns across the board" means one table merging both channels: every `concern_submitted` event (kind + note from `detail_json`) and `setup_trouble_note` (kind shown as "trouble note"), scanned over every session of the day via detail. Exclude by default: the templated "Session ... hit an error: finalize failed" `submission_concern` auto-reports (internal errors, not candidate text) and operator test sessions (`@<org-domain>` emails). Say how many were excluded and why.
- Build the table as markdown, create a fresh doc (`gog docs create <title>`), push with `docs write --replace --markdown --file <md>`, then `docs cat` to verify rows. Default columns: session, candidate email, status, recall bot id, Meet link, note. Escape `|` and newlines inside notes.

## Channels to watch
Filter CloudWatch for all three endpoints: `concern`, `trouble-note` and `trouble-exit`. Watching only `concern` misses setup-page trouble notes.

## Telegram watcher
- The watcher (`/home/ubuntu/.hermes/scripts/ti-concern-watcher.py`, ticked every minute) polls the admin alert-stream endpoint `GET /v1/admin/concerns?limit=100&after=<cursor>` plus a session-list pass for `ready_expired*` endings, and sends to the TI Hiring group via `hermes send -t telegram:<group id>`. Cursor lives at `/home/ubuntu/.hermes/state/ti-concern-cursor.json`, so restarts don't re-ping old events. Read the script for the current group id rather than assuming.
- Preferred runner when people should be able to reply/tag under alerts: a systemd user service (`ti-concern-watcher.service`, `Restart=on-failure`, `RestartSec=30`, enabled at boot) running a bash loop that calls the tick every 60s and sends via `hermes send -t telegram:<group id>`. It survives session end and parent-process cleanup. Remove any cron copy when switching so alerts don't double-deliver. Operate with `systemctl --user status|restart ti-concern-watcher`; log at `/home/ubuntu/.hermes/logs/ti-concern-watcher.log`.
- systemd unit pitfalls: `ExecStart` must invoke `/bin/bash` for a shell loop (pointing it at python3 crash-loops on SyntaxError), and the unit env has no `hermes` on PATH, so call the venv's absolute `hermes` binary and set a full `Environment=PATH=...`. A quiet tick still exits 0 with a broken PATH, so the failure only shows on the first real alert. Prove the delivery leg under the unit's exact env: `env -i HOME=/home/ubuntu PATH=<unit PATH> <abs hermes> send -t telegram:<id> "<test>"` must print `sent`. (`systemd-run --wait --pipe` only shows resource stats, not the command output.)
- Never hardcode a `/home/ubuntu/.hermes/installs/<hash>/...` hermes path in the watcher (or any long-lived script): the hash changes on every `hermes update` and the first alert after it crash-loops with FileNotFoundError while the cursor stays stuck, silently holding every new concern. Hit on 2026-11-01: two same-hour concerns went undelivered for ~30 min while the loop looked alive. Resolve the binary at call time (`shutil.which` → `~/.local/bin/hermes` → glob the installs tree); `~/.local/bin/hermes` is the stable path.
- Alternative runner: a Hermes cron job in no-agent mode (`every 1m`, `deliver: telegram:<group id>`). Always give the explicit chat id: a bare `deliver: telegram` resolves no target and every run reports "result was not delivered"; check `hermes cron list` for that warning after setup.
- Other group members can only talk to the bot if they pass the gateway allowlist: by default it denies everyone not in `TELEGRAM_ALLOWED_USERS` (or paired), so the bot answers the owner and silently ignores teammates in the same group. Fix by adding the teammate's numeric Telegram user id to `TELEGRAM_ALLOWED_USERS` and restarting the gateway, or have them DM the bot and approve with `hermes pairing approve telegram <code>`. Group session routing keys also include the sender's user id (`agent:main:telegram:group:<chat>:<user>`), so each member gets their own session in the group. Allowed non-admins can chat freely; slash commands need the group admin split (`group_allow_admin_from`).
- No-agent mode delivers ANY stdout to the chat, so the script must print nothing on a quiet tick (guard the summary log line with `if delivered or gate:`). A per-minute "delivered 0" line spams the group. Run the script once by hand after every edit: a clean quiet tick prints nothing and exits 0.
- The `/v1/admin/concerns` stream carries both `concern_submitted` and `trouble_exit` kinds, so trouble exits need no extra wiring; format them distinctly (from-state plus late/on time).
- If running as a raw process instead, launch it only via the terminal tool with `background=true`. `nohup` / `setsid ... &` from a foreground terminal or execute_code call is reaped when the call returns, so the watcher silently never runs.
- Keep the watcher script and its cursor file at a durable path (e.g. under `/home/ubuntu/ti-hiring-ops/`), never in the Hermes scratch dir: scratch entries idle 24h are pruned, so the process keeps running from memory with its source gone and can't be inspected, fixed or restarted.
- After launch, verify with `ps` plus the log's start line before reporting it's up. Also confirm the delivery leg actually exists (a Telegram send in the script, or a cron `deliver: telegram:<id>`); a watcher that only writes its own log pings nobody.
- Before a batch, health-check any watcher still running from an earlier batch: tail its log for the same session repeating (a stuck cursor) and for empty note text, and restart it from the durable source rather than trusting it.
- When asked whether a watcher/alert path is still live, report only what was verified (process alive, script present, delivery target, last real ping); do not assert an SNS/alarm path delivers to Telegram without checking the subscription.
- Dedupe to one ping per session per channel: the `trouble-note` endpoint is an autosave that logs roughly once a second while the candidate types, so a per-line ping floods the group. Fetch the latest note text for the ping instead of pinging each autosave.
- When an alert was missed, check whether the watcher process was alive over that window before debugging filters.

## Documenting the watcher for others
When asked for a doc on the watcher (or any ops script), write a plain-language main tab (what it watches, how it works, auth, failure behavior, operating commands, known limits) and put the full script source in a second tab (`gog docs add-tab`, then `docs write --tab <title> --markdown`). Readers outside the box cannot see local scripts, so the source must live in the doc.

## Media-gate expiry alerts
- A candidate dying at the media gate is not a concern event; it is a session ending with `end_reason` `ready_expired_*` (the sweeper also logs warn `"ready ttl expired with the media gate closed"` with `reason` `media_gate_blocked` / `media_gate_not_satisfied`).
- Watcher leg: each tick, list sessions via the admin API, take rows whose `endReason` starts with `ready_expired`, and ping only ids not in a seen-marker file. On first run seed the marker with every existing expiry without paging, or the group gets flooded with historical batches.
- AWS-native leg (pattern the existing alarms use): log-metric filter on `/ecs/ti-orchestrator` -> metric in namespace `TIHiring` -> alarm. CLI gotchas: `--metric-transformations` keys are lowercase (`metricName=...,metricNamespace=...,metricValue=1`) and `put-metric-alarm` needs `--evaluation-periods`. A new log-metric alarm sits in INSUFFICIENT_DATA until the first matching line; that is normal.
- Check the alarm's SNS topic has a subscriber before calling it a page path; the concerns topic has had none, so Telegram via the watcher is the real delivery.

## Email alarms
SNS email subscriptions on the concern alarm get auto-unsubscribed by the corporate mail gateway's link scanner (it follows the unsubscribe link), so users see only deactivation mails. Use Telegram as the primary push channel.

## Telegram group id
Forwarding a message to an id bot returns the forwarder's user id. Add an id bot (e.g. @getidsbot) to the group itself to get the negative group chat id.
