# Reviewing a cohort's eval reports (filter + viewer)

Use when the user wants a college cohort's candidates filtered by their transcript-eval results and shown for review. Viewer mechanics (which version lists, how to run it) are in `references/eval-review-viewer.md`.

## Procedure
1. **Define the cohort from session data, not the sheet's verdict column.** The cohort sheet may carry a hand-filled eval-result column for only a subset. The real set is every session for that cohort, plus manually appended rows at the bottom of the sheet. Confirm the count with the user if it looks small.
2. **Fetch reports from GCS** (bucket `<gcs-bucket>`, one `report.json` per `<session>/<assignment>`). If the gcloud/gsutil CLI wants interactive re-auth, use the transcript-eval repo's own node GCS client (`NODE_PATH=<repo>/transcript-eval/node_modules node script.js`) instead of asking the user to auth. Run the download as a background job with notify. Never block on long sleeps or long foreground timeouts.
3. **Default rule: per signal, take the best of the two eval blocks.** Each report has `focused.findings` and `combined.findings`, and they can disagree per candidate. The user's rule: each signal = best(focused, combined), ranked `shows` > `mixed` > `not_exercised` > `does_not_show`; a candidate passes when all three signals are at least yellow (`mixed`). Render the chips on the filtered page from the same best-of values, not the viewer's `combined`-only chips, and state the rule on the page in one plain line so a cold reader knows why each candidate is there.
4. **Filter on the three signals** (`problem_ownership`, `question_quality`, `advice_seeking`). When reporting the set, name who entered or left versus the previous rule.
5. **Always include candidates the user names explicitly**, even if outside the filter. Tag how they differ (e.g. "1 of 3 yellow") instead of dropping them.
6. **Serve the set, don't paste it.** Layout the user settled on: the **filtered list on 8787** (the front door) and the **newer ID-scoped viewer on 8788** (the one that opens from `?candidate_id=&assignment_id=`). Build the filtered page so it reads the local report cache itself (glob `<cache>/ses_*/*/report.json`, compute best-of chips) rather than proxying the viewer's `/api/runs`: the newer viewer's `/api/runs` returns 400 without both id params and has no list-all mode, so a proxying page breaks the moment the viewer is swapped. Render name/email/assignment/signal chips with each name linking into the viewer. Link format depends on the viewer version: the list-capable version opens a run from the URL hash (`http://<host>:8788/#<session>/<assignment>`) and ignores query params (a `?candidate_id=` link lands on the empty drop-files screen); only the newer ID-scoped version takes `?candidate_id=&assignment_id=`. Grep the viewer's `index.html` for `hashchange` / `URLSearchParams` to confirm. Verify with curl: row count, names, chip values, the link format, and that `/runs/<session>/<assignment>/report.json` serves.
7. When the user's local agent should host it, give one paste-ready ssh tunnel line (the newer viewer binds 127.0.0.1 only, so forward 8788 as `-L 8788:127.0.0.1:8788`) forwarding both ports plus the URL to open, not a viewer command to rerun locally.

## Pitfalls
- Truncated session prefixes in a handoff are useless to another agent. Resolve full ids from the report paths first.
- Report layout is `<cache>/<session>/<assignment>/report.json`; glob `<session>/*/report.json`, not `<session>*/report.json`.
- In `gcp` mode, reviews written in the viewer save back to GCS. Tell the user.
- Before swapping ports, kill the old process and confirm the port is free (`ss -tlnp`); `pkill -f` can match and kill your own shell command, so run the check in a separate call.
