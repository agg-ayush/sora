## Candidate communication rules

- **Never say "session" to a candidate.** Candidates don't know the internal term. Say "your assessment" or "your interview". "Session" is fine in internal notes/sheets only.
- **Every candidate schedule email must restate BOTH parts**, even if only one part's time changed: (1) Project Deep Dive / VVA — proctored AI interview, ~20 min, link `<internal-host>`, well-lit room + headset; (2) Technical assessment / ADD — ~30 min live coding, link `<internal-host>` + a Meet link, join-by time, camera/mic/screen-share on. A candidate treats this email as their single source of truth for the whole day — omitting the unchanged part reads as incomplete and draws a complaint, even if that part's time truly didn't move.
- **When asked to "send the same mail" or match an earlier template, retrieve the actual prior sent email from the Sent folder and reuse its exact structure** (search `in:sent subject:...`, pull the full HTML body) rather than reconstructing the two-part format from memory. Reconstructing from memory drops sections (this is exactly how the VVA half got dropped once).
- **Don't assume a candidate's "yes"/"confirm" reply confirms every part of a multi-part proposal.** Read the reply literally — a candidate replying to a 2-slot proposal may confirm only one slot, decline, or say something ambiguous ("I already gave..."). Classify each of the multiple pending replies individually before acting on any of them.
- **When offering a reschedule to several candidates in the same batch, give them all identical slots** (not per-candidate negotiated times) — simpler to track and matches how the batch actually runs.
- **Don't narrate fault.** If an issue is the candidate's own doing (wrong platform, own account error), the reschedule offer should be neutral — no "we're looking into it" or apology implying our side broke something.
- **Never send a candidate-facing decision/disposition email (accept/decline/outcome) without the user's explicit go-ahead on that specific email, every time.** A prior approval to send a similar email to a different candidate does not extend to the next one — draft it, show it, wait. This is a hard gate, not a default-to-send workflow.
- **Before sending any email whose content is based on reviewing a specific candidate's recording/transcript, re-run the session-id → candidate-email lookup fresh, immediately before sending.** Don't rely on a session id you mentally mapped to a name several turns earlier — re-verify it every time right before the send action. A stale mapping sends the wrong verdict to the wrong person, which is not recoverable by apology once delivered.
- **When previewing a candidate email for the user before send, render it as a Google Doc (`gog docs write --replace --markdown`), not raw HTML source or a screenshot of an ad-hoc HTML file.** The user reads the doc directly; this is faster and more reliable than opening HTML in a browser to screenshot it.
- **When the user is iterating on copy (multiple rounds of "cut this line", "split this sentence", "too long now"), keep writing every revision into that same doc tab (`gog docs write --replace --markdown --tab "<tab>"`) — never paste the draft back into chat/terminal for them to read.** The user has said explicitly he doesn't want to read drafts in the terminal; a full edit loop (draft → feedback → re-edit → feedback) all happens through the doc, with your chat reply only summarizing what changed.
- **Expect a tighten → re-bloat → tighten cycle when merging several requirements into instruction bullets, and resolve it by cutting redundancy, not by re-splitting.** Combining related requirements into one bullet can read as a run-on and get flagged ("3 things in 1 sentence"); splitting them into separate bullets fixes that but can then read as too long overall. The fix at that point is not to re-merge — it's to drop whatever a bullet restates that's already stated elsewhere (the duration in the section header, the deadline covering timing, the brief page covering detailed rules) rather than exhaustively enumerating every requirement as its own line.

- **Before claiming a line is or isn't in the template doc, `gog docs cat <id> --all-tabs` the live doc and grep it — never answer from the local markdown source, the doc's comment threads, or memory.** Reviewer comments quote text that may already be gone or never existed in the body, and the local source can drift from what was last written; the user checks the doc itself and a wrong "it's not there" costs a correction round.
- **Apply every copy edit to BOTH the template (source markdown copy section + its HTML block) and any filled per-recipient HTML, then resend, in one pass.** Edit the source, full-replace the doc, re-cat to verify, patch the filled HTML the same way, send. Offering to sync the other copy afterwards is a wasted round trip.
- **"Make the timings bold" means the whole schedule line as one unit, zone included** (`<strong>Wednesday, 1 October 2026, 7:00 - 7:30 IST.</strong>`), not each placeholder value wrapped separately. Piecewise bolding leaves the date separators and "IST" regular weight and reads as broken.

- **Never use an em dash anywhere in candidate-facing copy (subject, body, bullets) - this is the user's standing global writing rule, not specific to the rules-narration point above.** Replace with a comma, colon, or period, or split into two sentences. Sweep the rendered HTML/plain-text AND the source doc tab for `&mdash;`/`&ndash;`/literal em/en dash characters before a final send; a time range ("6:00 - 6:40 PM") should use a plain hyphen, not `&ndash;`.
- **To center the whole email as a block on the page while keeping the text inside it left-aligned (the user's preferred layout, not centering every line), use a `<table role="presentation" width="100%"><tr><td align="center">` outer wrapper containing a fixed-width (e.g. 560px) inner table whose cell has `text-align:left`.** This is the reliable cross-client pattern (plain CSS `margin:auto` on a div is not universally respected by email clients); don't center-align the text itself when asked to "center the block."

## Candidate-facing copy: where it lives, and how to verify a change

- **There is no invite/scheduling email template anywhere in the repo — but there IS a maintained master template as a Google Doc, check it before assuming you need to hand-compose or Sent-folder-archaeology your way to the copy.** Confirmed exhaustively: `orchestrator/src/providers/notifier.ts` is internal alerts only, and no docs/README in-repo carry email copy. The orchestrator's own Calendar/Meet invite (`orchestrator/src/providers/meet.ts`, `events.insert`) carries ONLY a `summary` title (`"TI Assessment: <name>"`) — no `description` field is ever set, so the auto-generated Google Calendar invite email has zero instructional content. The actual two-part (VVA/Deep-Dive + ADD/technical) scheduling email — subject line, placeholders (`{candidate_name}`, `{deepdive_datetime}`, `{assessment_datetime}`, `{duration_minutes}`, `{join_deadline}`), and the full Do/Don't-style instructions — lives in a standing Google Doc the team edits directly and reuses across every batch (ask the user for the current doc id/link if not already given in-session; it is NOT the same as a specific candidate's Sent-folder copy). Edit that doc in place for a copy change, don't treat "no template in the repo" as license to draft one from scratch each time. The ONLY in-repo candidate-facing text for the assessment itself is the briefing page (`wrapper/src/app/session/[id]/page.tsx`, the Do/Don't grid + "Before you start" list), plus `candidate/intro.md` and `assignments/GUIDELINES.md`.
- **Before letting candidate-facing copy claim an agent capability (e.g. "the agent has internet access, use it freely for research"), verify the actual mechanism, don't assume egress being open implies every tool works.** The candidate sandbox's `ANTHROPIC_BASE_URL` points at the Fireworks gateway, not Anthropic directly — Claude Code's native `WebSearch` tool calls Anthropic's own search backend, which the Fireworks gateway does not serve, so it likely fails even though the sandbox has unrestricted outbound egress (`"*": []`) and Claude Code runs unpermissioned (`--permission-mode bypassPermissions`). `WebFetch` (fetching one already-known URL) rides on plain HTTP egress and works regardless of backend; `WebSearch` (querying) does not. Check `ANTHROPIC_BASE_URL` (`aws ssm get-parameter --name /ti/orchestrator/ANTHROPIC_BASE_URL --with-decryption`) and test the actual tool on a live sandbox before shipping copy that promises "research"/"search" capability — don't infer it from open-egress or bypassed-permissions alone.
- **A task phrased as "update the instructions" can mean the invite email doc, the briefing page, or both — they are separate surfaces that can be independently in flux (e.g. a live violation-policy redesign changing the briefing page while the email is untouched).** Ask which surface before drafting anything; don't default to whichever is easier to grep for. When the scope is confirmed as email-only, deliver ready-to-paste copy for that doc and leave the repo untouched — don't re-search the repo for a template file that doesn't exist.
- **When rewriting instruction copy to match a policy change (e.g. block-in-place violations instead of terminate-on-strike), strip mechanism/consequence narration and state the rule plainly** — "Stay on the assessment tab" not "switching away ends the session" or "pauses until you disconnect" — per the user's standing instruction that rules lists state the rule only, never the enforcement mechanism. This applies to timing mechanics too: don't state when a countdown/timer arms ("the timer starts when you click Continue") in candidate copy if the brief page already discloses it elsewhere — it's redundant detail, not a rule the candidate needs restated in the email.
- **The per-candidate Meet link can be embedded directly in the invite email body, not left to arrive only via the calendar invite.** `POST /v1/sessions` (session creation) triggers the Calendar event insert with `conferenceData`, which generates the Meet link at schedule time — so by the time you're sending the instruction email (after scheduling), every candidate's real `meetUrl` already exists and can be merged into the email as `{meet_url}`. Don't default to "the invite carries the link, the email just points at brief/assessment URLs" — ask whether the email should carry the link too, since embedding it removes a hop for the candidate.
- **The Google-Doc preview covers copy iteration; it does NOT tell you how the email will actually render in an inbox (bold, bullets, clickable links, HTML vs plain-text fallback).** Once the copy is settled and before a real batch send, send an actual test email to the user's own address so he sees the real rendering, not the doc's rendering. Procedure: (1) mint a throwaway session (`npm run create-session -- --email <test-address> --name "..." --at <UTC time> --duration-minutes <n>` in `orchestrator/`) purely to obtain a real `meetUrl` — GET `/v1/sessions/{id}` and read `meetUrl` once it's past `scheduled`; (2) fill every placeholder (`{candidate_name}`, `{assessment_datetime}` converted to IST, `{meet_url}`, `{join_deadline}`, `{duration_minutes}`) with concrete preview values computed the same way the real batch will compute them; (3) write BOTH a plain-text body and an HTML body (`<strong>` for section titles, `<ul><li>` for bullet lists, `<a href>` for links — a bare plain-text send reads as flat and undersells the real formatting); (4) send with `gog gmail send --account <ops-mailbox> --client startgreat --to <test-address> --subject "<subject>" --body-file <plain.txt> --body-html-file <email.html>` — passing both in one call sends a real multipart message so the client's actual HTML rendering path is exercised, with the plain text as fallback. `--subject` is a separate flag; strip any leading `Subject:` line out of the body content first. Destroy the throwaway session afterward (`/override {"action":"force_destroy"}`) so it doesn't linger in batch/count queries.
- **Before editing the briefing page's Do/Don't list, confirm the proctoring media-gate logic lives in a SEPARATE file** (`provisioning-continue.tsx` — the 5-signal joined/camera/mic/screenshare/recording gate) from the copy (`page.tsx`). A copy-only task should touch zero lines of the gate file; `git diff --name-only origin/main` before committing and confirm the gate file isn't in the list.
- **To verify a candidate-facing copy change actually renders the intended text**, beyond whatever the existing test suite already asserts, write a scratch vitest file that mocks the page's data dependencies and calls `renderToStaticMarkup` directly on the async Server Component, then check the plain-text output (unescape `&#x27;`/`&amp;`) for the exact strings — see the Next.js Server Component recipe in `pr-verification-audits` skill's `references/fix-verification-audit.md` ("Live-probe where feasible"). Delete the scratch file after. This is independent evidence beyond the committed test assertions, and it also confirms new copy landed inside an EXISTING list/section rather than a new one (relevant when a test elsewhere asserts a structural count like an exact number of `<ul>` elements on the page).

## Candidate error-report triage

When a batch of candidates emails in with errors around a scheduled start time, don't assume an engineering bug — most reports resolve to one of three known states, checkable via `/v1/sessions/lookup?email=` + `/v1/sessions/{id}/detail`:

- **"No assessment shown" / blank page after sign-in"** — almost always a **forfeited** session (`status=forfeited`/`terminated`, `end_reason=forfeited` in events): the candidate joined after the join window (default 10 min past `scheduled_start_at`) closed. This is expected behavior, not a bug. Check status before writing it up as an outage; a cluster of these around one batch's start time is the join-window ticking, not a regression.
- **"Session ended / it froze and I didn't do anything wrong"** — check the session's events for `tab_hidden` count and `strike_count`. `TAB_STRIKE_LIMIT` is 2: two `tab_hidden` events freeze/end the session server-side, and that is working-as-designed if the events are present. If the candidate ADMITS switching tabs or opening devtools, don't re-verify — that's a legitimate strike, handle as policy dictates. Only when a candidate DISPUTES it (claims they never switched) is investigation needed: pull the session detail and check for `tab_hidden`/`frozen` events. Zero strikes and `status=live` means the server never froze them — their "it ended" is a different failure (see next bullet), not a tab violation, and the claim is credible.
- **"Connection lost" while the server shows the session as `live` with zero strikes** — this is a client-side WebSocket/ttyd drop to the sandbox, not proctoring. Confirm by hitting the sandbox's own URL directly (`https://sb-<id>.vercel.run`) — a `410 Gone` means the sandbox itself died; a live 200 with a still-`live` orchestrator session means the socket dropped independently of the sandbox. Don't conflate this with the tab-strike freeze; they have different root causes and different fixes. If a meaningful fraction of live sessions show this (check ws-bridge logs for WS reconnect storms), suspect the wrapper's terminal reconnect loop giving up too early on a transient network blip rather than a sandbox/platform failure — see `references/architecture-and-ops.md` ("Candidate terminal connectivity") for the diagnostic path and fix pattern.
- **Don't default-bucket every "connection lost" report as our fault.** When a batch is drawn from a region/college with known-poor connectivity, and the SAME symptom is reported independently on the separate VVA/Deep-Dive system (a different codebase, different infra), that's evidence the drops are regional network, not our wrapper. Bucket these as a distinct "connection lost — ambiguous" outcome rather than "our fault," and only reclassify to our-fault if there's fleet-wide corroboration in our own signals (a high reconnect-storm rate in ws-bridge logs, or 429/rate-limit strings inside the affected candidates' own transcript JSONL) — a handful of individual reports alone isn't enough to indict the system.
- **Once the user tells you a specific candidate's incident is settled or was misdiagnosed (e.g. "that one was just a tab switch, drop it"), stop naming that candidate in later incident write-ups, cards, or status updates.** Re-surfacing a closed/resolved case as if still open reads as not having listened and forces a repeat correction.
- **A subagent's "root-caused, verified live, no code change needed" self-report is not itself proof the incident is resolved for real candidates.** If the user pushes back that the underlying symptom is still happening (e.g. "they couldn't scroll/use arrows even after the disclaimer"), don't defend the prior investigation — a single-session repro can miss the real conditions (different build, timing, browser, candidate state). Say plainly that the two accounts conflict, and get a fresh live repro on the currently-deployed build before re-asserting the fix holds. Likewise, a fix that makes a failure MODE recoverable (e.g. retry-forever on a dropped socket) is not the same as fixing why the failure happens at all — say so explicitly rather than letting "deployed and live" read as "root cause resolved."
- **To decide a disputed case, get the recording, don't decide from events alone.** Drive folder/recording/transcript only populate after teardown — a `live` or `frozen`-but-not-yet-torn-down session has none. If the session is still `live`, `POST /v1/sessions/{id}/override {"action":"freeze"}` forces teardown (capture → recording_ready → Drive upload) so you have the actual recording to review before ruling on the candidate's claim. Do this before making any reinstate/uphold decision on a disputed freeze.

## Batch outcome reporting

When asked "how many proper submissions" or to list who "finished" a batch vs who hit issues, classify every session in the batch by `status` + `end_reason` from `/v1/sessions/{id}/detail` — don't eyeball a status count alone, since `ended`/`terminated` each contain both clean and problem cases:

- **Clean/proper submission** = `status=ended` AND `end_reason` in (`timer`, `candidate_done`) AND `entered` event present AND `transcript_status=ready`. This is the "finished, didn't terminate on issues" bucket the user means by a proper submission — timer (ran the full duration) and candidate_done (clicked Done early) both count; require `entered` + transcript-ready too, since a session can end with those reasons but never actually have the candidate inside.
- **Not a proper submission**: `end_reason=forfeited` (never joined in time — `entered=False`), `end_reason=tab_violation` (entered but proctoring froze them), `admin_force_destroy`/`admin_freeze` (our own test/cleanup or a disputed-case teardown, not a real candidate outcome).
- **Always report the joined count alongside the proper-submission count, not just the raw total scheduled.** The user's standard follow-up to any submission count is "per how many actually joined" — compute `joined` (has a `joined` event) as a separate figure from `total scheduled` up front, so you can answer proper/joined and proper/total without a second query round-trip. Forfeits (never joined) are usually the largest single bucket and should be broken out explicitly, not folded into "didn't finish."
- **When the user cites a specific artifact (e.g. a Drive folder link) as evidence for a claim, resolve identity by looking up that exact identifier against the source API, never by assuming it's at some position (e.g. "row 3") in your own locally-sorted reconstruction of the list** — your sort order and the doc's rendered order can differ, and matching by position first can implicate the wrong candidate before you've checked the one actually named.
- Pull the full batch by filtering `/v1/sessions?limit=100&cursor=...` (paginate via the returned cursor) on `scheduledStartAt` prefix-matching the batch's UTC start time, then hit `/v1/sessions/{id}/detail` per session for the real classification fields — the list endpoint's `scheduled_start_at` is empty/unreliable (see scheduling mechanics below), and status/end_reason granularity only exists on detail.
- **`drive_folder_id` is a detail-only field — the list endpoint's session objects never carry it, even though they carry `candidateEmail` and `id`.** To build an email→Drive-folder map for a whole batch: first pull the list once to get `{id: candidateEmail}` for the batch (filter by `scheduledStartAt` prefix as above), then fan out `/v1/sessions/{id}/detail` per session **concurrently** (`concurrent.futures.ThreadPoolExecutor`, ~10-12 workers — 300+ sequential detail calls is too slow for one call) and read `drive_folder_id` off each. Not every session in the batch has one (forfeits/no-shows never reach teardown) — filter to non-null before reporting a count, and state that filtered count alongside the raw scheduled total.
- **Detail-endpoint `events` entries can be either dicts (`{"event": "entered", ...}`) or bare strings** depending on the event type — normalize with `(e.get('event') if isinstance(e, dict) else e) for e in events` before matching, or a plain `e.get(...)` list comprehension throws `AttributeError` partway through a 300+ session loop.
- To hand the clean list to the user: build one row per candidate (name, email, end_reason, Drive folder link `<internal-doc><drive_folder_id>`), write as markdown, then `gog docs create "<title>"` + `gog docs write <id> --replace --markdown --file <path>` — same doc-rendering pattern as candidate email previews, and it's the fastest way to hand over a reviewable batch-outcome list instead of pasting a huge table in chat.

## Review-viewer server operations

The transcript-eval review UI (`node tools/review-viewer/server.mjs`) can run in two modes: `--source gcp` (reads the bucket live) or `--source local --root <dir>` (reads a local mirror). Same binary either way — there is no separate "our" vs "their" viewer.

- **`--source gcp` needs Application Default Credentials on the box (`~/.config/gcloud/application_default_credentials.json`), separate from a normal `gcloud auth login`.** On a headless box, run `gcloud auth application-default login --no-browser` — it prints a link to open on another machine, consent, then paste the code back; the interactive (non-`--no-browser`) flow can't complete on a box with no local browser.
- **Live `--source gcp` mode is too slow for interactive use once the cache has hundreds of objects** — listing the bucket on every `/api/runs` call can exceed 60s and time out. For interactive review sessions, mirror the relevant cache prefix(es) to a local dir first (`gcloud storage cp -r "gs://<bucket>/transcript-eval/cache/<email-or-pattern>" <local-dir>/`, parallelizable per-candidate) and run `--source local --root <local-dir>` — reads become instant. Re-sync the mirror (re-run the cp) whenever new candidates are added to the batch or GCS-side reviews change.
- **After changing a running server's flags, verify the change actually took before trusting the UI** — hit its own config-introspection endpoint (e.g. `/api/config`) and check the reported `source`/`work_root` match what you just launched with. A `pkill -f <script-name>` pattern-match can miss a differently-invoked prior instance still holding the port; the "new" server then fails to bind and the OLD process keeps serving stale config silently, with no error surfaced to you. If config doesn't match: find the exact PID holding the port (`lsof -i :<port>` or grep process list for the script path), kill that specific PID, confirm the port is free, then restart — and re-check `/api/config` again, since a SIGKILL aimed at a stale PID in the same shell session can also take down the new server if they share a process group.

## Kanban board-mismatch gotcha (T2/supervisor sessions)

When a task body says something like "pass --board ti-hiring on every hermes kanban call," that phrasing itself is a signal: the session's `HERMES_KANBAN_BOARD` env var is pinned to a DIFFERENT board (e.g. an unrelated project board), so any `kanban_*` tool call made with no explicit `board` argument silently resolves against the wrong board's SQLite file and fails with a generic `unknown task <id>` error — which reads exactly like a wrong/typo'd task_id but is really a wrong board. Each board is its own file at `~/.hermes/kanban/boards/<slug>/board.db`, so "unknown task" against the wrong board almost always means "right id, wrong board," not a nonexistent task. Fix: pass `board=<slug>` explicitly as a top-level argument on every `kanban_comment`/`kanban_block`/`kanban_attach`/etc. call for the whole session, not just the first one — a call that worked once (e.g. because you happened to pass `board` on it) does not mean later calls without it will too. To confirm the mismatch after the fact: `env | grep HERMES_KANBAN_BOARD` vs the task's stated board slug.

## Diagnosing crashed/blocked kanban engineering-fix tasks

- **When you diagnose a real defect (red CI/smoke on main, a UI bug, a stuck state), card it in the same turn; do not leave it as "want me to card this?".** An offer the user does not answer is a dropped task, and he later asks "didn't we card this". Check the board (`tasks` title/body LIKE the symptom, status in ready/running/blocked) before claiming a card exists.

When running the ti-hiring engineering fix pipeline as a swarm of `kanban_create`'d worker tasks (bug fixes, stress tests, spikes — dispatcher-managed, not T1/T2 tmux), workers occasionally crash. Don't treat every crash notification as needing intervention:

- **A single "worker crashed (pid gone); dispatcher will retry" is normal and self-heals.** Check `kanban_list(status="running")` for the task — if it shows a higher `current_run_id` than before and fresh heartbeats, the dispatcher already respawned it. No action needed.
- **Only act once the task actually reaches `blocked` with a `gave_up` event** (dispatcher hit its per-task failure limit, typically 2). `kanban_show` the task and read `runs[]` — each failed attempt's `error`/`outcome` tells you the crash type: `signaled`/exit_code 9 (killed, possibly OOM or an external kill), `protocol_violation` (worker exited rc=0 without calling a terminal kanban tool — treat as a crash, its work is unverified), or `pid not alive` (spawn itself failed).
- **Before deciding to retry, check whether any WIP survived** — `git fetch origin <expected-branch>` (from the body's "Commit on a non-main branch, push" instruction) and `ls` the task's workspace dir. If nothing was pushed and the workspace is empty, the crash happened before any real work landed — it's safe to `kanban_unblock` immediately, nothing is lost. If a branch/commits DO exist, read them before retrying — the next attempt may re-do work or need to resume it instead of starting over.
- **To check if a crash was a real OOM kill vs. some other SIGKILL**, don't assume from signal 9 alone: run `free -m` for current headroom and `dmesg -T | grep -i "killed process\|out of memory"` (fall back to `journalctl -k --since "-3h" | grep -i oom` if dmesg needs root). No matching kernel log entry means it wasn't the OOM killer — likely a manual kill, a dispatcher timeout, or a transient spawn failure, not a memory-pressure problem worth downsizing the task for.
- **`kanban_unblock` is the correct tool to retry a `gave_up` task** — it resets status to `ready` so the dispatcher respawns a fresh attempt. Use it once you've confirmed (via the WIP check above) that retrying won't stomp on real progress.
- **A "timed out (max_runtime=Ns); will retry" notification can fire AFTER a task already finished successfully** (its PR already open/merged, its `kanban_complete` already recorded) — this is the dispatcher's runtime-cap firing on a stale/lagging process report, not a real failure. Before treating it as work-to-redo, `kanban_show` the task: if status is already `done` with a real summary/PR, it's a stale notification — no action needed, don't re-investigate or re-run it.
- **A task body phrased as "first scope/read X, then build/wire Y" can come back `done` having only done the recon half** — the worker treats "determine the gap" as a valid stopping point and calls `kanban_complete` with a plausible-sounding read-only summary (git show/ls-tree only, no diff, `repo_modified: false` in its metadata) even though the body explicitly also asked for an implementation + PR. Always check the completion's own metadata/summary for evidence of an actual change (a branch, a diff stat, a PR link) before treating "done" as "built" — a confident recon writeup is not a substitute. If it stopped at recon, don't re-dispatch the same combined body (it will likely recon again); open a fresh task that pastes the prior recon's findings as given ground truth and asks ONLY for the implementation.
- **Before merging a PR whose safety case rests on a worker's "validated against N real cases" claim (a stress test, an eval dry-run, a data-reconciliation check), pull and read the actual raw output artifact yourself before calling it good to merge — don't merge on the worker's prose summary of verdicts alone.** A completion note that lists specific per-case results (e.g. "no_go for the lazy one, insufficient_evidence for the thin ones") can be accurate, but reading it back to the user as confirmed is just paraphrasing the self-report, not independent verification — the same gap the orchestration-wide rule about subagent self-reports warns against, and it applies to your own dispatched kanban workers too. If the real artifact (a report JSON, a GCS object, a workspace file) is gone by the time you check — worker workspaces get cleaned up after completion, and a deploy config's bucket/env var can be an unfilled placeholder — say that plainly and get a fresh run that surfaces the genuine output before asserting the feature works, rather than treating the absence of a retrievable artifact as if the summary already proved it.

## Writing a standalone decision doc (not an RCA, e.g. a build-vs-alternative doc)

Same stakeholder-doc discipline as the RCA section above, but for a decision doc that stands alone (a summary tab read without the full-detail tab open):

- **A summary/short tab must be readable and complete on its own** — if the full-detail tab states a specific technical reason for a choice (e.g. why tool A on one OS and tool B on another), the summary must state that reason too, not just the bottom-line choice. A reader who only opens the summary should not have an unanswered "why not just use one tool everywhere" question.
- **Never write a decision doc as a status log.** Phrases like "the build is done (in review)", "if the validation batch is clean, then...", "runs tomorrow's batch" are progress narration, not decisions — strip them. A "Next decisions" section lists actual open decisions going forward (flat statements: "do X", "validate Y before Z"), never build-step checklists or conditional-on-outcome sequencing.
- **Internal implementation plumbing does not belong in a decision doc** — a subdomain name, a service hostname, an internal endpoint path: these are ours to just pick, not a decision that needs stakeholder visibility or even doc space. Cut anything that reads as "here's a technical detail we handled" rather than "here's a choice with tradeoffs." If unsure whether a line is a decision or plumbing, ask: does getting this wrong require someone else's input to fix? If no, cut it.
- **When a doc frames a tradeoff/limitation defensively (implies we should have done more, e.g. "we should smoke-test on a clean machine before every batch"), check whether that step was already actually done** before leaving it as a forward caveat — restating an already-completed verification as a future to-do undersells the real state and invites an unnecessary question.
- Full-tab replace wipes live reviewer comments permanently (even Docs version-history can't restore them) — use `gog docs find-replace` for targeted edits on a doc/tab that might have comments; only full-replace a tab after confirming (via a comments-check or `--check-orphans`) there's nothing live to lose.

## Evaluator (transcript-eval) design decisions and legacy cleanup

- **The evaluator grades HOW the candidate drove the agent, never WHAT the agent/candidate produced.** The assignment's own candidate-facing text says this explicitly ("driving, not typing"), and the transcript is the only signal — no artifact is run or inspected. When scoping evaluator work, reject any rubric content that checks output correctness (a "canonical semantics" table, a spec-compliance checklist, a harness-passes/fails check) — that measures the wrong thing even if it's well-written.
- **Use ONE shared rubric across every assignment variant — never a per-assignment answer-key overlay.** Candidates draw different assignments; grading them against different per-assignment criteria isn't comparable and reads as unfair. If a per-assignment knowledge file (e.g. an INTERNAL.md "what this measures"/traps table) exists, that's a design smell for this pipeline specifically — flag it rather than treating its existence as settled, and default back to the shared rubric.
- **Before describing or comparing "what dimensions/signals the evaluator scores," re-read the rubric file from the CURRENTLY LIVE evaluator directory, never recall it from an earlier part of the conversation or from a sibling evaluator generation.** This pipeline has gone through multiple evaluator generations in the same repo (a deprecated N-dimension scorecard design superseded by a smaller signal-based rubric) — citing the old dimension names as current is a real, easy-to-make mistake since both still exist on disk. Check the live rubric path (e.g. `<evaluator-dir>/src/knowledge/rubric/rubric.md` + its `signals/*.md`) fresh every time this question comes up.
- **A `LEGACY.md`/"do not build here" marker on a deprecated directory does not guarantee nothing live still points into it.** Grep the whole repo for the deprecated dir's name before assuming it's safely fenced off or before recommending deletion is trivial — a workflow/config file can keep referencing the "legacy" path (venv, PYTHONPATH, script paths) despite the marker, which is exactly the kind of drift that causes confusion later. When cleaning up a legacy pair (e.g. an old evaluator + the workflow that drove it), delete both together and re-grep afterward to confirm zero references remain, including in `.dockerignore`/`.gcloudignore`-style exclude lists.
- **Batch-eval scope: a proctoring violation is NOT an eval exclusion.** A tab-strike/fullscreen-exit/devtools termination is a separate signal from the driving-quality signal the evaluator measures — grade the violated candidate's transcript like everyone else's and surface the violation alongside for the human reviewer to weigh, don't filter them out of the run.
- **"Registered for the batch" and "evaluable" are different counts — report both, never just the scheduled total.** A batch's scheduled/registered count includes no-shows and empty-transcript sessions; the count that matters for the eval run is sessions with real transcript content. State both numbers (e.g. "502 scheduled, 360 with a usable transcript") whenever reporting eval coverage.
- **A cheap pre-filter to skip empty sessions before the judge step is worth adding only if the judge pipeline is itself slow/costly enough that burning calls on empties matters — don't add the filter layer by default.** Check actual runtime/cost per session first; if it's already fast, an evaluator that already abstains honestly on empty input needs no separate pre-filter.
- **When filtering "empty" sessions, checking for zero `user`-type transcript rows is not sufficient — a candidate who hit a connection drop mid-session may have queued prompts that never got a completed model turn, which show up as `queue-operation`/`enqueue`-type rows in the transcript JSONL, not `user` rows.** Treating those sessions as empty and dropping them pre-judge discards real candidate signal; check for queued-but-unanswered prompts too before classifying a session as having no content.

## Review-cache hygiene: the GCS eval cache mixes cohorts

The transcript-eval GCS cache (`transcript-eval/cache/<candidate-id>/<assignment>/`) is a single flat namespace that accumulates every eval ever run — infra lead's original take-home sample batch (`c00xx`-style IDs, from GitHub-submission evals), any live candidate batch (email-addressed), and any calibration/internal-tester runs (also email-addressed, but `@<org-domain>` not a candidate domain). There is no batch-scoping in the storage layout itself.

- **Never mirror or serve the whole cache prefix and assume it's one batch.** Mirroring `gs://.../transcript-eval/cache/*` to a local dir for the review viewer pulls every cohort that ever ran through the tool, not just the batch you're reviewing — a stray `c00022`-style ID or an unrelated GitHub-submission candidate showing up in the review UI is cache pollution, not a bug in the eval itself. Before pointing a review viewer at a mirrored root, filter to the specific candidate-id set (e.g. the batch's known email list) and delete everything else from the local mirror.
- **When a named person doesn't look like they belong to the batch you're reviewing (wrong ID shape, wrong email domain, a candidate you don't recognize), don't assume a data leak or a code bug — check which cohort/run produced that entry first** (grep the cache dir's contents, check the sheet the batch was sourced from) before concluding anything is broken.
- **A request to eval a specific named person who isn't an obvious batch candidate (e.g. "run the eval on X and Y too, we'll find a baseline") is usually an internal-tester/calibration request, not a batch addition.** Check the "Internal Tester Calibration" Google Sheet (columns: Name, Email, Assignment, Session ID, Status, Took at UTC, Transcript, Prompts digest, Drive folder, Meet recording, Notes) for their row before assuming you need to search candidate rosters — internal testers get their own session id + Drive folder there, same shape as a real candidate session, and the eval runs on them exactly the same way (same rubric, same GCS publish path). Their results will land in the same shared cache under their `@<org-domain>` email, so re-filter the review mirror afterward if you'd already cleaned it to a single batch.
- **`report.json`'s per-signal grade lives at `combined.findings[]` (and `focused.findings[]`), each entry `{signal, pattern, summary, ...}`** — `signal` is one of the three rubric names (`problem_ownership`, `question_quality`, `advice_seeking`); `pattern` is one of `shows` (green), `mixed` (yellow), `does_not_show` (red), `not_exercised` (grey, no evidence either way). The review-viewer UI resolves a signal's badge as the FIRST finding matching that signal name (`findings.find(f => f.signal === X)`) — replicate that exact selection when scripting any candidate-level filter over the cache (e.g. "only show candidates with at least one non-red signal"), don't aggregate/average across findings, or your filter won't match what the UI actually displays.
- **To apply a view-only filter to the local review mirror (e.g. drop all-red candidates), MOVE the excluded candidate directories to a sibling directory rather than deleting them.** This is reversible (move back in one step) and never touches the GCS source-of-truth cache or any other consumer's view (e.g. a stakeholder running `--source gcp` sees everything, unaffected) — the filter is purely a local-mirror-serving decision, not a data change.
- **To bring a specific previously-excluded candidate back into view (the user wants to look at one they'd dropped earlier), `cp -r` their directory from the sibling dropped dir back into the served root** — no server restart needed, the running `server.mjs` reads the mirror directory fresh on each `/api/runs` request. Confirm the restore actually took by hitting `/api/runs` (or the equivalent list endpoint) yourself and checking the candidate's id/email appears in the response, rather than assuming the file copy alone means it's visible in the UI.
- **When reading reviewer verdicts back out of `review.json` for reporting (e.g. building a greenlit list or writing results to a sheet), read the raw file structure directly — don't reuse a locally-flattened/pre-aggregated JSON built earlier in the session.** A convenience dict that flattens `criteria.<signal>` down to a bare verdict string (to make one query easy) silently drops sibling fields like `verdict_comment`/`eval_feedback`/the overall `comment` that live alongside the verdict in the real object. If a later ask needs the feedback text too, re-fetch the actual `review.json` objects from GCS fresh rather than querying the earlier flattened structure — the flattening was lossy by construction, and quietly querying it a second time for a field it never carried gets you `null`/no-feedback for candidates who genuinely have some.
- **The overall feedback field is `overall.verdict_comment`, not `overall.comment` — the per-criterion equivalent is `criteria.<signal>.verdict_comment`.** Reading `overall.comment` (a field that doesn't exist or is usually empty) silently returns near-zero feedback across a whole batch even after correctly re-fetching the raw file, which looks identical to "most reviews are verdict-only" and is easy to accept at face value. Sanity-check any bulk feedback-extraction result against the reviewer's own expectation before reporting it (e.g. if they say they left comments on every pass and several fails, and your extraction finds feedback on only 1-2 records total, the key name is wrong, not the reviewer's memory) — dump one full known-commented record's raw JSON and confirm the field path by eye before trusting a batch extraction.

## Classifying evaluator PRs for stakeholder review

When a stakeholder who built the evaluator (or owns final say on grading) asks to see "PRs that change evaluation strategy or prompts" before release, and green-lights plumbing to ship without review:

- **The line is whether the RUBRIC/grading criteria changed, not whether a judge/prompt file was touched.** A PR that changes what the judge is FED (new input source, more transcript tabs, a captured-session format instead of a repo) is plumbing to the new assessment flow even if it edits `judge/prompt.ts` or `judge/rubric.ts` to wire the new input through — the grading criteria itself is unchanged. Only a PR that edits the rubric/signal markdown content itself (what counts as does_show vs does_not_show) is a strategy change. Don't let "touches the same file as the rubric code" pull a pure-plumbing PR into the review-required bucket.
- **When unsure, list the changed files per PR (`gh pr view <N> --json files`) and check literally which paths changed** (`knowledge/rubric/*.md` and `knowledge/rubric/signals/*.md` = rubric content; everything else touching judge code = wiring) rather than reasoning from the PR title or your own summary of what it does.

## Scanning transcripts for infra-error evidence (429s, rate limits, other systemic faults)

When the user asks "how many candidates hit X" for an infra-level fault (rate limits, overload errors, dropped connections) that would show up as raw text inside the session transcripts, the right source is the transcript JSONL captures in GCS (`transcript-eval/captures/<session-id>/*.jsonl`), scanned per-session — not the eval's own report.json, which only records the grading verdict, not infra symptoms.

- **Anchor patterns to structured error shapes, not bare keywords.** A bare `\b429\b` or `quota` pattern false-positives on legitimate candidate content — a candidate's own code, comments, or pasted API docs can contain "429" or "quota" with zero connection to an actual rate-limit event. Require the number to co-occur with an error-shape marker within a short window (`"status":429`, `429.{0,40}(too many|rate|limit)`, `"type":"rate_limit_error"`, `Overloaded`) so a hit means a real API error response, not incidental text.
- **Run this as a batch scan across every session's captures, not just the one candidate named** — an infra fault reported for one candidate is rarely isolated; count how many of the whole batch show the same evidence so the user gets the systemic picture (e.g. "110 of 185 candidates, ranging from 1 brush-with-the-limit to 30+ heavy-throttle hits") instead of a single anecdote.
- **Bucket hit counts into severity tiers (light/moderate/heavy) rather than reporting a flat count** — a candidate with 1-2 hits barely noticed it; a candidate with 20+ hits lost real working time to the throttle, which is directly relevant context if their session also graded as thin or `insufficient_evidence`. Flag that correlation explicitly (cross-reference heavy-hit candidates against weak verdicts) since a throttled-into-emptiness session is an infra artifact, not a true skill signal, and may warrant a re-run rather than a fail.
- Auth for GCS reads on the ops box: `gcloud auth application-default print-access-token` (ADC), used as a Bearer token against the JSON API (`storage.googleapis.com/storage/v1/b/<bucket>/o?prefix=...` for listing, `.../o/<name>?alt=media` for content) — same pattern as other GCS reads in this pipeline, works even when a plain `gcloud auth login` user token has expired.

## Cleaning candidate-facing artifacts (prompts.txt) of harness noise

A session's Drive `prompts.txt` ("everything you typed to Claude") and the eval's own transcript rendering both draw from the same raw `transcript-*.jsonl` captures, and both are naively over-inclusive: any `type:"user"` message with string content gets treated as a genuine candidate turn, including harness-injected blocks (`<task-notification>`, `<system-reminder>`) that are NOT something the candidate typed. A file that's ~50% harness noise (or a report that graded the candidate on notification-block content) misrepresents what the candidate actually did.

- **A per-line/per-entry prefix check (`text.strip().startswith("<task-notification>")`) is not sufficient — task-notification blocks can span many separate JSONL entries.** A single notification's payload (e.g. a pasted multi-step plan) gets chunked across dozens of consecutive `user`-type entries; only the FIRST entry's text starts with the tag, and the rest look like ordinary standalone prompts once you filter line-by-line. This shatters one harness block into dozens of fake "genuine" turns. The correct filter tracks open/close state: once `<task-notification>` opens, treat every subsequent entry as still inside it until the entry containing `</task-notification>` closes it — never key the check off a single entry's own prefix. Verify by counting: the true genuine-prompt count for a real candidate should be small (single digits to low tens for a ~20min session); if a "cleaned" file still has 20+ entries, the shattering bug is still active — go re-check the close-tag handling before trusting the output.
- **Dedup cross-tab repeats by a normalized-text key** (`re.sub(r"\s+"," ",text)[:300]` as the seen-set key) — multi-tab sessions repeat the same early prompts across tabs, and without dedup a "clean" file still overcounts.
- **Sort by timestamp before writing, not by JSONL/tab file order** — transcripts from multiple tabs concatenate in file-discovery order, not chronological order, so an un-sorted "clean" list can present prompt #3 before #1 in wall-clock time.
- **Test the filter against a known-noisy real session BEFORE running it across a whole batch.** Verify by hand that the output prompt count and content look like real candidate typing (short, task-relevant, first-person) — a naive fix that looks right on a clean-ish sample can still leak on a session whose notification block happens to be unusually large.
- The tested extraction+dedup+sort logic (and the Drive-replace pattern below) is at `scripts/extract_candidate_prompts.py` — reuse it rather than re-deriving the filter each time this comes up.

## gog CLI usage gotchas

- **A gog subcommand typo can fail with a short stderr message (`unexpected argument values`) while your pipeline still parses stdout as if it succeeded** — an empty or malformed stdout after a failed command looks identical to "the query legitimately returned nothing." This nearly caused a real false negative: `gog sheets values get <id> "A:A"` doesn't exist (the real subcommand is `gog sheets get <id> <range>`, aliases `read`/`show`), so a script piping that output through a regex silently extracted zero rows and looked like proof a candidate was missing from a sheet he was actually in. Before trusting a "not found" / "zero results" conclusion from a gog-based script, check the command's actual exit code and stderr, or dry-run the exact gog invocation once directly in the terminal — don't let a downstream parser's empty output stand in for a verified absence.
- Check a subcommand's real form with `gog <resource> --help` (e.g. `gog sheets --help` lists `get (read,show) <spreadsheetId> <range>`) rather than guessing from a REST-API-shaped name like `values get`.

## Drive file in-place content replacement

gog has no "update/overwrite content of existing fileId" command — only upload (new file) and delete/trash/rename. To replace a Drive file's content while preserving the original as evidence (never destroy candidate-facing artifacts outright):

- **Write access to a file is scoped to whichever OAuth identity owns/can-write that file — a different account's ADC or gog token can read metadata but 403s or silently no-ops on write/PATCH even if it authenticates fine.** If the folder's owner is a service identity (e.g. `<ops-mailbox>`), you MUST write through that identity's gog client (`gog --account <ops-mailbox> --client startgreat drive upload/rename ...`), not your own personal account's token, even though your own account can list/read the same folder fine.
- **Procedure: upload the new content as a new file (with the target's real name), confirm it got a new fileId, THEN rename the OLD file to a `-raw`/`-original` suffix (never delete it).** This keeps the clean version at the expected filename for anyone consuming it, while the original stays retrievable in the same folder as an audit trail — a candidate dispute or a stakeholder question about "what did the filter actually remove" needs the raw version to still exist.
- Don't upload a second file under a distinguishing name (e.g. `-filtered`) and leave both live side by side unless explicitly asked — the user's expectation for a "clean up this file" request is that the filename people already have bookmarked/linked ends up holding the clean content, with the noisy original demoted, not two files at two different names.
- Before running a Drive artifact regeneration across a whole batch (100+ folders), validate the upload+rename mechanics on ONE known folder first (list its current files, confirm the client that owns it, dry-run the rename) — the failure mode of authenticating with the wrong client for 150 folders is expensive to unwind (leaves partial state: some folders with two prompts.txt-named files, ambiguous which is which).

## PR-description attribution for stakeholder-facing changes

When a PR body will be read by the person whose own feedback partly motivated it (e.g. a rubric-hardening PR responding to a reviewer's batch critique):

- **Attribute each substantive change to its actual source** (the stakeholder's specific review comment, your own finding from a sample eval run, a preventive measure for an upcoming process change) — don't blanket-credit one person's feedback for the whole PR when only part of it came from them. Over-attribution reads as claiming validation you don't have and undersells your own findings.
- **State plainly in the PR body which parts of the surrounding batch of work are the substantive change and which are just rewiring to a new format** — a reviewer scanning for what to actually review needs that split up front, not buried in file-level diff review.
- Fix a misleading PR description by editing it in place (`gh api -X PATCH .../pulls/<N>` or `gh pr edit --body-file`), not by appending a correction comment underneath the original claim.
- **A PR description is a point-in-time artifact of the change AS PROPOSED — never inject knowledge you only have because you're writing/fixing it later** (a batch's eventual results, a downstream re-run's outcome, cross-PR narrative about what happened after merge). Even when rewriting a PR body for accuracy in the same session where you already know how it turned out, keep the description to what was true and known when the change was raised (the gap being fixed, the mechanism, why) and leave the outcome out entirely — a reviewer reading it later should see the change as it was pitched, not a retrospective.

## GCP project (ti-hiring) — security lockdown, no agent-initiated changes

The account owner's standing directive: the ti-hiring GCP project must stay locked down — no agent creates keys, enables APIs, creates secrets/service-accounts, or changes IAM policy on it, ever, without the owner personally knowing about each specific change beforehand. Treat the project's control plane as read-only for agents.

- **Before any GCP action on ti-hiring, classify it as a project-control-plane change or a data operation.** Control-plane = enabling an API, creating/rotating a secret or service account, granting/changing IAM policy, deploying/redeploying a Cloud Run job or service — none of these may be agent-initiated; surface the need and let the owner do it or explicitly approve it first. Data operation = reading/writing objects with credentials that already exist and are already scoped that way (e.g. the owner's own `gcloud auth login` user identity reading Drive and writing to a GCS bucket it can already reach) — this is fine and does not need per-instance approval, because it changes no permissions and creates nothing new.
- **If a task's only path forward requires a control-plane change (a new secret, an IAM grant, enabling an API), don't do it — stop and surface the specific change needed, or fall back to a path that avoids it entirely** (e.g. sync data into GCS under the user's own existing auth instead of granting a service account Drive-secret access).
- **If an agent already made a control-plane change on this project before this rule was known or enforced, disclose it explicitly and by name (what was created/enabled, by which task) rather than silently building on it or leaving it unmentioned.** Don't undo it unilaterally either — that's still a change; let the owner decide whether to keep or revert it.

## AFK / unattended-run handoff

When the user is going AFK for hours and wants a long-running pipeline (an eval batch, a data backfill) to keep making progress unattended:

- **Put the "don't block on me, fall back instead" instruction directly on the kanban card as a comment**, spelling out the exact fallback path (e.g. "if the deployed/remote path hits any blocker, switch to the local path immediately") and the concurrency ceiling to use (low — prioritize not crashing over speed when no one's watching to restart it). A worker that hits an owner-approval wall with no fallback instruction will correctly block and sit idle for the whole AFK window.
- **Arm a local watchdog cron (`cronjob_manage`, `no_agent` script) alongside the hand-off** so a wedged/crashed local process gets caught even though no one is watching interactively — see `local-state-monitoring` skill for the watchdog-script pattern (silent when healthy, one line only when something needs attention).

## Executing a large per-candidate batch (sessions + verified emails) via delegate_task

When a batch (session creation + individually-verified instruction email per candidate, e.g. 300+ recipients) is handed to a `delegate_task` subagent because it's mechanical and shouldn't pollute the main session:

- **Design the runner as resumable from the first version, not after the first timeout.** A subagent doing one session-create + one verified email per candidate for a few hundred recipients routinely exceeds the ~30-minute subagent wall clock and gets killed mid-batch — this is expected, not a failure to fix. Have it write one JSON line per candidate to a log file immediately after each send (`status`, `email`, `cohort`, any error), and have it skip any recipient already `status=sent` in that log on every invocation.
- **On a timeout, don't re-plan — just re-dispatch the identical goal pointing at the same log and recipient list.** Read the log first (`wc -l`, group by status) to report real progress and confirm zero failures before re-dispatching; a clean resume needs no new instructions beyond "skip anything already sent in the log."
- **Verify-before-send stays in force on every resume**, not just the first pass — each email still needs the candidate's own session's real Meet link, correct name, and their cohort's own times checked against the schedule before it goes out, since the resumed run is still touching real candidates.

## Prefilled, mail-only Gmail batches

When the user explicitly supplies prefilled per-recipient HTML and says this is a scheduling heads-up, **do not create sessions or call booking/intake APIs**; send the supplied files unchanged. Send a test to the specified internal address first and require a returned message ID (then read back its Sent metadata) before starting the batch. Validate manifest length, indexed file completeness, and file nonemptiness. Map each row index directly to its corresponding HTML file, including duplicate recipient addresses if the user explicitly requested every row; surface duplicate-address counts in the report. Pace sends at approximately one per second, write and flush one result record (index, recipient, message ID or error) after every attempt, continue past per-row failures, and resume only at the first unlogged index after a timeout so no successful mail is sent twice. Read back each sent message by its exact ID, checking Sent label, sender, recipient, and subject, before reporting verified totals. Keep keyring passwords out of output/logs.

## Batch scheduling math under a concurrency cap

When scheduling a large batch (hundreds of candidates) across a fixed time window with a hard concurrent-ADD-session cap (e.g. 100) and two assessments per candidate (ADD technical + VVA/Deep Dive) that must both run inside the window with a gap between them:

- **The cap forces at most one cohort on ADD at a time if cohort size approaches the cap** - two ~85-person cohorts running ADD simultaneously already exceeds a 100 cap (170 concurrent). Don't assume splitting into N cohorts lets N run ADD in parallel; check cohort_size * concurrent_cohorts <= cap explicitly before proposing a schedule, and default to staggering ADD waves one cohort at a time when cohort size is a large fraction of the cap.
- **Build the schedule around three fixed numbers the user gives you, don't guess any of them: ADD duration + join window, VVA duration, and the minimum gap required between a candidate's two assessments.** Solve for cohort count and start-time stagger that (a) keeps concurrent ADD under the cap, (b) gives every candidate at least the minimum gap between their two assessments, and (c) fits the whole batch inside the available window. Present the resulting per-cohort time grid as a table (cohort, size, first assessment window, second assessment window) so the user can sanity-check concurrency and gap at a glance rather than re-deriving it from prose.
- **A stagger-by-X-minutes schedule can look right at a glance but still violate the gap requirement or run over the window edge - recompute the actual end time of the last cohort's last assessment against the window close, and the actual gap for every cohort, before presenting the grid as final.** Redo the arithmetic when the user tightens or loosens the gap requirement (e.g. moving from an implicit back-to-back default to an explicit 15-30 min ask) rather than patching only the cohorts that looked closest to violating it.
- Random/arbitrary cohort splitting (not by grad year or college) is acceptable once the user confirms it's fine for a given batch - don't over-engineer a stratified split unless asked.

## Session scheduling mechanics

- **There is no reschedule API.** `scheduled_start_at` is set once at session creation; there is no PUT/override action that moves it (checked `/override` — only extend/freeze/force_destroy/retry_upload exist). To move a candidate to a new time: **destroy the existing session, create a new one** with the same assignment at the new `scheduled_start_at`, wait for provisioning to reach ready (Meet link created), then **resend the candidate's assessment email using the NEW session's Meet link** (the old Meet link is dead once destroyed).
- `scheduledStartAt` (camelCase) is the field name on session detail/list responses — not `scheduled_start_at` on the list endpoint, which returns it empty. Query the detail endpoint per-session if you need the real scheduled time reliably.
- **When scheduling a new sub-batch (e.g. a walk-in college roster), find an actual sent invite to a candidate already in that batch/city and pull both its exact template AND its two timings (technical + deep dive) from there** — don't re-derive or guess timings from a generic batch invite; different batches/cities can have different times, and the Sent-folder copy is the ground truth for that specific batch.
- **Never trust automated PDF/text extraction of a tabular roster (Google Form export, multi-column PDF) for candidate emails.** Column-based PDF-to-text extraction routinely misaligns and truncates columns (emails cut off mid-domain, e.g. `...@gmail.co`), and a wrong or guessed-complete email sends the assessment invite to the wrong address or nowhere. If extraction looks even slightly mangled, ask the user to paste the raw rows as text rather than reconstructing/completing truncated emails yourself.
- **A time given without an explicit zone ("3pm", "schedule for 2:30") means IST, never UTC.** Every candidate and HR user in this pipeline works in Asia/Kolkata; the wrapper's own admin dashboard already converts on this assumption (`wrapper/src/lib/admin/ist.ts`, fixed UTC+5:30, no DST). Convert to UTC yourself before calling the create-session API, and echo the IST↔UTC pair back when confirming a scheduled time so a wrong default surfaces immediately instead of after the candidate is already told the wrong time.

## Deploy verification (merge ≠ live)

- **After any merge, pull the actual failed step's log before concluding anything about the merged code.** `gh run list --branch main --limit 8` (not just the one workflow you expect — a merge can trigger multiple deploy workflows, e.g. orchestrator + wrapper + transcript-eval, and only one may fail) then `gh run view <run-id> --log-failed | grep -iE 'error|##\[error\]'` on any `failure` row. Two failure classes show up repeatedly on this repo and are NOT code bugs in the merged PR: (1) a CloudFormation template exceeding the 51,200-byte inline-template limit — CFN then refuses the deploy and demands `--s3-bucket` packaging, fixed once in `deploy.sh`, will recur if the stack template keeps growing without S3 packaging. Switching to S3 packaging surfaces a SECOND gap the first time it runs: the GitHub Actions deploy role typically has object-level S3 perms (get/put/list on an existing bucket) but not `s3:CreateBucket`, so the deploy fails with AccessDenied trying to create the staging bucket itself. This is a one-time bootstrap, not a role redesign — least-privilege fix is to pre-create the bucket once with the human's own creds (`aws s3api create-bucket --bucket <name> --region <region> --create-bucket-configuration LocationConstraint=<region>` then `aws s3api put-public-access-block --bucket <name> --region <region> --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true`), after which every subsequent deploy no-ops the create step and stages fine via the role's existing object-level perms. Don't grant the role `s3:CreateBucket` as the default fix — that's broader than the one-time need. Harden the deploy script to distinguish 404 (bucket missing, tell the operator the exact bootstrap commands) from 403/other (real permission problem) on the head-bucket check, so the failure is actionable instead of a bare AccessDenied; (2) `google-github-actions/auth` failing with "must specify exactly one of workload_identity_provider or credentials_json" — a GCP-deploy workflow-config issue (missing/renamed secret), not a code problem with whatever PR triggered that deploy. Diagnose the actual error line before telling the user a merge broke something, and before assuming a prior merge is unsafe.
  - **Diagnostic procedure for this specific error, before touching the workflow file**: (a) diff the workflow YAML at the failing sha against main (`git show <failing-sha>:<workflow-path>` vs current) — if the auth step's `with:` block is unchanged, the file is not the bug; (b) `gh secret list` AND `gh secret list --env production` (secrets can be repo-level or environment-scoped, check both) for the two secret names the auth step references; (c) if genuinely absent, check the GCP side too before concluding it's a pure GitHub-config gap: `gcloud auth application-default print-access-token` then hit the IAM API directly (`curl -H "Authorization: Bearer $TOKEN" https://iam.googleapis.com/v1/projects/<project>/serviceAccounts` and `.../locations/global/workloadIdentityPools`) to confirm whether a deploy SA and a Workload Identity Pool exist at all — an empty pool list means the WIF federation was never provisioned, not just unwired into repo secrets.
  - **This is a control-plane gap, so it falls under the GCP lockdown rule below: do not provision the WIF pool, deploy SA, or IAM bindings yourself.** Post the exact missing-secret/missing-pool findings as a kanban comment with a concrete proposed SA name + roles, then `kanban_block(kind="needs_input")` — do not open a PR (there is no code fix) and do not invent or mint any credential.
- **A failed CloudFormation deploy does not roll out a partial or broken state — it simply fails to apply, and the previously-live revision keeps serving.** Confirm this by checking the service is still on its last-known-good task definition/image; don't treat a failed CFN update as "something broke in production," it means nothing changed.
- **A merged PR is not a deployed fix.** Every merge-on-green watcher must be followed by checking the actual running image, not just the merge state. GitHub Actions deploy runs on this repo have been silently cancelled (not failed — cancelled, no error surfaced) more than once right after a merge, leaving main several commits ahead of what's live. Before telling the user a fix is "live": compare the deployed image SHA against the PR's merge commit, not against "the merge succeeded."
- Check deployed SHA: `aws ecs describe-task-definition --task-definition ti-orchestrator --region ap-south-1 --query "taskDefinition.containerDefinitions[0].image" --output text`. Get each PR's real merge commit with `gh pr view <N> --json mergeCommit --jq .mergeCommit.oid` (don't trust `git log` on a possibly-stale local clone — `git fetch origin main` first, or PR merge commits silently won't appear and you'll misread an older SHA as current).
- Confirm a commit is actually included in the deployed image with `git merge-base --is-ancestor <commit> <deployed-sha> && echo IN || echo NOT-IN` rather than eyeballing `git log` output.
- If the deploy run for the current main head shows `cancelled` in `gh run list --workflow "Deploy orchestrator" --limit 5`, re-trigger it yourself: `gh workflow run "Deploy orchestrator" --ref main`. Don't wait for it to auto-retry — it won't.
- Don't block a foreground turn on `gh run watch` for this pipeline — orchestrator deploys (build+push+ECS rollout) can run past typical tool timeouts. Arm a background poll instead (`terminal(background=true, notify=[...])` looping on the ECS describe-task-definition call above) and report back when the SHA matches, rather than repeatedly re-polling in the foreground.
- **The deploy workflow runs with `cancel-in-progress: false`, so a second merge while a deploy is still running QUEUES behind it instead of superseding it.** If a newer main head lands (e.g. PR B merges right after PR A, while A's deploy is still `in_progress`), the queued run for the newer head will only start once the older one finishes or is cancelled — meaning you'd deploy A, then B, sequentially, doubling wait time. Check `gh run list --workflow "Deploy orchestrator" --limit 5 --json databaseId,status,headSha` for a `queued` run behind an `in_progress` one on an older sha; if the queued run's sha is a superset (newer main head includes the older commit), `gh run cancel <older-run-id>` to let the newer, complete run start immediately instead of waiting through both.

## Deploying a hotfix when deploy.sh can't run locally

When a fix needs to go live but the checkout's `.env` is missing values `deploy/deploy.sh` needs (e.g. `DRIVE_ROOT_FOLDER_ID`, `VERCEL_TEAM_ID`, `VERCEL_PROJECT_ID`) and provisioning those just to run a script is overkill for a pure image bump:

- **An image-only change doesn't need the full deploy script** — register a new ECS task-definition revision that copies the CURRENT live revision's container definition verbatim except the `image` field (pull it with `aws ecs describe-task-definition`, edit only the image tag/digest, `register-task-definition` with the edited JSON), then `update-service --force-new-deployment`. Every other setting (env vars, secrets, CPU/memory, task role) stays byte-identical to what's already proven live — this is the safe subset of "deploy" that doesn't require the missing local config.
- **Before rolling, check for live sessions** (`/v1/sessions?status=live` or equivalent) — a service update replaces the running task, which drops any in-flight candidate mid-assessment. Zero live sessions makes the roll safe; if there are live sessions, wait or coordinate before rolling a P0 fix, don't silently proceed.
- **After rolling, confirm the NEW task actually booted the fixed image** (task-def revision number, image digest, and a health check) before treating the fix as live — a service can report `steady state` while still serving an old task if the roll silently failed to replace it.

## Forcing a session past `scheduled` for e2e verification

A session created via the admin API sits in `scheduled` and does **not** auto-transition on `scheduled_start_at` alone — the `scheduled → provisioning → ready` chain only fires on an actual join (a session-bound wrapper token hitting the join endpoint), same as a real candidate opening the assessment link. To drive an e2e verification session to `ready` without a browser: mint or reuse a wrapper token scoped to that session, POST the join call with it, then poll session detail until `status=ready` (or watch orchestrator logs for "provisioning → ready"). Force-destroy (`/override {"action":"force_destroy"}`) the verification session afterward so it doesn't linger as a fake live session in later batch/count queries.
- **Don't try to drive this via browser automation instead.** The session URL redirects straight to real Google OAuth sign-in, which cannot be scripted (no credentials to feed it, and shouldn't be) — a browser-automation attempt dead-ends at the login screen every time. Use the wrapper-token join method above, or hand the URL to the actual human whose account is invited for a manual click-through.

## Candidate-facing tooling decisions (client software candidates must install/run)

When deciding what tool a candidate installs and runs unsupervised (e.g. an SSH-over-WebSocket client to reach their sandbox), reliability outranks install convenience — a candidate has no chance to debug a flaky tool live, and a hang/crash/AV-quarantine reads as our failure even when it's the tool's. An extra install step is recoverable; a flaky run is not.

- **Don't settle a reliability question from a subagent's web-search summary or a README's memory-recalled caveat alone — re-check the project's live GitHub state yourself before locking the decision.** `gh release list --repo <owner>/<repo> --limit 10` for the true latest stable (a v4/v2-alpha tag can outrank the real stable numerically but still be prerelease — check the `Latest`/`Pre-release` label, not just version numbers). Then `gh issue list --repo <owner>/<repo> --state all --limit 60 --json number,title,state,createdAt` filtered for the specific risk keyword (the OS, protocol, or failure mode at stake), sorted by date, so a stale caveat (fixed since) is distinguished from a live one (an issue opened last week). When the user says "check the latest" after an earlier pass, this is the exact check they mean.
- **Compare failure MODES, not just presence/absence of issues — two competing tools each having open issues is not a wash.** A tool that fails to launch or hangs silently (unrecoverable, no workaround via instructions) is worse than one an antivirus flags as a false positive (mitigable: host the binary yourself, add a one-line "click Run Anyway" note). Weight the mitigable-risk tool over the unmitigable-risk one even if the unmitigable one installs in fewer steps.
- **Verify the exact mechanics live before writing them into a decision doc, not from documentation alone.** Build the actual client→bridge→sshd→login-hook chain (or whatever the mechanism is) end to end and observe it working — doc-only claims about e.g. binary-vs-text mode requirements, file-ownership requirements for a forced session, or which flags are mandatory on which end frequently differ from what a live run surfaces (binary framing corruption, socket-ownership permission errors, forced-command paths needing world-readable dirs). Delegate this verification to a subagent with explicit instructions to build and run it, not just read about it, and report back the concrete gotchas as copy-paste config, not prose description.
- Delegate the release/issue-tracker verification and the live-build verification as separate parallel `delegate_task` spikes when both are needed — client-tooling reliability research and server-side mechanics verification don't depend on each other and can run concurrently.
- **The Vercel Sandbox `node24` runtime image is Amazon Linux 2023 (`dnf`/`yum`), not Debian/Ubuntu — `apt-get` is not present.** Confirm the package manager (`cat /etc/os-release`; probe `for c in apt-get dnf yum apk; do command -v $c; done`) before writing any provisioning script that installs packages into a sandbox; a script written assuming apt silently no-ops (`command not found`, exit 127) with no packages installed. `sshd`/`tmux` are not preinstalled but install cleanly via `dnf install -y openssh-server tmux`; `runCommand` needs `sudo:true` for both the package manager and for the sshd/dir-ownership setup steps. websocat's static musl binary runs on this image with zero dependencies (no package manager step needed for the WS bridge itself).
This validates the SSH-over-WebSocket mechanism itself (client ↔ Vercel's HTTPS/WSS proxy ↔ in-sandbox bridge ↔ sshd).
- **The bridge tool on the sandbox side and the tunnel client on the candidate side must be the SAME tool (a matched pair) — mixing them is not an orthogonal choice, it breaks the handshake.** A websocat server paired with a wstunnel client (or vice versa) frames the WebSocket differently enough that SSH KEX starts but dies mid-exchange (stuck after `SSH2_MSG_KEX_ECDH_REPLY` sent, never received) even though each tool works fine paired with itself. This looks like a network/AV/reliability problem but is a pure protocol mismatch — before trusting any cross-tool test result, confirm the sandbox is running the server half of whichever client tool you're actually testing (e.g. `wstunnel server --restrict-to 127.0.0.1:22 ws://0.0.0.0:<port>` for a wstunnel client), and re-verify the matched pair from Linux first before handing a Windows tester the endpoint.
- **When a Python/shell test harness shells out to a Rust-based CLI tool (wstunnel, websocat) via `subprocess`, strip `NO_COLOR`/`CLICOLOR`/`CLICOLOR_FORCE` from the child's env before invoking it, don't inherit `os.environ` unmodified.** Some terminals (e.g. Cursor's) set `NO_COLOR=1` globally, and some Rust CLI arg-parsers error out on it before the tunnel even opens — the failure looks exactly like a connectivity/KEX problem in the harness output but is actually the child process never starting. Build an explicit `env=` dict with those vars removed and pass it to `subprocess.run`.
- **Keep the throwaway test-pack (live sandbox endpoint + private key + run command) in a separate doc from the durable decision doc, even when handing both to the same person for the same test.** The test-pack's content is disposable and gets rewritten every time the sandbox is re-provisioned (new endpoint, new key, new expiry); the decision doc is meant to outlive the test and be forwardable without leaking a live credential. When the user asks for "a doc" on the decision itself, create it fresh (`gog docs create`) rather than reusing the test-pack doc's id.
- **When provisioning a throwaway Vercel sandbox for someone else to test asynchronously (e.g. "I'll try it on my Windows box"), set the sandbox's `timeout` in hours, not the default ~30 min.** The recipient doesn't run the test the instant you hand it off — they read the doc, copy files, switch machines. A short-lived sandbox expires mid-handoff and the endpoint returns `410 Gone` on their first real attempt, burning a full round trip to re-provision and re-send new credentials. Default to `timeout: 3*60*60*1000` (3h) or longer for any sandbox whose test isn't run in the same tool call that provisions it.
- **Verify a handoff sandbox is actually reachable (probe the wss URL + a real SSH auth attempt) immediately before sending its endpoint/key to someone else**, not just right after `Sandbox.create` returns — provisioning success and "still alive when the recipient needs it" are different checks, and the gap between them is exactly where a short timeout bites.
- **When bundling a secret (private key) + script + live endpoint into one document for handoff, regenerate the whole bundle together if the endpoint changes** (e.g. after re-provisioning past a timeout) — a stale key paired with a fresh endpoint (or vice versa) fails silently with a generic auth/connection error that looks like the same class of failure as the original problem being tested, wasting a diagnostic cycle. Use one script pass that replaces both the endpoint and the key block in the same edit, then re-verify liveness before re-sending the doc link.

## IIT Patna Master sheet — column layout and row-count gotcha

The shared Master sheet ("Innovation Catalyst Internship Application", tab `Master sheet`) tracks funnel stage per candidate. Confirmed column positions (re-verify with `gog sheets get "'Master sheet'!A1:Q1" --json` before a write, since a header can shift if someone edits the sheet structure — don't assume these are permanent):
- A-F: Name, Email, Phone, College, Graduation year, GitHub.
- G: ADD Sent, H: ADD Submitted, I: ADD Result (Passed/Failed), J: ADD Feedback Summary.
- N: VVA Feedback Summary (confirmed). The VVA block (K-N) likely mirrors the ADD block's Sent/Submitted/Result/Feedback shape, but only N is directly verified — check K-M against real header text before writing to them.
- **The sheet's reported grid size (`sheetProperties.gridProperties.rowCount` from metadata) overstates actual data rows** — a sheet reporting ~1600 rows of grid can have only ~1365 rows with real content. Always compute the row count to operate on from `len(values)` on an actual `sheets get` pull, never from the grid-size metadata, before planning a batch write, append, or delete — the grid number caused a real mismatch once between "which rows are the empty-ADD block to delete" and the metadata-implied total.
- **To find candidates whose outcome diverged between two funnel stages (e.g. "who was rated hire on the earlier VVA stage but failed the later ADD stage"), filter by the earlier stage's own feedback/verdict column, then read off the later stage's columns for the same rows** — don't infer the earlier stage's verdict from the later stage's data. This cross-stage comparison is usually the actually-valuable question (it surfaces likely evaluator false negatives/positives), not either stage's raw pass/fail count alone.

## Automated e2e coverage for the candidate assessment flow (Playwright)

The repo already has a live-driving Playwright suite at `smoke/tests/smoke.spec.ts` and `smoke/tests/adversarial.spec.ts` — it runs against the real deployed `https://<internal-host>` and mints real sessions via the admin API, so it IS e2e, not a mock. Read both files before proposing new coverage; extend them, never suggest rebuilding from scratch.

- **What it already covers**: OAuth redirect, mint-session-via-admin, join → provisioning → Continue, terminal renders + WS opens + typed command echoes, Claude answers in-sandbox, heartbeat, timer countdown, early-end + transcript review, no-session state; adversarial: join-before/after-window, wrong-account, direct terminal URL without join, double-join, nonexistent session id, heartbeat identity mismatch, unauthenticated page + WS.
- **What it does NOT cover** — this is exactly the class of bug a manual candidate-facing QA pass catches and the suite doesn't: terminal reconnect under a dropped WebSocket, mouse-wheel/PgUp-PgDn scroll, typing fidelity, mouse copy from the terminal, Claude launching with no blocking permission prompt, Claude relaunching on exit, the proctoring gate actually refusing Continue when camera/mic/screen-share/recording aren't live, reload-mid-session resuming instead of 404ing, independent multi-tab terminals, split-pane resize, and the destructive violation paths (tab-switch strike, fullscreen-exit strike, devtools terminate, rejoin-blocked-after-violation). When asked to close this gap, scope new specs against this exact list rather than reinventing categories.
- **This is a needs-design=yes task even though it "just adds tests"**: each new spec provisions a real Vercel sandbox (cost + time) and the violation specs are destructive by design (they end the session) — the design must decide how these are tagged so they don't gate default CI, how sessions get created/torn down per test, and must keep the existing specs passing unchanged.
- **Be honest about what can't be driven headless.** Devtools-open detection and fullscreen-exit are hard or impossible to trigger faithfully through headless Playwright — call this out explicitly in the design rather than forcing a flaky pixel-level workaround; a documented manual-check fallback for those specific cases is an acceptable outcome.
- **Don't claim the new suite is "green" from a run that never got past provisioning.** If a live provisioning blocker is open on the pipeline, live e2e runs (existing or new) will fail at session mint/provision regardless of the spec content — write and review the specs, but hold the "suite passes" claim until a run actually completes past provisioning on the current deployed build.

## Model fallback for rate-limit resilience (Claude Code native chain)

When asked to add a fallback model so candidates don't get stuck on a 429 mid-assessment:

- **Rate limits are per-model-per-account** — falling back to a DIFFERENT model on the SAME provider account (e.g. Fireworks) dodges the ceiling entirely; no cross-provider infra or custom shim is needed.
- **Claude Code has a native fallback chain** (`--fallback-model` flag / `fallbackModel` setting) that can point model aliases (e.g. the `sonnet`/`haiku` slugs) at different underlying model deployments on the same account — so a primary→fallback swap is just aliasing, not a shim you build. Verify against current Claude Code docs exactly which failure conditions trigger the native failover (not every rate-limit error shape is guaranteed to fire it) before assuming full coverage.
- **Empirically test the actual 429 path before building on top of it** — confirm the failure surfaces in a form the fallback chain actually reacts to, on this pipeline's real Fireworks setup, rather than trusting the documented behavior alone. This is a needs-design task: which model is the fallback is a scoring-relevant decision for the user to make (the fallback model produces the answers candidates get evaluated on), not something to default silently.

## Admin helper — original supplemental skill


The TI hiring orchestrator's admin API is token-gated. The token is stored locally at `/home/ubuntu/.ti-hiring-admin-token` (chmod 600, verified to match the live `/ti/orchestrator/ADMIN_TOKEN` SSM parameter). Never print the token value.



```
ti-hiring-admin.sh <method> <path> [json-body]
```

e.g. `ti-hiring-admin.sh GET /v1/sessions/ses_...` or `ti-hiring-admin.sh POST /v1/sessions '{...}'`.

If the token is stale (401/403), refresh it from SSM and rewrite the file:

```
aws --profile trilogy --region ap-south-1 ssm get-parameter \
  --name /ti/orchestrator/ADMIN_TOKEN --with-decryption \
  --query Parameter.Value --output text > /home/ubuntu/.ti-hiring-admin-token
chmod 600 /home/ubuntu/.ti-hiring-admin-token
```

## Common operations

- Book a session: `ti-hiring-admin.sh POST /v1/sessions '{"candidateEmail":...,"candidateName":...,"scheduledStartAt":...,"durationMinutes":30,"assignment":...,"idempotencyKey":...}'` (201 or 202 + poll `/v1/scheduling-attempts/:key/status`). For bulk booking, make exactly one POST per idempotency key and persist its result before continuing; the scheduler/sweeper handles transient meet-pacer deferrals internally. Do not resend on 502 or an attempt `status: failed` while `nextAttemptAt` is non-null. Before issuing a fresh `-r2` key for purportedly terminal attempts, GET each original key's live status: snapshots can be stale, and `committed` or `failed` with a future `nextAttemptAt` is not terminal.
- Get a session: `ti-hiring-admin.sh GET /v1/sessions/:id`
- Close/terminate: `ti-hiring-admin.sh POST /v1/sessions/:id/override '{"action":"force_destroy","reason":"..."}'` (works from ready; post-freeze rows need the retention sweep or the freeze-aware override)
- Cancel (pre-join): `ti-hiring-admin.sh POST /v1/sessions/:id/cancel '{}'`
- Reschedule: `ti-hiring-admin.sh PATCH /v1/sessions/:id '{"scheduledStartAt":...}'`
- Re-fire a booked session's locked invite mail without touching its schedule: `ti-hiring-admin.sh GET "/v1/sessions/lookup?email=<URL-encoded-email>"` to confirm the correct session and its name/start, then `ti-hiring-admin.sh PATCH /v1/sessions/:id '{"candidateName":"<exact candidate name>","sendEmail":true}'`. The helper appends `[http NNN]` to stdout on its own line; strip it before parsing JSON and check the HTTP status. `candidateName` is required for the mail. Do not infer delivery from a successful PATCH: verify `gog --account <ops-mailbox> --client startgreat gmail search 'in:sent to:<email>' --max 3` after loading `GOG_KEYRING_PASSWORD` from `~/.hermes/.env`; check the DATE column for the current intended date, as older emails to cancelled sessions are stale. Pace Gmail searches at least 12 seconds apart and back off 90 seconds on quota 403. If PATCH fails, preserve the full output and retry only once after 60 seconds. A successful PATCH can coexist with no sent-mail record if the asynchronous mail queue is stuck; report this honestly rather than repeating the PATCH blindly.

The token is also accepted for the operator-scoped routes; for a dedicated operator token use `/ti/orchestrator/OPERATOR_TOKEN` from SSM the same way.

## Recover a terminated infra-backed session's missing workspace capture

- First read `/v1/sessions/:id/detail` for `sandbox_id`, `infra_capture_s3_uri`, and status; do not invoke `/v1/admin/reconcile` to recover capture: its sweeps include **destructive orphan sandbox cleanup** and do not mint workspace archives. `retry_upload` in the override route needs an existing spool and is not a capture route.
- When no non-destructive API route can mint the capture, use the Vercel sandbox command API on the verified running sandbox. Read `/ti/orchestrator/VERCEL_TOKEN` from SSM into a private process variable; never print/log it. `POST https://api.vercel.com/v2/sandboxes/sessions/{vercelSessionId}/cmd?teamId=team_OciwdTBwczi5C3DxiiwfnpT1` with `{ "command":"sh", "args":["-c","cd /workspace && tar czf /tmp/workspace.tar.gz --exclude node_modules . && base64 -w0 /tmp/workspace.tar.gz"], "wait":true, "logs":true }`. The response is `application/x-ndjson`: concatenate `data` from records where `stream` is `stdout`, verify final `command.exitCode` is zero, base64-decode and validate the gzip tarball. Never print its full stdout/base64.
- Check an existing capture's real key before upload. The observed production layout is `s3://ti-hiring-captures-<aws-account>/captures/ti-ses-{uuid}/ses_{uuid}.tar.gz` (not a `.../ses_{uuid}/workspace.tar.gz` suffix). Check that the target doesn't exist before uploading; after `aws s3 cp`, verify nonzero `s3api head-object ContentLength` and exact `aws s3 ls` key. Clean up local archives after verification.
- The S3 upload alone does **not** populate the orchestrator's `infra_capture_s3_uri` column or candidate-facing `infraCapture`; read `/v1/sessions/:id` back to verify. If null remains, hand off the URI for a separately authorized DB/API backfill. Do not destroy restored sandboxes as part of capture rescue.
