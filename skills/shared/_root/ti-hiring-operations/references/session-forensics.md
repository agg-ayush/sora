# Session forensics via the admin API

Use for batch status counts, per-candidate RCA (media gate, teardown, concerns) and evidence-table exports. For serving a batch's eval results for review (GCS reports, S3 prompts, filtered list server) see `references/eval-review-servers.md`. For grading one candidate's submitted work by re-running it from the S3 capture see `references/candidate-work-review.md`.

## Parsing helper output

`ti-hiring-admin.sh` appends a trailing `\n[http NNN]` status line after the JSON body. Strip it before parsing: `json.loads(raw[:raw.rfind('\n[http')])`. The list endpoint returns a list or `{"sessions": [...]}`; handle both.

## List vs detail shapes

- `GET /v1/sessions?limit=500` is camelCase (`candidateEmail`, `scheduledStartAt`, `endReason`, `meetUrl`, `finalizeError`, `infraCapture`). It omits `setup_trouble_note`, `recall_bot_id` and events.
- `GET /v1/sessions/:id/detail` is the raw snake_case row (`candidate_email`, `recall_bot_id`, `setup_trouble_note`, `concern_note`, `infra_capture_s3_uri`, `infra_teardown_*`) plus an `events` array.
- Join both by session id when a table needs email (list) plus recall id or notes (detail). Never treat a field missing from one shape as missing data; check the other shape first.

## Quick lookups from a truncated session id

Ayush often pastes a cut-off id (`ses_4d645660-0d17-4f`) and asks for one field (Meet link, Recall id). A truncated id 404s on `/v1/sessions/:id`; never guess the tail. Fetch the list once, prefix-match `id`, take `meetUrl`/`candidateEmail`/`status` from the row, then hit `/detail` on the full id only for `recall_bot_id`. Reply with the full id, candidate name/email and the asked field; give Recall ids as the dashboard link `https://ap-northeast-1.recall.ai/dashboard/explorer/bot/<id>?order=desc&experience=new`. Batch several lookups into one script over a single list fetch.

## Batch slicing

Identify a batch by `scheduledStartAt` prefix (UTC); report times to Ayush in IST. Count `status` and `endReason`, plus `finalizeError` and populated `infraCapture` for capture health. `endReason` values: `candidate_done`, `timer`, `forfeited` (never joined, `joinedAt` null), `ready_expired_media_gate`, `ready_expired_teardown_incomplete` (also a gate expiry; only the cleanup afterwards differed).

## Invite-vs-session email mismatch (check before calling forfeits no-shows)

The app finds a candidate's session by their signed-in email. If the invite went to one address and the session was booked under another (gmail vs college address, double form submissions, truncated emails like `@dtu.a`), the candidate cannot reach their session and lands as `forfeited`. Before reporting forfeit counts or a candidate's "never joined":

1. Load the invite-send manifest/log emails and the day's sessions (list shape), lowercase both, and drop smoke-test (`*ti-hiring-smoke.test`) and operator (`@<org-domain>`) accounts.
2. Set-diff mailed emails against session `candidateEmail`. For each mailed-without-session address, name-match (normalized name inside the session email local part) to find the same student's session under a different address.
3. Report three buckets: certain mismatches (unique name match), fuzzy (common first names matching several sessions; verify by hand), and mailed with no session at all. Answer "where was the mail sent" from the send manifest, not from the session row.

Prevention belongs at batch setup: one canonical-email manifest drives both mail and booking.

### Rebooking candidates who submitted an email correction

1. Match correction-form respondents to the batch sheet by normalized NAME (email only as a tiebreak): the batch sheet carries the wrong email by definition, so email matching "misses" students who are actually there. Pull the sheet as a JSON grid, not TSV (multi-line cells break line parsing). Report buckets: matched with batch/row, ambiguous, not in sheet.
2. Show a plain-text mapping (name, correct email, original batch, target batch) and wait for confirmation before any API write. When Ayush asks for a mapping "for my view", do zero API calls.
3. Moving them means cancel + rebook under the CORRECT email; a PATCH of `scheduledStartAt` alone keeps the wrong email and defeats the purpose. Never reschedule before the email is fixed.
4. Base "already ran / not yet run" splits on the original bookings, never on intermediate states the agent itself created.
5. Book with `sendEmail: false` unless told otherwise. When told to send, verify each delivery in startgreat Sent (dated today). If the orchestrator's mail queue does not deliver, send manually from startgreat using the locked invite template's HTML body (button, bold slot line, full requirements), never a plain-text approximation; pace ~13s apart in a background process with notify.
6. Verify bookings via per-email `/v1/sessions/lookup`; strip the helper's `[http NNN]` line before filtering output, or every check falsely reports missing.

Answer status questions ("are these booked", "new or old emails", "mails sent?") with yes/no in the first line plus only the exceptions; do not launch a fresh investigation for a yes/no question when the state is already known.

## Classifying gate outcomes for Ayush

- Classify by what the candidate experienced, not by the internal cleanup path. Every candidate who got a sandbox but never crossed the gate is ONE class (media gate issue), whether the row ended `ready_expired_media_gate` or `ready_expired_teardown_incomplete`. Do not mix unrelated incidents (a teardown race, a stuck sweeper) into candidate-facing verdicts; those are infra accounting, kept separate.
- Verdict column wording: `OUR BUG` / `CANDIDATE` only where per-session RCA evidence proves it; `UNKNOWN - <why>` when the evidence source itself is missing (e.g. the Recall bot produced no participant artifact); `MEDIA GATE - not RCA'd` before any RCA pass. Never imply a verdict without evidence. Report the split as counts (e.g. N/N/N) and keep the doc's table matching the latest RCA pass exactly.
- Count gate overrides from `override_requested` / `override_click` events across the day's sessions, excluding operator test sessions (ours/colleague's). Judge whether the override worked from the outcome (`endReason` `candidate_done` or `timer` means they entered); `liveAt` on the list shape is not reliable for this.
- When a stakeholder shares their own list (e.g. "the 22 who never got past the gate"), reconcile it against the admin API by session id and say whether it matches before adding anything.

## Events array

Each event is `{session_id, ts, event, detail_json}`; the type key is `event` (not `kind`) and `detail_json` is a JSON string. The row has no `mediaGate` object; reconstruct gate state from events:

- `media_gate_recording_poll`: `{botId, code:"in_call_recording"}` on success, `{botId, error:true}` on a failed Recall read. Count ok vs error to measure poll flakiness.
- `media_gate_fail_open`: `{openedAt, missing:[...]}` lists the camera/screenshare/mic signals that were waived.
- `ready_expired`: `{phoneGate:true}` means the phone-camera leg never credited; `{mediaGate:true}` means the gate never opened for another reason. This field separates phone-detection failures from other gate expiries.
- Also: `joined`, `candidate_start_ready`, `candidate_joined_meet`, `candidate_left_meet`, `concern_submitted`, `trouble_exit`, `sandbox_destroyed`, `recall_stopped`.

State findings from these counts, not from the user's hypothesis; hand deeper multi-source RCA (CloudWatch + Recall API) to a subagent.

## Verifying bot presence straight from Recall

When the question is "was our bot in the call / did the candidate ever join the Meet", confirm from Recall rather than inferring from our poll events:

1. Use the orchestrator's own key from SSM, never a `RECALL_API_KEY` already in the local shell (that one belongs to another workspace/region and returns 401 `authentication_failed`): `RK=$(aws --profile trilogy --region ap-south-1 ssm get-parameter --name /ti/orchestrator/RECALL_API_KEY --with-decryption --query Parameter.Value --output text)`. Do not echo it.
2. Base URL is the task-def env `RECALL_API_URL` (`https://ap-northeast-1.recall.ai`, no `api.` prefix): `curl -sS "$RECALL_API_URL/api/v1/bot/<botId>/" -H "Authorization: Bearer $RK"`.
3. Read `status_changes[]` (`created_at`, `code`, `sub_code`); the bot object has no top-level `status`. Normal trail: `joining_call` -> `in_call_not_recording` -> `in_call_recording` -> `call_ended (bot_received_leave_call)` -> `recording_done` -> `done`.
4. Bots are created with `recording_config.start_recording_on: participant_join`, so `in_call_recording` marks the moment a non-bot participant joined. A bot that sits `in_call_not_recording` until `call_ended` is Recall-side proof nobody (the candidate) ever entered the Meet; the bot was present, so it is not a bot/infra gap. Intermittent `{error:true}` recording polls in our events are pacer/read flakiness, not bot absence.

Report as a per-candidate line: bot joined at T, recording started at T (or never), and what that implies about the candidate joining.

## Phone-gate expiry RCA (`ready_expired {phoneGate:true}`)

Check which identity rule the deployed build runs before blaming Recall or the read pacer (`git show <deployed-sha>:orchestrator/src/lifecycle/media-gate.ts` and the leave cascade in `routes-recall-webhook.ts`). The mechanism below is the phantom-row bug; builds whose leave cascade writes the screenshare row only `ifExists` and key identity on the currently-connected sharer do not have it, so a newer expiry needs a fresh RCA rather than this verdict by default. Participant webhooks (join/leave/webcam/screenshare) do not go through the Recall read pacer; `recall_pacer_exhausted` only hits the recording-status GET, which usually recovers before expiry. The phone check treats every participant that has any `screenshare` projection row as "the laptop" and needs exactly one such id. A `candidate_left_meet` webhook writes a `screenshare:disconnected` row even for a participant that never shared, so a device that joined and left (or two real sharers, or the phone itself sharing) makes the laptop ambiguous and the phone camera is never credited. To prove it per session: replay the events for leave-generated share rows plus real `screenshare_on`, and compare with Recall's participant artifact (`mobile_app` joined with webcam on before expiry). A filter on `screenshare_on` alone misses the phantom rows. Fail-open never waives the phone leg.

Verdict rules for a gate RCA (an RCA that breaks these gets rejected as not good enough):
- A verdict must follow from its own evidence column. "OUR BUG" requires positive proof the candidate did their whole part (a `mobile_app` participant with webcam on before expiry AND at least one genuine `screenshare_on` from a device) AND our code failing to credit it. No phone participant / no mobile evidence means `CANDIDATE - phone never joined`; zero genuine `screenshare_on` in the whole session means `CANDIDATE - never screenshared` (no laptop identity can exist, so the refusal is correct), never "our bug".
- The poisoning trigger to check per session: any `candidate_left_meet` by any participant before the candidate crossed the gate, or more than one participant with a real share, permanently blocks the phone credit for that session. Report it that way ("left at T before entering"); do not split sessions into separate "shapes" when the user is asking whether they share the same trigger.
- Platform stamps (`mobile_app`/`desktop`) on webhook events can be swapped between a candidate's two devices; use participant names and join order alongside the stamp before concluding which device is the phone.
- Recall participant artifacts are a proxy; the recording is ground truth. State in the report which sessions' recordings were actually watched and which verdicts rest on artifacts alone, so Ayush knows which rows to spot-check.
- Ayush's per-row review of a recording (doc comment like "actually didn't join" / "actual bug") overrides the RCA verdict. Apply the flip in the table, recount the totals and report the corrected split.
- When Ayush asks a narrow question about one session or the group ("was the camera on at the first attempt", "did they all leave before trying"), answer exactly that in the first line from the event trail, then stop. Do not re-litigate verdicts or pivot to a different pattern than the one asked about. Give per-session event timelines in IST (UTC+5:30), not UTC.
- Gate design direction (settled by Ayush): trust Recall's own output, keep each signal an independent flag. No inferred device identity: any `mobile_app` participant is the phone, any non-`mobile_app` is desktop; no sole-screensharer laptop inference. Recall event in, DB write, done. A candidate turning the camera off after passing is an accepted risk covered by the recording, not something the gate re-polices. Signals must persist in the DB once the candidate continues, overrides or trouble-exits; current-state re-checks are acceptable only while the candidate is still on the media page. When reviewing or carding gate changes, measure them against this, and do not re-propose stricter identity inference.
- Gate latency: candidates read a slow-ticking signal as a fault, so a 10-25s lag is a bug. Before tuning a poll interval, check whether the vendor pushes the same state as a webhook we never subscribed to. The recording leg is the case in point: it comes from a pacer-throttled Recall bot-status GET (`media_gate_recording_poll`), while Recall's bot status webhooks (`bot.in_call_recording`, `bot.recording_permission_denied`, `bot.call_ended`, `bot.fatal`) push it in real time. The dispatch subscription list (`PARTICIPANT_WEBHOOK_EVENTS` in `providers/recall.ts`) and the handler's `ACTIONS` map in `routes-recall-webhook.ts` are where a new event gets wired; verify the bot-status delivery uses the same endpoint auth before assuming it does. The wrapper's own gate poll (`GATE_POLL_INTERVAL_MS`, 2s) is not the bottleneck.
- For a per-session evidence pass a subagent can do, pull each bot's participant timeline (join/leave, platform, webcam-on windows) next to our gate events so the human recording check goes fast.

Concern notes: the row's `concern_note` holds only the latest write, and a machine auto-report (e.g. a finalize-failed concern) can overwrite a candidate's real note. Every concern POST also appends a `concern_submitted` event carrying the full text, so build any concerns list from the events array, not the row column, and check for rows whose column holds an auto-report.

`setup_trouble_note` is the gate-page "I'm having trouble" autosave, stored on the row (detail shape only). It is separate from `trouble_exit`. Candidates who type a note almost never click submit-and-exit, so count both before you say the exit path is broken.

## Batch-wide editor/sandbox regression ("why only today")

When many candidates in one batch report the editor not opening or being slow:

1. **Blast radius.** Pull every status (`?status=ended`, `terminated`, `frozen`, `live`; the unfiltered list is paginated oldest-first and misses the recent end), slice by `joinedAt` date, bucket `concern_submitted` texts by symptom and report unique sessions and rate against joined sessions.
2. **Right baseline.** Compare with the last batch of similar size, not literally yesterday. Compare complaint type as well as rate: a shift from "agent slow" to "editor won't open" is evidence of a new failure mode.
3. **What changed since that batch.** "No commit today" is not "nothing changed". Find the running task-def revision and its deploy time; if it landed after the baseline batch ended, today is the first real batch on that image. Diff image tag and env of old vs new revision with `aws ecs describe-task-definition --task-definition ti-orchestrator:REV --query 'taskDefinition.[containerDefinitions[0].image, containerDefinitions[0].environment]'`. Read `contracts/snapshots.json` via `git show origin/main:` (local checkout can be stale) and compare `bakedAt` to batch dates.
4. **Per-assignment counts (the shape Ayush asks for).** Report `assignment | complaints / joined | rate` plus a TOTAL row and the session-id list per assignment. Denominator is sessions with `joinedAt` set (filter by `joinedAt` date, else `scheduledStartAt`); no-shows never saw the editor and dilute the rate, so give the scheduled-denominator view only as a secondary line. A bimodal split (some assignments 0%, others ~30%) rules out fleet-wide causes and points at per-assignment inputs (snapshot bake, workspace). Then **cross-tab** joined sessions by join cohort x assignment (`infra_repo_path` on the detail row) and compute complaint rate per cell. Note operator/test participants in a cohort: a good-machine tester complaining weakens the candidate-device explanation.
5. **Eliminate with evidence**, one line each: deploy, snapshot, infra API latency (p50/p95 of structured `infra request` log `durationMs` per window), static assets (direct probe), workspace size, background bake/verify sweeps, recurring warnings, sandbox host metrics (active CPU, memory, region, vCPU and egress, concern vs OK; similar CPU/mem clears host throttling, higher egress on concern sandboxes means reload/retry churn).
5a. **Workspace captures are the ground truth for what the candidate actually got.** `infra_capture_s3_uri` on the detail row is a tar.gz; download to scratch with `aws --profile trilogy --region ap-south-1 s3 cp`. Inside: `workspace/` work products and `.claude/projects/-workspace/<uuid>.jsonl` (the candidate's Claude session). Per session compute: Claude used at all and what work exists (separates "never got in" from "got in late"), gap from `joined_at` to the first jsonl `timestamp` (time to first usable environment), and user->assistant response latency median/p90 (clears or implicates the agent itself). Always compute the same gap on a sample of OK sessions from the same cohort: everyone has reading time before first use, so only the difference is evidence.
5c. **Snapshot A/B mechanics.** Best isolation pair is one assignment with an old-good and a new-suspect bake (`contracts/snapshots.json`). A clone from a snapshot does not run the editor; it starts only on `$TI_HOME/self/provision.sh --converge` (`TI_HOME` is `/opt/ti-hiring` in baked snapshots), then is ready when `curl -sf http://127.0.0.1:8080/healthz` succeeds. The converge needs the infra service's full create env (`convergeEnv` plus `REPO_PATH`, and `REPO_URL` for `WORKSPACE_SOURCE=clone`; see `createSandbox` in `orchestrator/src/infra/service.ts`). Passing only `EDITOR_PORT` exits immediately with `REPO_URL is required`, and a healthz timeout then says nothing about the bake. Check `/tmp/converge.log` before reading a timeout as a result. Also diff `$TI_HOME/state.env` and `/workspace/.claude/settings.json` between the two bakes: config baked into a snapshot (e.g. a different default model) is a real per-assignment difference.
5d. **Silent victims and per-cohort usage.** Concerns undercount: candidates who never get an editor often press done without filing anything. For a suspect join cohort, check every session's capture for a Claude jsonl; a tiny capture (about 6-8 KB, no jsonl) plus `candidate_done` means they never reached the terminal. Compare against an earlier same-day cohort as the baseline (a healthy cohort shows roughly three quarters using Claude). A cohort far below baseline is batch-level evidence even when only one candidate complained.
5e. **Probing a sandbox URL.** Probe `accessUrl + /?folder=/workspace` only while the session is live. After teardown the route returns `502 SANDBOX_NOT_LISTENING` (destroyed) or `410 SANDBOX_STOPPED`; both are expected post-teardown states, never incident evidence. To check the route path now, probe several currently live peers instead (healthy: 200 in about 1s).
5f. **Recording frames.** The recording exists only after the session ends: the `recording_ready` event (detail `fileId`, `bytes`) appears seconds after `endsAt`. For a live session, poll `/detail` for that event in loops kept under ~270s per `execute_code` call (the cell is killed at 300s and loses state), or end the turn and come back after `endsAt`. Take the `fileId` programmatically from the `recording_ready` detail, never hand-typed (one wrong character 404s). The same applies to every recording link put in a reply: emit the `url` from the event, never retype it. When Ayush says a link 404s, or a `gog drive` call 404s on a file that `drive search "ses_<prefix>"` lists, first diff the id character by character against the event/search id; a transposed character looks exactly like a broken permission or deleted file, and diagnosing permissions first wastes the round and misreports the cause. A correct id can still 404 for a minute or two after `recording_ready` while Drive settles, so retry after ~60s before calling it missing. Before extracting, check the flags: if screenshare never turned on (`media_gate_fail_open` missing `screenshare` and no `screenshare_on` event), the recording only shows camera tiles and cannot show the screen, so say that rather than dispatching frame analysis for screen state. Then `gog drive download <fileId> --output rec.mp4`, `ffprobe` duration, extract frames at fixed offsets with `ffmpeg -ss T -i rec.mp4 -frames:v 1 -q:v 3 tT.jpg`, map offsets to wall clock from the recording start (offset 0 = the first `media_gate_recording_poll` with `code: in_call_recording`, or Recall's `in_call_recording` status change, since the bot records from first participant join; sanity-check that start + `ffprobe` duration lands near `endsAt`), compute the concern's offset from that before choosing frames, then hand the frames to a vision subagent (images param, at most 8 per task; pick the offsets that bracket `entered` and the concern ts) asking per frame: which page (instructions, `sb-*.vercel.run`, Meet) and blank white vs spinner vs error vs loaded editor. First inspect whether the recording is an actual screenshare or only a phone camera pointed edge-on at the laptop: a narrow, blurred slice of the display cannot prove a URL, editor state, terminal, Claude or error, even after rotation/OCR. Say "not discernible" rather than "absent," and seek screenshare or browser/server logs for a usable-time bound. Blank white on the sandbox URL across different browsers/OSes points at delivery, not the candidate's device.
5b. **Ask before writes.** Recordings/transcripts and provider request logs are read-only; a fresh sandbox clone timed from the new vs old snapshot is the decisive experiment but creates resources, so propose it and wait for approval.
6. **Report** as changed / eliminated / strongest signal / remaining checks ordered by decisiveness, naming the one experiment that breaks the confound (e.g. concurrent synthetic editor clients against one sandbox per suspect snapshot).

Pitfalls:
- Before naming a log line as the cause, check it on healthy sessions in the same window (same snapshot, `candidate_done`). The pane-health "no route for ttyd port 7681" warning and `ti-bake-*` zero-port warnings fire on every infra_http session and around the clock; they are noise. Asserting a signal and retracting it later costs trust, so verify first.
- Orchestrator logs see only the infra API, not browser-to-sandbox editor traffic. Clean sandbox-create latency does not clear the sandbox; say what is unobserved instead of calling infra healthy.
- When cohort and snapshot changed together, report correlation and the confound, not a root cause.
- When asked whether the agent (claude) "failed" for a candidate, first check whether they ever reached a terminal; a session with no terminal never tested the agent, so the framing is wrong.
- DevFactory SAML creds expire hourly during a long RCA; S3 `head-object` then fails with a bare `400 Bad Request`, not ExpiredToken. Confirm with `sts get-caller-identity`, run `/home/ubuntu/.hermes/scripts/aws-creds-refresh.sh`, retry.

## Single-concern triage ("is this our end?")

When Ayush replies to one concern/trouble-exit asking what went wrong:

1. Detail timeline first (events minus `media_gate_recording_poll`): joined -> `candidate_start_ready` gap (sandbox health), Meet joins per participantId with platform, webcam/mic/screenshare, `media_gate_fail_open`, `entered`, every `concern_submitted`, `ready_expired` detail, `endReason`.
2. Ended session: pull the capture (5a) and Vercel sandbox stats by name. If AWS is unavailable (S3 capture and watchdog diagnostics unreachable), do not stall on it: the detail row's `infraCapture` size and transcript count already classify the shape (about 6-8 KB with zero transcripts = Claude never held a conversation), and the Drive recording needs only gog, so move straight to frames and name the S3 diagnostics as the missing evidence leg in the reply; editor delay = `entered` -> first jsonl timestamp; non-trivial egress plus work dirs means they got in eventually. Then recording frames (5f) via a background subagent; give a partial verdict meanwhile and confirm when frames land.
3. "Claude was slow / not responding for N minutes": count user messages and measure user->assistant latency in the jsonl before agreeing. Then map the claimed window onto the jsonl: list gaps between consecutive `type: user` records and check what the last assistant message before each gap says. A gap that follows an assistant completion ("Done", a final summary) is Claude waiting on the candidate, not Claude stuck; candidates misremember their own idle time as the agent hanging. A single long response (tens of seconds) next to a multi-minute candidate gap that matches a reported power cut or network drop is the candidate's connection, not the model. Seconds of latency on one or two messages means the perceived slowness was the editor wait, not the model. Report median/p90/max latency, the idle gaps with timestamps, and what work exists in the capture.
   - Live or `frozen` sessions: the capture lands at freeze (seconds after the timer), so a concern filed in the last minute is already checkable right after `frozen`.
   - "Claude not working" on a LIVE session: verify inside the sandbox (see "Inspecting a live candidate sandbox") instead of waiting for the capture. Run `claude --version` and one harmless `claude -p "say ok"` as the sandbox user (proves binary + gateway end to end), time a request to the gateway, then read candidate-side state: `ls -la ~/.claude/sessions/` and `~/.claude/projects/` (an empty sessions dir means no conversation ever started), `~/.claude.json` mtime vs `entered` (onboarding completed at that time), `ps aux | grep -c '[c]laude'` (running now) and pty count (terminal opened). "Onboarding done, zero messages, agent answers our probe" means the agent works and something on the candidate's screen read as broken; get the recording frames for the concern window to see what they saw, and do not assert a specific on-screen cause (an error banner, a prompt) before the frames confirm it.
   - "Claude slow / no response for N minutes" on a LIVE session: read the conversation logs in place instead of waiting for the capture. List `/home/vercel-sandbox/.claude/projects/-workspace/*.jsonl` with size and mtime (one file per conversation), pull each with `base64 -w0 <file>` through the cmd endpoint and parse the records locally (do not grep JSON in the shell; nested content breaks the patterns). Per file, print the user-text prompts and assistant text with timestamps, then `tail` the raw record types. A wedged conversation looks like: normal second-level replies, a final assistant `tool_use`, then nothing until a `queue-operation` record minutes later, while the claude process (`ps aux | grep '[c]laude'`, start time per PID) is still alive. If a newer file/process answers in seconds on the same sandbox and model, the cause is one hung conversation, not gateway or model latency; say so, confirm the claim is true for that window, and note that starting a fresh conversation (Esc or relaunching Claude) recovers it. Measure the claimed duration from the stall point, not the first prompt.
   - "Claude didn't work at all" on an ENDED session: a ~7 KB capture with only starter files and no jsonl means Claude never held a conversation. Frames showing a fully loaded editor where the candidate only browsed files, with no terminal or Claude session visible, give the verdict "editor fine on our side, Claude genuinely never ran for them". Report it as partially true (accurate outcome, infra healthy) and name peers on the same infra who used Claude normally. Frames every ~5 min cannot tell a hung Claude panel from one never opened, so say the cause is undetermined unless denser frames around `entered` show it.
   - Batch-level "Claude stuck / not answering" cluster (several candidates, same cohort): measure two numbers per conversation from the captures, for complainers AND a baseline of non-complaining sessions on the SAME assignment and cohort. (a) TTFT: each `type: user` record -> first following `type: assistant` record. (b) Turn wall-time: user record -> last assistant record before the next user record. Then list the turns with TTFT > 60s and print their prompt text. A pasted full problem statement ("What you are building ...") as the opening prompt can sit 1.5-3.5 min before the first token while the panel shows only "thinking", then run a multi-minute tool chain; the candidate reads that as hung, files a concern and re-pastes (extra conversations, `queue-operation` records). Short prompts on the same assignment stay at ~2s TTFT and seconds-long turns, which clears gateway/model degradation. Report per complainer the long-TTFT turns with their prompt shape, the baseline distribution (median/p90/max, count over 60s/120s), and only then the cause; give an untested mitigation (effort setting, prompting guidance, loading hint) as a proposal, not a verified fix.
   - jsonl parsing pitfalls for these metrics: user prompts are often list-form `message.content` (`text` parts), while top-level `content` can be null. A `isinstance(content, str)` filter silently drops them and returns empty results that look like "no data"; `stop_reason: end_turn` is not on every final assistant record, so do not key turn ends on it. When a metric comes back empty on sessions known to have used Claude, fix the parser before drawing any conclusion. Exclude `isMeta`, tool-result parts, interrupt markers, `<system-reminder>`, `<local-command...>`, `<command-name>`/`<command-message>` and `<task-notification>` records from real-prompt TTFT; command-name records otherwise produce fictitious multi-minute TTFT. Match each real prompt to the next assistant record in its own JSONL conversation, not a concurrent sidechain, and note if conversation forks copy the same prompt/timestamp into several files. Compare entered-to-first-editor with wrapper `editor_opened`-to-first-editor; a long interval entirely before `editor_opened` does not by itself prove slow shell loading.

For frames, extract every ~20s across the first ~7 minutes after `entered` (plus around the concern ts) and ask per frame for the right-panel state (welcome/sign-in, empty input, typed text, error or warning text, active conversation) and any terminal with typing, not just "is a terminal open".

Use when a concern needs ground truth from inside a running sandbox (wrong workspace, missing files, config).

1. Find the sandbox: sandbox name is `ti-ses-<full session uuid>`, so fetch it directly with `GET https://api.vercel.com/v2/sandboxes/<name>?teamId=<team>&projectId=<orchestrator project>`. The list endpoint (`/v2/sandboxes?teamId=&project=&limit=50`, follow `next`) does not reliably surface every live sandbox on page 1, so do not conclude "not found" from it. Use `sandbox.currentSessionId` (`sbx_...`) for commands, not the name.

2. Run commands: `POST /v2/sandboxes/sessions/<sbx id>/cmd?teamId=<team>` with `{"command":"sh","args":["-c",<script>],"wait":true,"logs":true}`; the response is NDJSON with `stdout`/`stderr` stream records and a final `command.exitCode`. Base64-encode multi-line scripts (`echo <b64> | base64 -d | sh`) to avoid quoting breakage.
3. Keep it strictly read-only (`cat`, `ls`, `head`, `find`): it is a candidate's live environment. Grep out `TOKEN` lines when printing `/opt/ti-hiring/state.env`.

Launched Extension Host Process` mark when the browser's editor connection actually landed (169.254.0.1 is the Vercel tunnel), and `The client has disconnected gracefully` marks them closing it. Count pty processes (`ps aux | grep -cE '[p]ty|[t]erminal'`) to tell whether a terminal was ever opened. Report per candidate: server healthy (yes/no), first connection time vs join and concern, terminal opened, and a concrete live action (refresh the editor page) while the session is still running.

**Claude panel watchdog log (blank/empty Claude panel concerns).** Snapshots with the panel watchdog write `/home/vercel-sandbox/.local/state/claude-panel/events.log`, one line per editor window (`host=<pid>`): `editor window started`, `panel loaded after Ns`, `panel not loaded after 90s, reloading the panel`, `panel still not loaded after Ns, asking to reload the editor` (sticky notice with a Reload editor button), `window closed`. `started/<pid>` markers list windows. Then confirm Claude is running and a `projects/-workspace/*.jsonl` exists.
- To check whether a sandbox runs the fixed snapshot, look for the baked binary (`/opt/ti-hiring/bin/claude-panel-filter`), not the watchdog state dir: the dir is created only when the first editor window starts, so it is absent for a candidate who has not opened the editor yet. Concluding "fixes not deployed" from a missing state dir is wrong and has to be retracted.

Count `reconnected`/`disconnected` in the editor log separately; graceful disconnections alone do not prove bad candidate networking. Check for `ptyHost terminated unexpectedly` near the candidate's concern; this can corroborate editor failure even if Claude had worked earlier.

**Batch watchdog/capture triangulation.** In S3 `diagnostics/<sandbox>/<session>/`, use `claude-panel-events.log` and `editor-logs.txt` together; count panel reloads and `panel loaded` *per host PID*, because two concurrent windows can disagree (one healthy conversation does not disprove another window's persistent reload churn). **Reading captured watchdog/editor diagnostics.** Teardown diagnostics are stored under `s3://ti-hiring-captures-<aws-account>/diagnostics/ti-ses-<uuid>/ses_<uuid>/` as `claude-panel-events.log` (which may be absent if no window started) and `editor-logs.txt`. ## RCA write-up shape

An RCA doc for Ayush is a concise technical document a human reads top to bottom, not a log/evidence dump or investigation narrative. The reference bar is the team's SSH-orchestrator-race RCA; when another RCA in the same project exists, read it first and match its structure and density. Sections in order:

1. **Title**: `RCA: <mechanism> <effect> (<date>)`. Name the mechanism, not the symptom.
2. **TLDR**: 5-7 crisp bullets, one short sentence each, labelled like the reference RCA (Bug / Effect / Trigger / Blast radius / Why not caught earlier / Fix). Name it as a defect ("the leave handler records non-sharers as sharers and never cleans the rows"), never as neutral system behavior ("the system requires exactly one sharer"). Pitch the register between plain English and code: name the component and the wrong action precisely, but no identifiers, table names or SQL (those belong in the code-path section). Always include a "why it was not caught earlier" bullet. Cut any bullet that restates another or spells out an obvious consequence ("no action on their side could change the outcome"). A reader who stops here knows what broke and why.
3. **Timeline table** (UTC; columns Time | Event | Evidence): commits that introduced the behavior (short hash + what changed), first prod occurrence, one representative case second-by-second, each wave. Evidence is a short source tag (git, main log, ssh log, admin API, Recall artifact), never pasted log lines.
4. **The code path**: numbered subsections (1a, 1b...), each with file:line at the deployed SHA, the minimal code/SQL excerpt that proves it, then plain sentences. End with the resulting broken state.
5. **Why it showed up when it did**: git provenance with dates, the volume curve that turned a latent bug into a cohort-level one, the test gap (shapes covered vs the shape that broke).
6. **Tally**: counts per verdict, session ids listed once; recovered vs lost; escape-hatch counts (overrides).
7. **Why no alarm fired**: which filters/alarms exist on which log groups, why none matched, what misled operators (red herrings).
8. **Impact**: one line per affected group.
9. **Recommended fixes, smallest first**: immediate mitigation, code invariant, defence in depth, tests for the exact missing shapes, alarms; include any "do not take the obvious simplification because X" warning.

Formatting: write the RCA as markdown with real `#`/`##`/`###` headings and pipe tables (the timeline must be a native table), push with `docs write --replace --markdown`, and check `docs structure` for HEADING/TABLE types before saying it renders. `docs cat` always prints flattened text, so it can neither prove nor disprove rendering; never report "rendered" from a `cat` readback or from the write's exit status. When asked to "format/render the RCA as markdown", run the em-dash/Oxford-comma sweep on the source file before pushing (replace ` — ` with a comma, colon or period), and give the absolute path of the markdown master too. Keep the markdown source file as the editable master; never regenerate an RCA by re-parsing `docs cat` output, which is tab-separated plain text with the structure already lost.

Scope the RCA to one mechanism. Other bugs from the same batch (a dead button, an SSH teardown race, a finalize failure) get their own RCA or card even if they hit the same candidates; strip them from the TLDR, timeline, tally, impact and fixes, and drop columns that only carry another incident's values (e.g. an end-reason column full of teardown codes) from shared tables.

No internal process narration ("RCA pass 2", "the subagent found"), no named-person attribution, no em dashes or Oxford commas. Per-session evidence tables go in separate tabs, referenced from the main tab, never inline. When the RCA belongs with an existing tracking doc (verdict table, concerns list), write it as a tab there too so verdicts and explanation sit together.
