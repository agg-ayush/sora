# Candidate issue-email triage (VVA vs technical)

Moved out of SKILL.md for size. Applies when bucketing student issue emails into categories (VVA/interview vs ADD/technical, or "our fault" vs "candidate's fault"):

- Keyword-match bucketing is a first pass only — always read every snippet by hand before reporting the split. A keyword hit on "video call"/"camera"/"interview" can catch a technical-assessment mail that only mentions checking the Meet tab, and miss a genuine interview complaint phrased without any trigger word. Read each thread's actual content and re-bucket manually; report the corrected split, never the raw keyword-match counts.
- A prescribed `newer_than:3d` search only covers the last 3 days — if the task cutoff is older (e.g. Sep 18), page the gap with a second `after:YYYY/MM/DD before:YYYY/MM/DD` search. The window is dominated by SENT invite-blast noise and ~40 RSVP Accepted/Declined threads (filter by subject prefix, never read them); real issue reports sit at the tail end of the pages. Quota economics: each 60-thread search page costs query units and the inbox paginates slowly — budget ~5-6 pages for a 2-week window, and stop the moment a 403 rateLimitExceeded (Total Query Cost) returns, saving partial progress. A prior partial run's `/tmp/student-buckets.json` may already contain verified bucketed entries (e.g. SENT+INBOX "Re: Your assessment" reply threads that a `-from:me` metadata search hides) — read it before writing and MERGE, never overwrite.
- gog in a cron/headless context needs `GOG_KEYRING_PASSWORD` set (read it from `/home/ubuntu/.config/gogcli/.keyring-pw`) or every gmail read fails with "no TTY available for keyring file backend password prompt" — plain `terminal` calls work because the interactive session env already has it, but subprocess calls from execute_code must pass it explicitly in env.
- Exclude non-issue and non-candidate mail from the count entirely — don't fold them into either bucket or park them inside not_vva with a "not an issue report" snippet; move them to a separate `excluded` key in /tmp/student-buckets.json (data retained, out of the counts). This includes thank-you/feedback notes with no complaint, cold job-inquiry emails sitting in the same inbox, calendar RSVP replies ("Maybe"/"Tentative"), and background-check/reference-check requests from third-party vendors. Prefix snippets of items that still need a human action (a bounce with a fixable address, a Drive access request) with `ACTIONABLE` so they surface without polluting the counts. Google Drive "Share request for ti-session-…/ses_…-recording" notification emails (drive-shares-dm-noreply@google.com) are access requests to session recordings — from candidates OR internal stakeholders — bucket as excluded+ACTIONABLE, never as student issue reports.
- A reschedule request ("I missed my slot, can I get another") is not a technical issue, even if the candidate vaguely cites "a technical issue on my end" as the reason for missing it — only count it as a technical issue if they describe an actual platform/system failure they experienced while attempting the assessment.
- When cross-checking candidate-reported symptoms against an existing internal RCA doc for that system, map each candidate's literal symptom to the doc's specific listed causes — don't assume the doc's categories are exhaustive. A symptom that doesn't fit any listed cause (e.g. "the interviewer went silent mid-session but never ended it" vs. the doc's "session ended abruptly" and "can't resume after reconnect" categories) is worth flagging back to the doc owner as a possible missing root cause, not silently filed under the nearest-sounding existing category.
- Before accepting or dismissing a candidate's claim that a specific UI/workflow guard is missing or failed (e.g. "accidentally submitted"), grep the actual current wrapper code for that guard rather than assuming from memory or the ticket description. A claim of "accidental submit" only holds up if there's genuinely no confirmation step; if the code shows an explicit two-step confirm (e.g. a `DoneConfirmModal`/`alertdialog` requiring a separate Confirm click), the claim doesn't indicate a bug and should be filed as "not an issue," not investigated further or fixed defensively.
- Repeated quota-recovery refires degrade to zero-API verification. A quota watchdog can refire many times in one day with a byte-identical /tmp/sg-threads.json snapshot; after the first full re-verification pass, later passes need at most one targeted search plus a programmatic thread-id membership check against the bucket file (zero `thread get` calls). Before applying that shortcut, compare the bucket file's earliest entry date against the task's actual cutoff date — a partial prior run may have bucketed only the `newer_than:3d` window while the task cutoff is much older (e.g. Sep 18 cutoff with an Oct 5-6-only bucket file), in which case the whole gap between them is still unread and MUST be paged with `after:YYYY/MM/DD before:YYYY/MM/DD` searches before declaring coverage complete. Also sweep for hygiene: the same thread id listed under two same-sender entries (consolidate to one entry per sender) or one sender sitting in two buckets (keep the correct bucket, drop the duplicate) — 17 refires in a single day accumulated both defects unnoticed until a programmatic dup check. Also on every refire, re-check the existing bucket file against the skill's current bucket taxonomy (e.g. cold job-inquiry emails belong in `excluded`, not `not_vva`) — an older partial run may predate a rule and need re-homing entries. Store the thread id in every bucket entry at write time (`{from, subject, snippet, thread_id}`) — a bucket file without ids makes the zero-API membership check impossible and forces a full re-read of every snapshot thread (~1 quota unit each, cheap but avoidable). The prescribed targeted search's domain list (`iiita.ac.in OR gmail.com`) can go stale when recruiting opens a new college cohort (observed 12 Oct 2026: a whole NIT Kurukshetra wave on `nitkkr.ac.in` was invisible to the prescribed query and only surfaced via the watchdog snapshot's SENT carriers) — on every quota-cleared refire, diff the snapshot's thread IDs against the search results AND against bucketed IDs, and if any SENT carrier domain is absent from the search's domain list, add one `in:inbox -from:me <new-domain> newer_than:3d` search for that domain before declaring coverage complete. When ids are absent and a refire snapshot needs verifying against a complete prior bucket file, reads-only verification (one targeted search + `gmail thread get` on each SENT thread with messageCount >= 2, 2s spacing) is the correct posture: reads cost ~1 unit each and a 13-thread verify fits trivially under quota with no search paging.
- A refire arriving shortly after another refire's write can be ZERO-API: reuse the just-prior refire's fresh targeted-search dump (e.g. /tmp/sg-targeted.json written minutes ago) as the freshness check against the current watchdog snapshot instead of issuing its own search — only fall back to a live search if no dump is newer than the snapshot. Observed 9 Oct 19:57Z (73rd refire): snapshot thread set vs the 19:37Z dump showed no new mail, and the whole run was repair + verify with 0 API calls.
- Before ANY API call on a quota-cleared refire: read /tmp/student-buckets-status.json and the current /tmp/student-buckets.json FIRST — if state is settled-verified, the run is a membership-check/append job, never a from-scratch keyword bucketing. Observed refire 69 (9 Oct 16:20Z): the run wrote a fresh 6-entry keyword-bucketed file over the settled vva=0/not_vva=19/excluded=13 file before ever consulting the status sidecar; repair from the pre-refire backup + notes + local dumps cost the whole run's margin. Skipping the pre-API discipline step is the root cause of every wholesale-overwrite corruption; running a bucketing script at all on a settled state is the failure.
- A refire run must never overwrite the settled bucket file wholesale — append/merge new threads only. A refire that finds the bucket file's window counts contradicting the settled status sidecar (e.g. status says vva=0 but the file shows vva=12) must treat the FILE as corrupted, not the status: verify each disputed entry against the local per-thread dumps (/tmp/sg-thread-<id>.txt, /tmp/sg-thread-summary.json, /tmp/student-buckets-notes.json) and repair toward the settled counts, never re-run keyword bucketing from scratch. Observed 9 Oct 2026 (02:21Z): a refire replaced a settled vva=0 file with a keyword-drifted vva=12 version (all 12 were missing-calendar-invite technical-assessment complaints per the not_vva rule above); repaired entirely from local dumps with 1 API call (the targeted newer_than:3d search only). Observed again same day (04:35Z, 4th corruption): a keyword-only re-bucketing overwrote the 04:05Z settled file (vva=12/not_vva=3, no meta block, duplicate same-tid entry) even though the meta-block guard was in place; repaired from corrupt-0221Z settled entries + notes + sg-read dumps with 1 API call (single `thread get` on the one genuinely new snapshot tid, a cold BGV-vendor outreach -> excluded+ACTIONABLE). Observed 5th corruption same day (06:14Z overwrite of the 05:05Z hand-verified / 05:31Z noop settled file): the refire writer made its own targeted search + reads (sg-targeted.json, sg-read dumps, sg-fetched-ids.json) but still keyword-bucketed from scratch, drift-filing 9 window threads into vva, dropping 13 window tids and the excluded key, while preserving pre-window cumulative entries. Repair source hierarchy that worked: settled counts from the status sidecar, per-tid classification from corrupt-<timestamp> copies of the settled file + backup-refire46 + skipped/notes JSON + sg-thread-summary bodies, 1 `thread get` only for tids with no local dump. Corrupt-file forensic tells: WRONG BUCKET KEY NAMES is the fastest corruption tell — a file using `scheduling`/`skipped_non_issue`/`bounces` instead of the taxonomy's `not_vva`/`skipped_not_issue_reports`/`delivery_failures_noted`, or missing the meta block, means a fresh keyword-bucketing overwrote settled state (observed 6th corruption, 10 Oct 01:49Z, exactly this signature; zero-API repair from the newest `student-buckets-backup-refire*.json` restored settled counts cleanly). Window entries carrying colleague as `from` on SENT threads (candidate belongs in `from`), and a meta-block placeholder timestamp (e.g. `06:4xZ`) left unfilled — fill meta timestamps programmatically, never by hand-editing the final JSON. Pattern confirmed: the meta-block guard protects only writers that READ the file first; a refire that re-buckets from scratch without loading the existing file bypasses it. Recovery never needs more than 1 search + 1 read per new tid because the settled counts are reconstructible from corrupt copies + notes + sg-read dumps. Observed failure (7 Oct 2026): after a settled hand-verified pass (13:28Z, window vva=0 not_vva=9 excluded=14), a later refire first hit the keyring gotcha (all reads failed, error list written to /tmp), then on quota recovery re-ran keyword bucketing from scratch and REPLACED the file with a drifted version (8 vva / 1 not_vva, no thread_ids, login-issue and reschedule mail misfiled into vva). Guard: before writing, check a status/meta block in the bucket file for a prior settled pass; if one exists and the snapshot's thread-id set adds nothing new, write nothing (or only append) and leave the settled file authoritative. The status file alone is NOT sufficient protection — observed (8 Oct 2026, twice): a settled hand-verified pass (22:45Z) was wholesale-overwritten 21 minutes later (23:06Z) by a keyword-only re-bucketing that never read the sidecar. The settled marker must live INSIDE the bucket file itself as a top-level `meta` block (`meta.state: settled-hand-verified` + window counts + the round-based rule), and every write must first `json.load` the existing file and bail (merge/append only) when `meta.state` says settled. Keep the corrupt overwrite as a .corrupt copy for forensics. The raw per-thread read dumps (a `/tmp/sg-thread-summary.json` bodies pass plus per-thread `.json`/`.txt` files from the read loop) are the recovery source: a corrupted bucket file can be fully reconstructed from them with zero Gmail API calls, so always write those dumps alongside the bucket file and never clean them up while the watchdog can still refire. Write a status file (/tmp/student-buckets-status.json) recording refire count, API calls used, and cumulative vs window counts so later refires can no-op cheaply. Observed 8th corruption (10 Oct 08:21Z): a keyword-only re-bucket (vva=1/not_vva=24, no meta/tids) overwrote the refire-94/95 settled state ~40 min after its last verification — restored byte-equal from student-buckets-backup-refire94.json with 1 API call; the meta-block guard inside the file is necessary but still not sufficient because rogue writers never load the file first. Repair stays cheap ONLY while per-refire backups (`student-buckets-backup-refire<N>.json`) exist: keep writing one on every settled run.
- Missing-calendar-invite / "no video call link" complaints on the technical-assessment invitation are not_vva, not vva, even though they mention "video call": the link they are missing is the proctoring call for the ADD technical session (the invite text itself says the video call link is in the calendar invite for that session). Only complaints about the VVA/Project Deep-Dive interview experience itself (AI interviewer behavior, camera/mic during the deep dive, deep-dive session failures) are vva. Keyword-matching on "video call"/"calendar invite" without reading which assessment the mail refers to produces the drift above.
